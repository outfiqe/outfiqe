# gamification

## Purpose

The admin control surface for the whole gamification system (spec 29–33/40): an overview of platform-wide XP/badge stats, the `Level` ladder, per-activity XP config and anti-abuse limits, the full badge catalog (create/edit, rule-based or admin-award), and manual actions — hand-awarding or removing a badge, granting or docking a user's XP — each with a mandatory reason.

## Structure

- `schemas.ts` — Zod response schemas mirroring the API's admin DTOs (`Level`, `ActivityXpConfig`, `BadgeAdmin`, `ChallengeAdmin`, `ManualAward`, `XpStats`, `BadgeStats`, `AwardBadgeResult`, `AdjustXpResult`) plus the enum value lists (`badgeCategorySchema`, `achievementMetricSchema`, etc.) hand-mirrored from the API's Prisma enums, same pattern `packages/types` already uses elsewhere in this monorepo. `ruleBasedRequirementTypeSchema` narrows `achievementRequirementTypeSchema` by `.exclude([ADMIN_AWARD_REQUIREMENT_TYPE])` for `ChallengeAdmin.achievement.requirementType`, since a challenge's achievement can never be `ADMIN_AWARD` — the backend never lets one be created that way.
- `api.ts` — `gamificationApi`, one function per admin endpoint under `/xp/*`, `/badges/*`, and `/challenges/*`.
- `badgeOptions.constants.ts` — `CATEGORY_OPTIONS`/`RARITY_OPTIONS`/`SHAPE_OPTIONS`/`RULE_BASED_REQUIREMENT_TYPES`, shared between `BadgesSection` and `ChallengesSection` since both forms edit the same underlying `Badge`/`Achievement` field set.
- `conditions/` — `ConditionsEditor.tsx` (the repeatable metric/operator/value rows) plus `condition.types.ts`/`condition.constants.ts`, shared between `BadgesSection` and `ChallengesSection` for the same reason.
- `datetime.utils.ts` — `toDatetimeLocalValue`/`toIsoOrNull`, shared between `BadgesSection` (optional seasonal window) and `ChallengesSection` (required challenge window).
- `StatsSection.tsx` — the overview tiles (spec 29), reusing `StatCard` from `../trending/TrendStatCards` directly by file path rather than duplicating it — a plain two-prop presentational component with nothing trending-specific about it.
- `LevelsSection.tsx` — `Level` list + create form + edit modal (name/required XP/icon, plus an `isActive` toggle — there's no delete; see the API's `xp/README.md` for why).
- `ActivityConfigSection/` — the `ActivityXpConfig` list + edit modal (enabled/XP amount/daily limit/cooldown/max-per-entity): `index.tsx`, `ActivityConfigCard.tsx`, `ActivityConfigFields.tsx`, `EditActivityConfigModal.tsx`, `activityConfigForm.types.ts`/`.constants.ts`/`.utils.ts` — same folder split as `BadgesSection`/`ChallengesSection`, applied here once the feature settled into that pattern even though this section's own form was never large on its own. Only rows that already exist are listed; there's no "add a new activity type" here, since `XpActivityType` is a fixed enum, not admin-defined data.
- `BadgesSection/` — the badge catalog: `index.tsx` (the section — list + create-form toggle + query/mutation wiring), `BadgeCard.tsx` (one catalog list item), `BadgeFields.tsx` (the shared create/edit field set, including the requirement-type toggle — checking "Admin-award only" swaps the form from a requirement-type-plus-conditions-plus-seasonal-window editor to a single assignment-limit field, mirroring the API's `createBadgeSchema`/`updateBadgeSchema` discriminated union exactly, see rationale below), `EditBadgeModal.tsx` (the edit modal, including the badge-level `Active` toggle and the achievement-level "engine evaluates this" toggle), and `badgeForm.types.ts`/`badgeForm.constants.ts`/`badgeForm.utils.ts` (form state shape, empty-state constants, and the `BadgeAdmin` ⇄ `BadgeFormState` ⇄ `BadgeFormInput` mapping functions).
- `ChallengesSection/` — time-boxed goals (spec 36–37), managed as their own list distinct from the general badge catalog even though a challenge _is_ a `Badge`+`Achievement` under the hood: `index.tsx`, `ChallengeCard.tsx`, `ChallengeFields.tsx` (challenge promo copy + banner upload + required start/end dates + the underlying badge's own fields + its conditions — no "admin-award" branch, since a challenge is always rule-based), `EditChallengeModal.tsx` (the challenge-level `isActive` "listed on the challenges page" toggle and the achievement-level "engine evaluates this" toggle, independent of each other exactly like `BadgesSection`'s), and `challengeForm.types.ts`/`.constants.ts`/`.utils.ts`. See rationale below for why the form has two separate name/description pairs.
- `ManualActionsSection.tsx` — three pieces: `AwardBadgeForm` (pick an active badge, a user id, a reason), `AdjustXpForm` (user id, a signed amount, a reason), and `ManualAwardsList` (every currently-manual, not-yet-removed `UserBadge`, each with a `Remove` button that prompts for a removal reason via `window.prompt`).
- `GamificationPage.tsx` — composes the sections in one page, same shape as `../commissions/CommissionsPage.tsx`.

## Funnel

**User-facing:** an admin opens **Gamification** from the sidebar, sees the overview tiles at a glance, adjusts levels/activity XP/badges as needed, and uses the manual-action forms at the bottom for one-off awards, removals, or XP corrections — each action requires typing a reason before it goes through.

**Technical:** every section is an independent `useQuery`/`useMutation` pair against `gamificationApi`, invalidating its own query key (and, where relevant, `admin-badge-stats`) on success — there's no single page-level data-fetch, each section owns its own loading/error state, same as `../commissions`' `CommissionTiersSection`/`CommissionsListSection` split. `BadgesSection` and `ManualActionsSection` both query `["admin-badges"]` independently (same literal key in two files) rather than sharing an export, so React Query's cache naturally dedupes the actual network request without either file importing from the other.

## Non-obvious rationale

**`ManualActionsSection`'s "User ID"/"Amount" fields used fixed-width classes (`w-72`, `w-56`, `w-32`) that overflowed the viewport at 360px, found live during chunk 13's polish pass.** `flex flex-wrap` only wraps whole items onto new rows — it doesn't shrink an individual item below its own declared width, so once the admin sidebar plus the badge-select and User ID inputs' combined fixed widths exceeded 360px, the row overflowed instead of wrapping cleanly. Fixed by making each field `w-full` by default and only fixing its width from `sm:` up (`w-full sm:w-72`, etc.) — every other field in this feature (`LevelsSection`, `ActivityConfigSection`, `BadgesSection`) happened to already fit at 360px with their smaller fixed widths, verified directly rather than assumed, so only the actually-broken fields were touched.

**`Select`/`Checkbox` are new `packages/design-system` primitives, added as part of this feature.** Neither existed before this chunk — every previous admin form only needed text/number inputs. Both are plain native `<select>`/`<input type="checkbox">` styled to match `input.tsx`, not Radix-based, matching `multi-select.tsx`'s own internal option-picker (also a styled native `<select>`) rather than introducing a new interaction pattern this design system doesn't otherwise use. See `packages/design-system/README.md`.

**Every form field has an explicit `id`/`htmlFor` pair, including a per-row `idPrefix` for `BadgesSection`'s/`ChallengesSection`'s create-form vs. edit-modal instances and their per-condition rows.** The pattern this feature's forms are modeled after (`../commissions/CommissionTiersSection.tsx`) uses bare `<label>` text with no `htmlFor`, an existing accessibility gap not worth fixing wholesale there but not worth propagating into new code either — screen readers can't associate an unlabelled control with its label otherwise. `ManualActionsSection`'s forms use static ids since each renders at most one instance at a time; `ActivityConfigSection` takes an `idPrefix` prop too even though it's in the same one-instance-at-a-time situation — consistent with every other section's field component rather than a special case, since it costs nothing and stops being "static ids are fine here" from silently going stale if a create form is ever added later. `LevelsSection`'s, `BadgesSection`'s, and `ChallengesSection`'s fields take a real per-instance `idPrefix` because their create form and edit modal can be mounted simultaneously (create form always visible/toggleable, edit modal opens on top of it), and two elements sharing one `id` on the same page is its own real bug, not just a style nit.

**The badge create/edit form's "Admin-award only" checkbox is a UI-level toggle over one `BadgeFormState`, not two separate forms.** `toFormInput` reads `form.isAdminAward` and emits either `{ requirementType: "ADMIN_AWARD" }` (no `conditions` key at all) or `{ requirementType, conditions }` — matching the API's `.strict()` discriminated union exactly, so an admin can't submit a shape the backend would reject. The conditions/assignment-limit sub-fields the toggle hides stay in local state even while hidden, so switching the checkbox back and forth doesn't lose what was typed.

**`ADMIN_AWARD_REQUIREMENT_TYPE` is a named export from `schemas.ts`, not a bare `"ADMIN_AWARD"` string repeated at each call site.** Every comparison against the admin-award requirement type — `BadgeCard`'s status line, `badgeForm.utils.ts`'s `formForBadge`/`toFormInput` — imports this one constant instead of retyping the literal, so a rename or a future additional exclusive-type value only needs to change in one place; the enum's own definition (`achievementRequirementTypeSchema`) is the only place the literal string itself appears.

**Seasonal-window inputs (`type="datetime-local"`) store local wall-clock time; the conversion to/from the API's UTC ISO strings happens entirely in `badgeForm.utils.ts`, not inline in the component.** `toDatetimeLocalValue` shifts a UTC ISO string by the browser's own timezone offset before slicing to `"YYYY-MM-DDTHH:mm"` (what the input needs to display the _correct local time_, not the UTC wall-clock digits); `toIsoOrNull` relies on `new Date(datetimeLocalValueWithoutTimezone)` being interpreted as local time by the JS spec, so it's the exact inverse. Both fields are optional (`""` round-trips to/from `null`) since a seasonal window is opt-in, and both only ever appear on the rule-based branch — an `ADMIN_AWARD` badge never reads or writes them, matching the API schema excluding them from that branch entirely.

**The achievement-level "engine evaluates this achievement" checkbox lives only in `EditBadgeModal`, never the create form.** A brand-new achievement always starts active — there's no scenario where an admin creates a badge specifically to have its rule immediately paused — so `achievementIsActive` has no `BadgeFormState` field at all; it's separate local state in the modal, defaulted from `badge.achievement?.isActive`, and folded into the mutation payload only when the badge isn't admin-award (the API schema's `ADMIN_AWARD` branch rejects the key entirely under `.strict()`).

**`badgeOptions.constants.ts`, `conditions/`, and `datetime.utils.ts` are shared at the feature root, not duplicated between `BadgesSection` and `ChallengesSection`.** A challenge's admin form edits the same underlying `Badge` category/rarity/shape list, the same `ConditionsEditor`, and the same local-wall-clock-to-UTC-ISO conversion the badge form's seasonal window already needed — the moment `ChallengesSection` needed the exact same building blocks a second time, they moved up to the feature root rather than getting a second copy, the same "second module needs it" rule this codebase applies at the API-module level (`CLAUDE.md`'s Turborepo section) applied here one level down, between sibling sections of one feature.

**A challenge's form has two separate name/description pairs — one for the badge, one for the challenge itself — not one shared pair.** `name`/`description` are the badge's catalog identity (what shows in a user's badge collection once earned); `challengeName`/`challengeDescription` are the promotional copy on the challenges page itself ("August Style Sprint" vs. the badge's own "Style Sprint," say). An admin is free to make them read identically, but the form doesn't force that — see the API's `challenges/README.md` for the full reasoning, this is the admin-form side of that same design decision.

**`ChallengeFields`'s start/end dates are `required`, unlike `BadgesSection`'s optional seasonal window.** A challenge is time-boxed by definition — spec 36–37's whole premise is "finish this before it ends" — so there's no meaningful "a challenge with no end date" state the way an ordinary badge's seasonal window can legitimately be left unset. `createEmptyChallengeForm()` defaults them to "starting now, ending in a week" rather than leaving them blank, purely as a starting point the admin edits rather than types from scratch — not a business-rule default, just a form-filling convenience.

**Manual badge award targets a user by pasting their ID, not a name/handle search.** This app has an existing admin user-search endpoint scoped to creators only (`../creators`); XP/badge actions can target _any_ user, not just creators, and building a general "search any user" admin endpoint is bigger scope than this chunk needs. An admin acting on a specific user typically already has their id from another admin screen. Flagged as a deliberate scope cut, not an oversight — worth revisiting if manual actions turn out to be a frequent workflow.
