# gamification

## Purpose

The admin control surface for the whole gamification system (spec 29–33/40): an overview of platform-wide XP/badge stats, the `Level` ladder, per-activity XP config and anti-abuse limits, the full badge catalog (create/edit, rule-based or admin-award), and manual actions — hand-awarding or removing a badge, granting or docking a user's XP — each with a mandatory reason.

## Structure

- `schemas.ts` — Zod response schemas mirroring the API's admin DTOs (`Level`, `ActivityXpConfig`, `BadgeAdmin`, `ChallengeAdmin`, `ManualAward`, `XpStats`, `BadgeStats`, `AwardBadgeResult`, `AdjustXpResult`) plus the enum value lists (`badgeCategorySchema`, `achievementMetricSchema`, etc.) hand-mirrored from the API's Prisma enums, same pattern `packages/types` already uses elsewhere in this monorepo. `ruleBasedRequirementTypeSchema` narrows `achievementRequirementTypeSchema` by `.exclude([ADMIN_AWARD_REQUIREMENT_TYPE])` for `ChallengeAdmin.achievement.requirementType`, since a challenge's achievement can never be `ADMIN_AWARD` — the backend never lets one be created that way.
- `api.ts` — `gamificationApi`, one function per admin endpoint under `/xp/*`, `/badges/*`, and `/challenges/*`.
- `badgeOptions.constants.ts` — `CATEGORY_OPTIONS`/`RARITY_OPTIONS`/`SHAPE_OPTIONS`/`RULE_BASED_REQUIREMENT_TYPES`/`ANIMATION_OPTIONS`/`ANIMATION_OPTION_LABEL`/`AUTO_ANIMATION_OPTION`, shared between `BadgesSection` and `ChallengesSection` since both forms edit the same underlying `Badge`/`Achievement` field set. `AUTO_ANIMATION_OPTION` (`"auto"`) is a form-only sentinel, never sent to the API — see rationale below.
- `conditions/` — `ConditionsEditor.tsx` (the repeatable metric/operator/value rows) plus `condition.types.ts`/`condition.constants.ts`, shared between `BadgesSection` and `ChallengesSection` for the same reason. `METRIC_OPTIONS` includes seven `*_rank` metrics (one per `creator-leaderboard` category) alongside the original counter metrics — meaningful mainly on a badge with "Dynamic" checked, since only rank metrics can ever cause a re-check to revoke eligibility (see `apps/api/src/modules/achievements/README.md`).
- `datetime.utils.ts` — `toDatetimeLocalValue`/`toIsoOrNull`, shared between `BadgesSection` (optional seasonal window) and `ChallengesSection` (required challenge window).
- `StatsSection.tsx` — the overview tiles (spec 29), reusing `StatCard` from `../trending/TrendStatCards` directly by file path rather than duplicating it — a plain two-prop presentational component with nothing trending-specific about it.
- `LevelsSection.tsx` — `Level` list + create form + edit modal (name/required XP/icon, plus an `isActive` toggle — there's no delete; see the API's `xp/README.md` for why).
- `MultipliersSection.tsx` — `XpMultiplier` list + create form + edit modal (label/multiplier/start/end, plus an `isActive` toggle), same single-file shape as `LevelsSection.tsx` since it's structurally the same "creatable list with an edit modal" pattern. Each row computes and shows a "● live now" badge client-side (`isCurrentlyActive`, checking `isActive` and the current time against `startsAt`/`endsAt`) so an admin can see at a glance which window, if any, is actually in effect right now without cross-referencing dates by hand.
- `ActivityConfigSection/` — the `ActivityXpConfig` list + edit modal (enabled/XP amount/daily limit/cooldown/max-per-entity): `index.tsx`, `ActivityConfigCard.tsx`, `ActivityConfigFields.tsx`, `EditActivityConfigModal.tsx`, `activityConfigForm.types.ts`/`.constants.ts`/`.utils.ts` — same folder split as `BadgesSection`/`ChallengesSection`, applied here once the feature settled into that pattern even though this section's own form was never large on its own. Only rows that already exist are listed; there's no "add a new activity type" here, since `XpActivityType` is a fixed enum, not admin-defined data.
- `BadgesSection/` — the badge catalog: `index.tsx` (the section — list + create-form toggle + query/mutation wiring), `BadgeCard.tsx` (one catalog list item, its summary line now also flags `· dynamic` when set, and `· sponsored by {brand}` when a sponsor is attached), `BadgeFields.tsx` (the shared create/edit field set, including the requirement-type toggle — checking "Admin-award only" swaps the form from a requirement-type-plus-conditions-plus-seasonal-window editor to a single assignment-limit field, mirroring the API's `createBadgeSchema`/`updateBadgeSchema` discriminated union exactly, see rationale below — plus a "Dynamic" checkbox, independent of that toggle, since a dynamic badge is still ordinarily rule-based — an "Animation" dropdown, defaulting to "Auto (by rarity)" — and the "Sponsor brand" field), `BrandSponsorField.tsx` (a single-select brand search, typed straight from `../schemas`' `SponsorBrand` — see rationale below for why it reuses the public brand search endpoint rather than a dedicated admin one), `EditBadgeModal.tsx` (the edit modal, including the badge-level `Active` toggle and the achievement-level "engine evaluates this" toggle), and `badgeForm.types.ts`/`badgeForm.constants.ts`/`badgeForm.utils.ts` (form state shape, empty-state constants, and the `BadgeAdmin` ⇄ `BadgeFormState` ⇄ `BadgeFormInput` mapping functions).
- `ChallengesSection/` — time-boxed goals (spec 36–37), managed as their own list distinct from the general badge catalog even though a challenge _is_ a `Badge`+`Achievement` under the hood: `index.tsx`, `ChallengeCard.tsx`, `ChallengeFields.tsx` (challenge promo copy + banner upload + required start/end dates + the underlying badge's own fields + its conditions — no "admin-award" branch, since a challenge is always rule-based), `EditChallengeModal.tsx` (the challenge-level `isActive` "listed on the challenges page" toggle and the achievement-level "engine evaluates this" toggle, independent of each other exactly like `BadgesSection`'s), and `challengeForm.types.ts`/`.constants.ts`/`.utils.ts`. See rationale below for why the form has two separate name/description pairs.
- `LeaderboardSection.tsx` — the seven creator-leaderboard categories (spec 36–37), each with a single enabled/disabled toggle — no create form, no fields to edit beyond that one flag, since the categories themselves are a fixed set the same way `ActivityXpConfig`'s activity types are. Kept as one file rather than a folder, unlike `BadgesSection`/`ChallengesSection`/`ActivityConfigSection` — there's no separate "fields" component or edit modal to split out when a row is just a label and a checkbox.
- `CompetitionsSection.tsx` — recurring weekly creator competitions: create form + list + edit modal, one file, same shape as `LevelsSection.tsx`/`MultipliersSection.tsx` (a creatable list with an edit modal, no achievement/conditions editor to justify a folder the way `BadgesSection`/`ChallengesSection` needed one). The form has two distinct groups — the competition itself (name, which leaderboard category it ranks by, how many winners each week) and the trophy badge it awards (the same category/rarity/shape/color/animation/permanence fields `BadgeFields`/`ChallengeFields` already use, reusing the shared `badgeOptions.constants.ts` options). `LEADERBOARD_CATEGORY_OPTIONS`/`LEADERBOARD_CATEGORY_LABEL` moved into `badgeOptions.constants.ts` from where they used to live only inside `LeaderboardSection.tsx`, the moment this section needed the exact same category list and labels a second time.
- `ManualActionsSection.tsx` — three pieces: `AwardBadgeForm` (pick an active badge, a user id, a reason), `AdjustXpForm` (user id, a signed amount, a reason), and `ManualAwardsList` (every currently-manual, not-yet-removed `UserBadge`, each with a `Remove` button that prompts for a removal reason via `window.prompt`).
- `GamificationOverviewPage.tsx` — the stats tiles alone (spec 29), the page the "Gamification" sidebar link itself opens.
- `GamificationXpLevelsPage.tsx` — `LevelsSection` + `MultipliersSection` + `ActivityConfigSection`.
- `GamificationBadgesPage.tsx` — `BadgesSection` + `ChallengesSection`.
- `GamificationLeaderboardsPage.tsx` — `LeaderboardSection` + `CompetitionsSection`.
- `GamificationManualActionsPage.tsx` — `ManualActionsSection` alone.

## Funnel

**User-facing:** an admin opens **Gamification** from the sidebar and lands on the overview tiles, then expands the sidebar item to reach **XP & Levels**, **Badges & Challenges**, **Leaderboards**, or **Manual Actions** as separate pages — each a real, bookmarkable/back-button-navigable route rather than a client-side tab, and the admin sidebar highlights both the active page and its expanded "Gamification" parent. Each page still adjusts its own settings as before; manual-action forms still require typing a reason before an award/removal/XP correction goes through.

**Technical:** originally one `GamificationPage.tsx` stacked all nine sections in a single long scroll. Once that became unwieldy, it was split into five sibling pages, each with its own flat-file TanStack route (`_authenticated.gamification.index.tsx`, `.xp-levels.tsx`, `.badges.tsx`, `.leaderboards.tsx`, `.manual-actions.tsx` — same dot-notation convention `_authenticated.orders.$orderId.tsx`/`.orders.index.tsx` already use), and `AdminSidebar.tsx`'s `NAV_SECTIONS` gained the feature's first use of `SidebarNavItem.items` (nested/expandable sub-links, `packages/components/src/sidebar`'s existing but previously-unused support for it) rather than an in-page tab bar. Every section is still an independent `useQuery`/`useMutation` pair against `gamificationApi`, invalidating its own query key (and, where relevant, `admin-badge-stats`) on success — there's no page-level data-fetch, each section owns its own loading/error state, same as `../commissions`' `CommissionTiersSection`/`CommissionsListSection` split. `BadgesSection` and `ManualActionsSection` both query `["admin-badges"]` independently (same literal key in two files) rather than sharing an export, so React Query's cache naturally dedupes the actual network request without either file importing from the other.

## Non-obvious rationale

**`ManualActionsSection`'s "User ID"/"Amount" fields used fixed-width classes (`w-72`, `w-56`, `w-32`) that overflowed the viewport at 360px, found live during chunk 13's polish pass.** `flex flex-wrap` only wraps whole items onto new rows — it doesn't shrink an individual item below its own declared width, so once the admin sidebar plus the badge-select and User ID inputs' combined fixed widths exceeded 360px, the row overflowed instead of wrapping cleanly. Fixed by making each field `w-full` by default and only fixing its width from `sm:` up (`w-full sm:w-72`, etc.) — every other field in this feature (`LevelsSection`, `ActivityConfigSection`, `BadgesSection`) happened to already fit at 360px with their smaller fixed widths, verified directly rather than assumed, so only the actually-broken fields were touched.

**`Select`/`Checkbox` are new `packages/design-system` primitives, added as part of this feature.** Neither existed before this chunk — every previous admin form only needed text/number inputs. Both are plain native `<select>`/`<input type="checkbox">` styled to match `input.tsx`, not Radix-based, matching `multi-select.tsx`'s own internal option-picker (also a styled native `<select>`) rather than introducing a new interaction pattern this design system doesn't otherwise use. See `packages/design-system/README.md`.

**Every form field has an explicit `id`/`htmlFor` pair, including a per-row `idPrefix` for `BadgesSection`'s/`ChallengesSection`'s create-form vs. edit-modal instances and their per-condition rows.** The pattern this feature's forms are modeled after (`../commissions/CommissionTiersSection.tsx`) uses bare `<label>` text with no `htmlFor`, an existing accessibility gap not worth fixing wholesale there but not worth propagating into new code either — screen readers can't associate an unlabelled control with its label otherwise. `ManualActionsSection`'s forms use static ids since each renders at most one instance at a time; `ActivityConfigSection` takes an `idPrefix` prop too even though it's in the same one-instance-at-a-time situation — consistent with every other section's field component rather than a special case, since it costs nothing and stops being "static ids are fine here" from silently going stale if a create form is ever added later. `LevelsSection`'s, `BadgesSection`'s, and `ChallengesSection`'s fields take a real per-instance `idPrefix` because their create form and edit modal can be mounted simultaneously (create form always visible/toggleable, edit modal opens on top of it), and two elements sharing one `id` on the same page is its own real bug, not just a style nit.

**The badge create/edit form's "Admin-award only" checkbox is a UI-level toggle over one `BadgeFormState`, not two separate forms.** `toFormInput` reads `form.isAdminAward` and emits either `{ requirementType: "ADMIN_AWARD" }` (no `conditions` key at all) or `{ requirementType, conditions }` — matching the API's `.strict()` discriminated union exactly, so an admin can't submit a shape the backend would reject. The conditions/assignment-limit sub-fields the toggle hides stay in local state even while hidden, so switching the checkbox back and forth doesn't lose what was typed.

**`ADMIN_AWARD_REQUIREMENT_TYPE` is a named export from `schemas.ts`, not a bare `"ADMIN_AWARD"` string repeated at each call site.** Every comparison against the admin-award requirement type — `BadgeCard`'s status line, `badgeForm.utils.ts`'s `formForBadge`/`toFormInput` — imports this one constant instead of retyping the literal, so a rename or a future additional exclusive-type value only needs to change in one place; the enum's own definition (`achievementRequirementTypeSchema`) is the only place the literal string itself appears.

**Seasonal-window inputs (`type="datetime-local"`) store local wall-clock time; the conversion to/from the API's UTC ISO strings happens entirely in `badgeForm.utils.ts`, not inline in the component.** `toDatetimeLocalValue` shifts a UTC ISO string by the browser's own timezone offset before slicing to `"YYYY-MM-DDTHH:mm"` (what the input needs to display the _correct local time_, not the UTC wall-clock digits); `toIsoOrNull` relies on `new Date(datetimeLocalValueWithoutTimezone)` being interpreted as local time by the JS spec, so it's the exact inverse. Both fields are optional (`""` round-trips to/from `null`) since a seasonal window is opt-in, and both only ever appear on the rule-based branch — an `ADMIN_AWARD` badge never reads or writes them, matching the API schema excluding them from that branch entirely.

**The achievement-level "engine evaluates this achievement" checkbox lives only in `EditBadgeModal`, never the create form.** A brand-new achievement always starts active — there's no scenario where an admin creates a badge specifically to have its rule immediately paused — so `achievementIsActive` has no `BadgeFormState` field at all; it's separate local state in the modal, defaulted from `badge.achievement?.isActive`, and folded into the mutation payload only when the badge isn't admin-award (the API schema's `ADMIN_AWARD` branch rejects the key entirely under `.strict()`).

**`badgeOptions.constants.ts`, `conditions/`, and `datetime.utils.ts` are shared at the feature root, not duplicated between `BadgesSection` and `ChallengesSection`.** A challenge's admin form edits the same underlying `Badge` category/rarity/shape list, the same `ConditionsEditor`, and the same local-wall-clock-to-UTC-ISO conversion the badge form's seasonal window already needed — the moment `ChallengesSection` needed the exact same building blocks a second time, they moved up to the feature root rather than getting a second copy, the same "second module needs it" rule this codebase applies at the API-module level (`CLAUDE.md`'s Turborepo section) applied here one level down, between sibling sections of one feature.

**A challenge's form has two separate name/description pairs — one for the badge, one for the challenge itself — not one shared pair.** `name`/`description` are the badge's catalog identity (what shows in a user's badge collection once earned); `challengeName`/`challengeDescription` are the promotional copy on the challenges page itself ("August Style Sprint" vs. the badge's own "Style Sprint," say). An admin is free to make them read identically, but the form doesn't force that — see the API's `challenges/README.md` for the full reasoning, this is the admin-form side of that same design decision.

**`ChallengeFields`'s start/end dates are `required`, unlike `BadgesSection`'s optional seasonal window.** A challenge is time-boxed by definition — spec 36–37's whole premise is "finish this before it ends" — so there's no meaningful "a challenge with no end date" state the way an ordinary badge's seasonal window can legitimately be left unset. `createEmptyChallengeForm()` defaults them to "starting now, ending in a week" rather than leaving them blank, purely as a starting point the admin edits rather than types from scratch — not a business-rule default, just a form-filling convenience.

**`LeaderboardSection`'s toggle disabling a category actually withholds its ranking from the public API — it isn't a client-side "hide this tab" hint.** `GET /creator-leaderboard`'s `getTop()` short-circuits to an empty `entries` array the moment a category's `enabled` flag is off, before touching Redis at all — matching spec 37's "leaderboards should stay optional" as a real, server-enforced state rather than a display preference a client could bypass. See the API's `creator-leaderboard/README.md`.

**Manual badge award targets a user by pasting their ID, not a name/handle search.** This app has an existing admin user-search endpoint scoped to creators only (`../creators`); XP/badge actions can target _any_ user, not just creators, and building a general "search any user" admin endpoint is bigger scope than this chunk needs. An admin acting on a specific user typically already has their id from another admin screen. Flagged as a deliberate scope cut, not an oversight — worth revisiting if manual actions turn out to be a frequent workflow.

**The "Animation" dropdown has no live preview — an admin picks "Shimmer" by name, not by seeing it shimmer.** Neither this form nor anywhere else in `apps/admin` currently renders a shaped/colored badge icon at all (`BadgeCard.tsx`'s catalog list just shows the raw emoji and a text summary) — building a live preview here would mean either duplicating `apps/web`'s `AchievementBadgeIcon` shape/rarity-ring rendering logic into this app for the first time, or extracting it into a shared package neither app currently needs it from for any other reason. Given the admin form already ships usable (an admin can read what "Glow"/"Shimmer"/"Pulse"/"Radiant" mean from the name, and the actual rendering is fully correct and verified on the real collection/challenge-card surfaces in `apps/web`), a full preview was left out as a scope line rather than gold-plated in — worth building once/if this app gets its own badge-icon renderer for another reason (a live preview on `BadgeCard.tsx` itself would be a natural first use).

**`AUTO_ANIMATION_OPTION` (`"auto"`) exists only in `BadgeFormState`/`ChallengeFormState`, never in `BadgeAnimationValue` or the API payload.** `designConfig.animation` is optional at the API layer — omitted means "let the rarity decide," an explicit `"none"` means "force this badge static regardless of rarity," and those are two different, real states a form needs to represent even though the API only has one optional field. `toFormInput`/`toChallengeFormInput` spread the `animation` key into the payload only when it isn't the `"auto"` sentinel, so picking "Auto" sends a `designConfig` with no `animation` key at all (letting `apps/web`'s rarity-default fallback apply) rather than sending some literal `"auto"` string the API schema doesn't know about.

**`MultipliersSection`'s "● live now" indicator is computed client-side (`isCurrentlyActive`) from the same `startsAt`/`endsAt`/`isActive` fields the list already has, not a separate `isLive` field the API precomputes.** The API's own `findActiveMultiplier` query (`xp/README.md`) already does the equivalent check server-side for the real award path, but that's a different, single-row lookup at award time, not something worth threading through the admin list-all response just to save a `Date.now()` comparison client-side for a page an admin looks at occasionally, not something driving a real decision under time pressure. If this list ever needs to be correct against clock drift or needs to update live without a refetch, that's the point to reconsider moving the check server-side.

**`CompetitionFormState`/`CreatorCompetitionFormInput` use `leaderboardCategory`, matching the API's own field name exactly, not `category`.** The badge fields this form also edits already have their own `category: BadgeCategoryValue` (the trophy's catalog category, `SPECIAL`/`BEGINNER`/etc.) — see the API's `creator-competitions/README.md` for the real bug this exact collision caused server-side before the API's own field got renamed. Keeping the admin form's field name identical to the API's, rather than picking a locally-convenient name and translating at the request boundary, is what keeps that distinction visible here too instead of quietly reintroducing the same ambiguity on the client side.

**A competition's `description` is generated (`` `Awarded weekly to the top ${topN} in ${category label}.` ``), not a field the admin fills in.** Unlike `BadgesSection`/`ChallengesSection`, this form has no description input at all — the badge's `description` column still needs a value (the schema requires one), and a competition's description is entirely mechanical (derived from data the form already has), so generating it removes a field an admin would otherwise have to keep in sync with the category/topN they just picked. If this ever needs real editorial copy, the fix is adding the field back, not working around the generated string.

**The "Gamification" sidebar parent has no separate "Overview" child item pointing at `/gamification` — the parent link itself is that page.** `isNavItemActive` treats any nav item's `href` as a prefix match (`pathname.startsWith(href + "/")`), which would make the parent's `href` prefix-match every one of its own children's routes. Adding a sibling child whose own `href` was also `/gamification` would make that child's `href` prefix-match every other child's route too (`/gamification/xp-levels` starts with `/gamification/`), so it would show as active alongside whichever real sub-page is open. The fix is what's here now: the parent's own link is the overview page, and every child link is a distinct, non-prefix-of-each-other path.

**A parent nav item (one with `items`, like "Gamification") gets a distinct, muted "you're inside this section" style (`navLinkAncestorActiveClass`) when a descendant route is open, separate from the solid `navLinkActiveClass` reserved for the exact current page.** This is the common nested-nav convention (Material Design's navigation drawer, Ant Design's `Menu`, GitHub/Linear-style sidebars all do the same) — without it, a user several levels into a nested sidebar has no cue which top-level section they're in once the exact leaf isn't visible or the submenu gets collapsed. `packages/components/src/sidebar`'s `hasActiveDescendant`/`descendantActive` is what distinguishes "this item is on the active trail" from "this item literally is the current page" (`isCurrentPage`), so the two states never collide — only one row at a time ever shows the solid full-active pill. Critically, this only changes the parent's own _highlight color_, never its position or size: the row's own markup never grows/shrinks/moves when a descendant becomes active or its submenu opens or closes — only the `<ul>` of children (appended below it) toggles visibility.

**`BrandSponsorField` calls the same public `GET /api/brands?q=...` endpoint `apps/web`'s brand-browse page would use, not a new admin-only brand-search route.** It's `optionalAuth`, already paginated, and already returns exactly the public-safe id/name/avatarUrl shape this picker needs — building a second, admin-scoped brand-lookup endpoint for the same query would duplicate real, tested query logic (`apps/api/src/modules/brands/README.md`) for zero actual gain, since nothing about "which brand is this" is admin-sensitive information. `sponsorBrandId`/`sponsorBrandName` are two separate `BadgeFormState` fields, not one brand object, mirroring `CompetitionFields`' own `topN`/`leaderboardCategory` split of API-shaped primitives — `formForBadge` reads both off `badge.sponsorBrand` when editing, `toFormInput` only ever sends the id, and the name exists purely so the autocomplete input can show what's currently selected without an extra fetch on open.

**Clearing a sponsor is an explicit "✕" button next to the input, not "type nothing and blur."** An empty search box could just as easily mean "the admin hasn't finished typing yet" as "remove the sponsor," so `BrandSponsorField` only ever calls `onChange(null)` from the dedicated clear button — blurring with an empty, unsearched box reverts to whatever was last confirmed (mirroring `CityAutocomplete`'s own blur-reverts-to-value behavior), never silently drops a sponsor a click away from being lost.
