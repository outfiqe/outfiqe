# product-tour (apps/admin)

## Purpose

Guided walkthroughs of this app's two areas — the tenant CRM and the platform panel — each opened the first time the right kind of staff member reaches that area, remembered per account on the server, and replayable at any time. The steps a person sees match what their own role can actually reach — the same visibility check the sidebar itself uses decides what each tour shows.

## Structure

- `components/CrmDashboardTour.tsx` — takes the already-fetched `Organization` as a prop (from `CrmPage`, which already reads it via `["crm-organization"]`), filters the step list down to what this viewer's role and organization actually expose, and renders the design-system `Tour` (`@outfiqe/design-system`) through the shared `useTourController`.
- `constants/crmDashboardTour.ts` — the CRM tour's key, **version**, and every possible step. Each step (other than welcome/finish) carries the same `permissionKey`/`requiresLinkedBrand` shape `AdminSidebar.tsx`'s `CRM_SUB_ITEMS` uses, plus `CRM_SEARCH_TOUR_ANCHOR` for the header search box.
- `utils/visibleCrmTourSteps.ts` — filters the CRM step list through `isCrmSubItemVisible` (`@/components/AdminSidebar.utils`), the exact function the sidebar itself calls, so the tour can never describe a CRM section this viewer can't see.
- `components/PlatformDashboardTour.tsx` — the platform-panel equivalent. Fetches `["crm-organization"]` itself (`PlatformOverviewPage` doesn't already have it the way `CrmPage` does) and reads `hasPlatformAccess`/`isCoFounder`/`hiddenPlatformNavKeys` from `useAuth()`, then filters and renders the same way.
- `constants/platformDashboardTour.ts` — the platform tour's key, **version**, and its steps: a welcome card, the platform-wide figures, one step per sidebar group (Brand & Tenants, Catalog, Commerce, Moderation, Finance, Growth, Platform Settings), and a closing card. Each group step carries the `groupKey` `AdminSidebar.tsx`'s `PLATFORM_NAV_ITEMS` uses.
- `utils/visiblePlatformTourSteps.ts` — filters the platform step list through `groupPlatformNavItems` (`@/components/AdminSidebar.utils`) against the exported `PLATFORM_NAV_ITEMS`/`PLATFORM_NAV_GROUP_ICONS` (`@/components/AdminSidebar`), the exact computation the sidebar itself uses to decide which groups to render — see rationale.
- `hooks/useTourController.ts` — the same open/close/replay state machine as `apps/web`'s tour (see that app's `features/product-tour/README.md`), adapted for this app's stack: it reads and clears the `?tour=` value with `useSearchFilter` (`@/lib/useSearchFilter`) instead of Next.js's router, since this is a plain client-rendered SPA with no per-navigation server refetch to avoid. Shared by both tours — a tour key, a version and an eligibility flag are all it needs.
- `constants/tourOutcome.ts`, `constants/tourProgressQueryKey.ts`, `constants/tourReplay.ts`, `api/toursApi.ts` + `toursSchemas.ts`, `hooks/useTourProgress.ts` + `useRecordTourOutcome.ts`, `utils/hasSeenTour.ts` + `withRecordedOutcome.ts` — the same shapes as `apps/web`'s equivalents, talking to the same `GET`/`PUT /api/tours/me[...]` endpoints (`apps/api/src/modules/tours`), deliberately kept as separate small files rather than shared across apps — see rationale.
- `index.ts` — the public entry: both tour components, each one's replay destination and anchor ids, and the shared "Take the tour" label.

## Funnel

**User-facing:** a CRM member signs in and opens `/crm`. Once the organization has loaded, the tour opens with a welcome card, points at the global search box, then at each sidebar section this role can see — Partners, Customers, Contacts, Pipeline, Tasks, Support, Reports, Roles, Audit, Billing, in that order, skipping any the viewer's role or the organization itself doesn't expose — and ends with a closing card. It never opens for the platform organization, since CRM has nothing behind it there (`shouldShowCrmSection`).

Platform staff opening `/platform` get the same shape of walkthrough for that side of the app instead: a welcome card, the platform-wide totals, then one step per sidebar group, skipping any group this admin's own sidebar doesn't show (a co-founder can hide individual nav items from another admin), ending with a closing card. It never opens for someone without platform access, or while the resolved organization is a real tenant rather than the platform itself.

Both: "Take the tour" in the page's own header replays it.

**Technical:** `CrmPage`/`PlatformOverviewPage` → `CrmDashboardTour`/`PlatformDashboardTour` → `useTourController` → `useTourProgress` → `toursApi.listMine` → `GET /api/tours/me`. When a tour ends: `useRecordTourOutcome` → `toursApi.recordOutcome` → `PUT /api/tours/me/<tour-key>`. Each replay link is a TanStack Router `<Link to="..." search={{ tour: "<tour-key>" }}>`; `useTourController` sees the value, opens from step one, and clears it with the same `useSearchFilter` a status/date filter elsewhere in this app already uses to change the URL without a page reload.

## Non-obvious rationale

- **Steps are filtered per viewer, not fixed, for both tours.** A CRM Member role and an organization's SUPERADMIN can see quite different CRM sections; a platform admin can have individual platform nav items hidden by a co-founder. A single fixed tour would describe things some viewers can't open. Both `visibleCrmTourSteps` and `visiblePlatformTourSteps` reuse the sidebar's own visibility computation rather than a second, hand-maintained copy of the same rule — if a permission key or a hidden-nav-key ever changes, both places move together automatically.
- **A brand-scoped CRM step (Partners, Customers, Billing) is hidden for everyone, including a super admin, once the organization has no linked brand.** That mirrors `isCrmSubItemVisible` exactly: `requiresLinkedBrand` is about whether the data behind that section exists at all for this organization, not about who is asking.
- **The platform tour is grouped, not one step per nav link.** `PLATFORM_NAV_ITEMS` has around thirty individual links across seven sidebar groups — a step per link would make this by far the longest tour in the app for little extra value, since the groups are what the sidebar itself collapses to and what a new admin actually needs oriented first. `visiblePlatformTourSteps` calls the same `groupPlatformNavItems` the sidebar uses (with the exported `PLATFORM_NAV_ITEMS`/`PLATFORM_NAV_GROUP_ICONS`) and keeps a group's step only if that call still returns it — so a group step disappears the moment every item inside it is hidden for this viewer, exactly matching what they'd see on their own sidebar.
- **Neither admin tour has a mobile fallback design, unlike the equivalent tours in `apps/web`.** Neither the CRM nor the platform side of this app (`AdminSidebar`, `AppShell`, every page in both areas) has a responsive layout at all today — the sidebar and header render at full desktop width regardless of viewport, so there is no real "the sidebar is hidden" case for a step's anchor to gracefully fall back from here. If either area ever gets a genuine mobile layout, these tours' steps already degrade to a centred card the same way `apps/web`'s do whenever a target selector doesn't match anything on screen — nothing here would need to change.
- **`useTourController` reads and clears the replay query with `useSearchFilter`, not a raw history mutation.** `apps/web`'s equivalent avoids a real router navigation because that app's dashboard page re-authenticates and re-fetches on every visit; this app is a plain client-rendered SPA where a `navigate({ replace: true })` is instant and never touches the server, so there is nothing to work around here — reusing the same small utility every other filter in this app already uses is the simpler, more consistent choice.
- **The read/write API layer, the outcome constant and the two pure helpers are a deliberate near-duplicate of `apps/web`'s equivalents, not a shared package.** Both talk to the exact same generic `/api/tours/*` endpoints, but the piece that would most benefit from sharing — the controller hook — is inherently tied to each app's own router (Next.js vs TanStack Router) and can't be lifted without a routing abstraction neither app needs yet. This matches this codebase's existing convention for the same situation (see `paymentRedirect.ts`'s own rationale note) — lift the small shared pieces into `packages/hooks`/`packages/utils` the next time a third consumer or a real touch-point makes the duplication worth resolving, rather than doing it opportunistically here.
