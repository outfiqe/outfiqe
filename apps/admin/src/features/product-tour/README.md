# product-tour (apps/admin)

## Purpose

A guided walkthrough of the tenant CRM, opened the first time a CRM member reaches `/crm`, remembered per account on the server, and replayable at any time. The steps a person sees match what their own role can actually reach — the same permission check the sidebar itself uses decides what the tour shows.

## Structure

- `components/CrmDashboardTour.tsx` — takes the already-fetched `Organization` as a prop (from `CrmPage`, which already reads it via `["crm-organization"]`), filters the step list down to what this viewer's role and organization actually expose, and renders the design-system `Tour` (`@outfiqe/design-system`) through the shared `useTourController`.
- `constants/crmDashboardTour.ts` — the tour's key, **version**, and every possible step. Each step (other than welcome/finish) carries the same `permissionKey`/`requiresLinkedBrand` shape `AdminSidebar.tsx`'s `CRM_SUB_ITEMS` uses, plus `CRM_SEARCH_TOUR_ANCHOR` for the header search box.
- `utils/visibleCrmTourSteps.ts` — filters the full step list through `isCrmSubItemVisible` (`@/components/AdminSidebar.utils`), the exact function the sidebar itself calls, so the tour can never describe a section this viewer can't see.
- `hooks/useTourController.ts` — the same open/close/replay state machine as `apps/web`'s tour (see that app's `features/product-tour/README.md`), adapted for this app's stack: it reads and clears the `?tour=` value with `useSearchFilter` (`@/lib/useSearchFilter`) instead of Next.js's router, since this is a plain client-rendered SPA with no per-navigation server refetch to avoid.
- `constants/tourOutcome.ts`, `constants/tourProgressQueryKey.ts`, `constants/tourReplay.ts`, `api/toursApi.ts` + `toursSchemas.ts`, `hooks/useTourProgress.ts` + `useRecordTourOutcome.ts`, `utils/hasSeenTour.ts` + `withRecordedOutcome.ts` — the same shapes as `apps/web`'s equivalents, talking to the same `GET`/`PUT /api/tours/me[...]` endpoints (`apps/api/src/modules/tours`), deliberately kept as separate small files rather than shared across apps — see rationale.
- `index.ts` — the public entry: `CrmDashboardTour`, the replay destination, the search anchor id, and the shared "Take the tour" label.

## Funnel

**User-facing:** a CRM member signs in and opens `/crm`. Once the organization has loaded, the tour opens with a welcome card, points at the global search box, then at each sidebar section this role can see — Partners, Customers, Contacts, Pipeline, Tasks, Support, Reports, Roles, Audit, Billing, in that order, skipping any the viewer's role or the organization itself doesn't expose — and ends with a closing card. "Take the tour" in the page header replays it. It never opens for the platform organization, since CRM has nothing behind it there (`shouldShowCrmSection`).

**Technical:** `CrmPage` → `CrmDashboardTour` → `useTourController` → `useTourProgress` → `toursApi.listMine` → `GET /api/tours/me`. When the tour ends: `useRecordTourOutcome` → `toursApi.recordOutcome` → `PUT /api/tours/me/crm-dashboard`. The replay link is a TanStack Router `<Link to="/crm" search={{ tour: "crm-dashboard" }}>`; `useTourController` sees the value, opens from step one, and clears it with the same `useSearchFilter` a status/date filter elsewhere in this app already uses to change the URL without a page reload.

## Non-obvious rationale

- **Steps are filtered per viewer, not fixed.** A Member role and an organization's SUPERADMIN can see quite different slices of the CRM (`isCrmSubItemVisible`'s permission and linked-brand checks), so a single fixed tour would describe sections some viewers can't open. `visibleCrmTourSteps` reuses the sidebar's own visibility function rather than a second, hand-maintained copy of the same rule — if a permission key ever changes, both places move together automatically.
- **A brand-scoped step (Partners, Customers, Billing) is hidden for everyone, including a super admin, once the organization has no linked brand.** That mirrors `isCrmSubItemVisible` exactly: `requiresLinkedBrand` is about whether the data behind that section exists at all for this organization, not about who is asking.
- **The tour has no mobile fallback design, unlike the equivalent tours in `apps/web`.** The CRM section of this app (`AdminSidebar`, `AppShell`, every CRM page) has no responsive layout at all today — the sidebar and header render at full desktop width regardless of viewport, so there is no real "the sidebar is hidden" case for a step's anchor to gracefully fall back from here. If the CRM ever gets a genuine mobile layout, this tour's steps already degrade to a centred card the same way `apps/web`'s do whenever a target selector doesn't match anything on screen — nothing here would need to change.
- **`useTourController` reads and clears the replay query with `useSearchFilter`, not a raw history mutation.** `apps/web`'s equivalent avoids a real router navigation because that app's dashboard page re-authenticates and re-fetches on every visit; this app is a plain client-rendered SPA where a `navigate({ replace: true })` is instant and never touches the server, so there is nothing to work around here — reusing the same small utility every other CRM filter already uses is the simpler, more consistent choice.
- **The read/write API layer, the outcome constant and the two pure helpers are a deliberate near-duplicate of `apps/web`'s equivalents, not a shared package.** Both talk to the exact same generic `/api/tours/*` endpoints, but the piece that would most benefit from sharing — the controller hook — is inherently tied to each app's own router (Next.js vs TanStack Router) and can't be lifted without a routing abstraction neither app needs yet. This matches this codebase's existing convention for the same situation (see `paymentRedirect.ts`'s own rationale note) — lift the small shared pieces into `packages/hooks`/`packages/utils` the next time a third consumer or a real touch-point makes the duplication worth resolving, rather than doing it opportunistically here.
