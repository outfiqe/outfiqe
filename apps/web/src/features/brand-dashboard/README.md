# Brand dashboard

## Purpose

The signed-in brand owner's workspace: an at-a-glance overview, plus manage the brand profile, list/create/edit/delete products, manage stock, review the creator tags on the brand's products, and view orders containing the brand's items. Six pages — `/overview`, `/profile`, `/products`, `/tag-reviews`, `/manage-orders`, `/wallet` — one per concern, each its own `DashboardSidebar` nav item, sharing the same sidebar layout via the `(dashboard)` route group. `/overview` is the post-login landing (see `features/auth/utils/getDefaultRoute.ts`); `/manage-orders` (not `/orders`) since the top-level `/orders` route is already the buyer's own purchase-history page.

## Structure

- `components/BrandOverview.tsx` — the `/overview` landing. Three bands: a `StatCard` KPI row (revenue last-30-days with a delta / lifetime, available & pending payout, product count, low-stock count, unfulfilled-item count), an `<ChartCard>`+`<TrendChart>` area chart of revenue per day over 30 days, and the five most recent fulfilment groups via `BrandShipmentRow` (with a "View all" link to `/manage-orders`). Each KPI card passes a `hint` string (the `KPI_HINT` map) into `StatCard`, so a brand owner can hover/focus the info marker to read exactly how that figure is calculated — gross vs. net, which order states count, why out-of-stock isn't "low stock", etc. `api/brandOverviewApi.ts`/`brandOverviewSchemas.ts` (reusing `brandShipmentSummarySchema`) and `hooks/useBrandOverview.ts` mirror the other API/hook pairs; the page is one `GET /brands/me/overview` call.
- `components/BrandProfileView.tsx` — the profile page: banner/avatar/contact info and its edit modal, plus `BrandTagPolicyCard` below it.
- `components/BrandTagPolicyCard.tsx` — inline (no modal) controls for who can tag the brand's products: a `Select` for the base rule (`tagReviewPolicy`, 3 options from `tagReview.constants.ts`, each with a helper line) and a `Switch` for `autoApproveVerifiedBuyers`, saved together through `useUpdateBrandProfile` → `PATCH /brands/me`. Tracks its own "saved" baseline so Save re-disables after a successful write. `useUpdateBrandProfile` doesn't touch any React Query cache (there is none for this page — `/profile` is Server Component-rendered, see below) but does call `router.refresh()` on success, so a later revisit of `/profile` can't fall back to a stale, pre-edit cached render — see the rationale entry below for the bug this closes.
- `components/TagReviewsSection.tsx` — the `/tag-reviews` page. `Tabs` for Waiting / Approved / Declined (`useTagReviewQueue` per status, keyset-paginated), `useTagReviewPendingCount` drives the header sentence and the "Waiting (N)" tab label. Renders `TagReviewCard` per item; owns the `RejectTagModal` state and the approve/reject toasts.
- `components/TagReviewCard.tsx` — one queue row: look thumbnail (links to that look on the creator's profile), creator, tagged product + size, relative submitted time, a "Bought this on Outfiqe" / "Trusted creator" badge when the API flags it, and the actions — Approve / Approve &amp; trust / Decline for a waiting tag, "Remove tag" for a live one, and the brand's own note / approval-source line for a resolved one.
- `components/RejectTagModal.tsx` — reason `Select` (`TAG_REJECTION_REASON_OPTIONS`) + optional note, note required for `OTHER` (re-validates `rejectTagInputSchema` client-side before calling). Copy shifts between "decline" (pending) and "remove" (live).
- `tagReview.constants.ts` — the queue tab list, the brand-authored rejection-reason option labels, and the base-rule option list + labels.
- `api/tagReviewApi.ts` / `tagReviewSchemas.ts` — `GET /tag-reviews` (queue, `?status=`), `GET /tag-reviews/pending-count`, `POST /tag-reviews/:id/approve` (`{ trustCreator }`), `POST /tag-reviews/:id/reject` (`{ reason, note? }`).
- `hooks/useTagReviewQueue.ts` (infinite, per status), `useTagReviewPendingCount.ts` (brand-owner-gated `useQuery`), `useReviewTagActions.ts` (approve + reject mutations; both invalidate every queue key, the pending-count, and `explore-feed`).
- `components/ProductsSection.tsx` / `ProductModal.tsx` / `EditProductModal.tsx` + `EditProductForm.tsx` / `SizeStockFields.tsx` / `StockModal.tsx` / `DiscountModal.tsx` / `ProductActionsMenu.tsx` — the products page: listing, the "Add a product" form, the edit form (same fields, pre-filled), the restock modal, the sale-price editor, and the per-card 3-dot menu (Edit / Manage stock / Sale price / Delete).
- `components/ProductModal.constants.ts` — `PRODUCT_PHOTO_ASPECT` (1:1, matching the square product-grid thumbnails), `PRODUCT_CROP_BOX_STYLE`, `DEFAULT_IMAGE_MIME_TYPE`, `THRIFT_CONDITION_OPTIONS` — the product-specific parameters fed into the shared photo-crop pieces below and into `ThriftListingFields`.
- `components/ThriftListingFields.tsx` — the "This is a secondhand / thrifted piece" checkbox plus the condition rating/notes it reveals, shared verbatim by both product forms as plain value/`onChange` props (matching `SizeStockFields`' own shape) rather than a react-hook-form-generic component, since the two forms carry different Zod-inferred input types.
- Both product forms render their photo side through `@/shared/components/MediaFormShell` + `PhotoCropPane` + `@/shared/hooks/usePendingPhotos` — the same fixed-photo-pane / scrollable-fields / sticky-footer chrome and single-active-photo crop editor as `creator-dashboard`'s `PostModal`. See that feature's README and the rationale below for what's shared vs. product-specific.
- `components/OrdersSection.tsx` — the `/manage-orders` page: a paginated list of this brand's **fulfilment groups** (one shipment per order), each row (`BrandShipmentRow`) linking to `/manage-orders/[groupId]`. Backed by `useBrandShipments` → `brandFulfilmentApi.list` → `GET /orders/brand/fulfilment-groups`.
- `components/BrandShipmentDetail.tsx` + `MarkShipmentShippedModal.tsx` + `RequestShipmentCancellationModal.tsx` + `shipmentStatus.ts` — the `/manage-orders/[groupId]` shipment detail. Shows the buyer ship-to contact (name/phone/address), this brand's items with price breakdown, this brand's payout for the shipment, and the next fulfilment action: **Mark packed** / **Mark shipped** (carrier + tracking modal) / **Mark delivered** (`useAdvanceShipment` → `PATCH /orders/brand/fulfilment-groups/:groupId`), plus **Request cancellation** (`useRequestShipmentCancellation` → `POST …/request-cancellation`; the actual cancel + refund is an admin action). `shipmentStatus.ts` owns the status labels/tones and the `nextShipmentStatus` transition map. `api/brandFulfilmentApi.ts` / `brandFulfilmentSchemas.ts` and the `useBrandShipment(s)` / `useAdvanceShipment` / `useRequestShipmentCancellation` hooks mirror the other API/hook pairs.
- `components/WalletSummaryTiles.tsx` — the settlement-ledger breakdown (total sales, pending,
  available, withdrawn) shown at the top of `/wallet`, mirroring
  `creator-dashboard/EarningsSummaryTiles.tsx`. The wallet page's bank-account management and
  withdraw request flow itself isn't owned by this feature — see below.
- `api/brandDashboardApi.ts`, `brandProductsApi.ts`, `brandFulfilmentApi.ts`, `brandPayoutApi.ts` (+
  matching `*Schemas.ts`) — one API/schema pair per sub-area.
- `hooks/` — one hook per mutation/query (`useCreateProduct`, `useUpdateProduct`, `useAdjustStock`, `useDeleteProduct`, `useBrandProducts`, `useBrandShipments`/`useBrandShipment`, `useAdvanceShipment`, `useRequestShipmentCancellation`, `useUpdateBrandProfile`, `useBrandPayoutSummary`).
- `schemas/productForm.schema.ts` — `productFormSchema` (create) and `buildEditProductFormSchema` (edit — a factory, not a static schema; see below).

## Funnel

**User-facing**: sign in as a brand owner → `/profile` shows the brand's profile card. `/products` (its own sidebar item) shows the product grid. "Add product" opens a modal (photos, name, price, type, sizes + per-size stock, categories, and — if checked as thrift — a required condition rating and note) → submit for review; a thrift listing gets extra admin scrutiny on that same required condition disclosure (see `apps/api/src/modules/products/README.md`'s "Thrift listings" section). Each product card has a 3-dot menu: "Edit" opens the same fields pre-filled, changes apply immediately even on a live product; "Manage stock" opens a modal listing sizes with a running count and an "adjust by" input per size; "Delete" asks for confirmation, then removes it.

**Technical**: `ProductModal` → `useCreateProduct` → `POST /products`. `EditProductForm` → `useUpdateProduct` → `PATCH /products/:id`. `StockModal` → `useAdjustStock` → `PATCH /products/:id/stock`. `DiscountModal` → `useSetProductDiscount`/`useUpdateProductDiscount`/`useRemoveProductDiscount` → `POST`/`PATCH`/`DELETE /products/:id/discount` (see `apps/api/src/modules/products/README.md`'s "Brand-funded discounts" section). `ProductActionsMenu`'s Delete → confirmation `Modal` in `ProductsSection` → `useDeleteProduct` → `DELETE /products/:id` (soft delete — see `apps/api/src/modules/products/README.md`). The size picker (`SizeStockFields`, shared by create and edit) is fed by `apps/web/src/features/products/hooks/useSizeOptions`, reading the admin-owned catalog (`apps/api/src/modules/size-options`) filtered to whichever product type is currently selected. `app/(dashboard)/products/page.tsx` follows the same `requireDashboardSession` + brand-only `redirect` guard as `app/(dashboard)/manage-orders/page.tsx`.

Tag reviews: a creator tags one of the brand's products → the tag is `PENDING` (unless a policy auto-approved it) and the brand gets a `PRODUCT_TAG_SUBMITTED` notification deep-linking to `/tag-reviews`. `TagReviewsSection` → `useTagReviewQueue` → `GET /tag-reviews?status=` (each tab its own key + cursor). Approve → `POST /tag-reviews/:id/approve` (`{ trustCreator }` from which button was pressed) → the tag goes live on the creator's look; Decline / Remove → `RejectTagModal` → `POST /tag-reviews/:id/reject` (`{ reason, note? }`). The base-rule + verified-buyer toggle on `/profile` (`BrandTagPolicyCard`) write through the same `PATCH /brands/me` as the rest of the profile. See `apps/api/src/modules/tag-reviews/README.md`.

Photos: both forms hold their photos in `usePendingPhotos` (create seeds it empty; edit seeds it from `product.imageUrls`) and only resolve real URLs at submit time, via the shared `resolvePendingPhotoAssets` — it crops whichever entries have a local `File`, uploads them through `POST /uploads/pipeline` (so each also gets an `ImageProcessingAsset`), and passes already-hosted entries (edit's existing photos) straight through with a `null` asset id. Both forms then send the aligned `imageUrls` + `imageAssetIds` lists alongside the rest of the field values in the same `create`/`update` mutation call.

## Non-obvious rationale

**Three confirmed Products-page bugs, found and fixed in a QA/audit pass (2026-09-14).**

- **`ProductsSection` had no error state at all.** `useBrandProducts` (`useInfiniteQuery`) already exposes `isError`/`error`/`refetch`, but the component only branched on `isPending` and an empty products array — a failed fetch rendered the exact same "Nothing listed yet — add your first piece" empty state as a brand with zero products, with no indication anything had gone wrong and no way to retry short of a full page reload. Proved with a component test asserting the empty-state copy showed instead of an error on a mocked `isError: true` result (`ProductsSection.test.tsx`). Fixed by adding the same retry-capable error block `TagReviewsSection` already uses (`getErrorMessage(error)` + a "Try again" button calling `refetch()`), and gating the empty state on `!isError` so the two states can't render on top of each other.
- **`EditProductForm` didn't reset `sizes` when the type changed, unlike the create form.** `ProductModal`'s type `<select>` explicitly does `form.setValue("sizes", [])` in its own `onChange`; `EditProductForm`'s type `<select>` was missing that override entirely. Picking sizes for one type, then changing the type again before submitting, left the first type's `sizeOptionId`s sitting in the form's `sizes` array — invisible in the UI (`SizeStockFields` only renders checkboxes for the _current_ type's options) but still present in the submitted payload, and in the worst case (switching to a third type without ever visibly checking a box) it satisfied the "at least one size" validation with entirely stale data and reached the API with sizes that don't belong to the new type at all. Proved with a component test that changes type A → B (checks a B size) → C and asserts the submit payload; before the fix it called `useUpdateProduct` with the stale B-type `sizeOptionId` (`EditProductForm.test.tsx`). Fixed by adding the same `form.setValue("sizes", [])` reset the create form already had, on every type change.
- **`DiscountModal` could get stuck once its cached `activeDiscount` went stale.** The create-vs-edit branch is decided purely from `product.activeDiscount` in the React Query cache. If that discount had actually expired, been removed elsewhere, or otherwise no longer existed by the time of submit, the server's `updateDiscount`/`removeDiscount` correctly rejects with `DISCOUNT_NOT_FOUND` — but the modal just toasted the error and left `existing` (and therefore its whole edit-mode UI) unchanged, so retrying failed the same way every time, and reopening the modal didn't help either since nothing had invalidated the stale `["brand-products"]` cache entry. Proved with a component test rejecting the update call with a `DISCOUNT_NOT_FOUND` `ApiClientError` and asserting the create call never followed (`DiscountModal.test.tsx`). Fixed by having `submit()` retry as `setDiscount` (create) when `updateDiscount` comes back `DISCOUNT_NOT_FOUND`, and having `remove()` treat the same code as "already achieved" — invalidate `["brand-products"]` and report success rather than surfacing an error for a discount that's already gone.

Also verified and ruled out in the same pass, each backed by a reproduction or evidence: all five product mutations (`useCreateProduct`/`useUpdateProduct`/`useAdjustStock`/`useSetProductDiscount`/`useUpdateProductDiscount`/`useRemoveProductDiscount`/`useDeleteProduct`) correctly invalidate `["brand-products"]` on success; `StockModal`'s "adjust by" can't drive stock negative (server-side atomic conditional `UPDATE ... WHERE stock >= qty` inside a `$transaction`, 409s cleanly, modal stays open and retryable); a multi-photo upload failure aborts the whole create/update before the mutation ever fires (`resolvePendingPhotoAssets` is awaited first, so a rejected upload never reaches `POST/PATCH /products`); a soft-deleted product's past `OrderItem`s still render correctly everywhere order history is shown, since every such read is a plain relation `include` with no `deletedAt` filter and `softDelete` never touches `name`/`imageUrl`. See `apps/api/src/modules/tag-reviews/README.md` for a fourth, more serious bug found in the same pass (a real concurrent-write race in tag approve/reject) and its fix.

**`/overview` "Revenue" is gross merchandise value, not payout.** The KPI and trend sum
`qty * unit_price` on the brand's order items where the order is paid (`PAID` or COD `DUE`) and
not cancelled — the same "real sale" filter `products` uses for card social proof. The brand's
actual settlement figures are the separate "available payout" / "pending payout" KPIs, sourced
from `brandPayoutService` (net of platform commission and gateway fees). Showing both on one
screen is intentional: gross sales and net payout answer different questions. See
`apps/api/src/modules/brand-overview/README.md`.

**Sizes are picked, not typed.** Neither form lets a brand type a size label — it fetches that product type's admin-defined size list and the brand checks off which ones apply, entering a stock count for each.

**Editing applies immediately, even to a live product — deliberately.** There's no re-review step. A brand can change name/price/photos/categories/type on an `APPROVED` product and it's live with the new values right away. This trades a small content-drift risk (a brand could swap in different photos post-approval without anyone re-checking) for not making a brand wait on an admin to fix a typo or update a price. Stock and delete already worked this way; edit now matches them for consistency — restocking, editing, and deleting are all "operational" actions a brand should self-serve, unlike creating a product in the first place, which still goes through review.

**Changing a product's type means re-picking its sizes, and it can fail.** `EditProductForm` only shows the size picker when the selected type differs from the product's original type (`buildEditProductFormSchema(originalType)` — a schema _factory_, not a static schema, because "sizes required" depends on that original value, which zod can't see on its own). Submitting a type change only sends `sizes` when `type !== originalType`; otherwise the size list submitted is `undefined` and the product's current sizes are left untouched entirely — they're not re-validated or re-fetched, since they're not part of what's being edited. If any of the sizes being replaced already has order history, the API rejects the whole edit with a 409 (surfaced via `FormBanner`) rather than silently dropping just the sizes that couldn't be removed — see `apps/api/src/modules/products/README.md` for why that's a hard DB-level constraint, not a validation choice.

**Deleting a live product is allowed too, same reasoning as edit.** The confirmation modal's copy changes for `APPROVED` products specifically, since that's the one case where the effect is immediately visible to shoppers, not just internal.

**The product form modals fully reuse `PostModal`'s crop pipeline, not just its chrome.** `usePendingPhotos`, `resolvePendingPhotoAssets`, `PendingPhotoThumbnailRail`/`PhotoCropPane`, and `MediaFormShell` moved to `@/shared` once this feature needed the exact same "pick photos, crop the active one, defer upload to submit" experience `creator-dashboard/PostModal.tsx` already had — same fixed-width left pane / scrollable right pane / sticky footer, same single-active-photo crop editor, same deferred-upload-at-submit flow. Only the parameters differ: products use a 1:1 `PRODUCT_PHOTO_ASPECT` (matching the square product-grid thumbnails) instead of Post's 4:5 portrait, and photos stay optional (no `.min()` on `imageUrls` in `productFormSchema`, unlike Post's mandatory one).

**Existing product photos aren't re-cropped in edit mode, same rationale as `EditPostForm`.** `usePendingPhotos` accepts `product.imageUrls` as seed entries with `file: null`. `PhotoCropPane` renders those as a plain static preview (still remove/add-able) instead of an interactive `CropSurface`, because `getCroppedImageFile` loads images with `crossOrigin="anonymous"` — re-cropping an already-hosted image would depend on the uploads host sending permissive CORS headers, which isn't guaranteed. `resolvePendingPhotoAssets` passes those `file: null` entries straight through untouched and only crops+uploads newly added ones, so this costs nothing beyond what edit already needed.

**`DiscountModal` decides create vs. edit itself, from `product.activeDiscount`, rather than the caller passing a mode.** No `activeDiscount` → the form starts blank (defaulting to 20% off, matching the API's `MAX_BRAND_DISCOUNT_BASIS_POINTS` guidance of staying well under the 70% ceiling) and submits via `useSetProductDiscount` (`POST`), which the API always treats as creating a fresh discount and deactivating any prior one. An existing `activeDiscount` → the form is pre-filled and submits via `useUpdateProductDiscount` (`PATCH`), editing that same row in place — its id, and its audit history, stay the same rather than starting a new discount for what's really the same ongoing sale. `startsAt` is only ever sent on create (`POST` requires it; `PATCH` merges onto the existing row's), so editing an already-live sale can't accidentally reset when it started.

**`/wallet` (`app/(dashboard)/wallet/page.tsx`) composes this feature's `WalletSummaryTiles` with the owner-agnostic `bank-accounts` and `withdraw` features, rather than this feature owning bank accounts/withdraw itself.** Those two concerns are identical in shape for a creator and a brand (same request/response contracts, same review flow), so they're built once, parameterized by `ownerType`, and reused from `/withdraw` (creator) and `/wallet` (brand) alike — see `bank-accounts/README.md` and `withdraw/README.md` for the full reasoning. This feature only supplies the brand-specific ledger summary tiles, which have no creator equivalent worth sharing (the creator side already has its own `EarningsSummaryTiles`, with different fields).

**Tagging policy is one `Select` + one `Switch`, not a radio group.** The PRD sketched a 3-way radio, but `@outfiqe/design-system` has no radio primitive and building one for a single settings control wasn't worth it — a native `Select` with the same per-option helper text below it reads fine for three mutually-exclusive choices. `BrandTagPolicyCard` is inline (no modal) because a brand adjusts these rarely and two controls don't warrant the extra open/save round-trip the profile modal has.

**The queue's "Bought this on Outfiqe" / "Trusted creator" badges are read-only signals.** They come from the API (`isVerifiedBuyer` / `isTrustedCreator` on the queue item), never gate an action, and a pending tag carrying "Trusted creator" just means the brand is on "Review every tag" — see `apps/api/src/modules/tag-reviews/README.md`.

**No bulk approve, and no sidebar count badge — deliberate scope cuts.** "Approve & trust" already collapses the common repeat case (that creator's future tags skip the queue), so per-row actions cover v1; bulk select is a fast-follow if queue volume warrants it. The pending count shows in the page header and the "Waiting (N)" tab rather than on the `DashboardSidebar` nav item, since a nav badge needs a `@outfiqe/components` `SidebarNavItem` change that also touches the admin sidebar.

**A saved profile/tag-policy edit could silently revert if you navigated away from `/profile` and back within 30 seconds.** `/profile` is a Server Component page (`getBrandProfileServer` runs on the server; `BrandProfileView` receives the result as a plain prop, not a React Query read), and `next.config.ts` explicitly sets `experimental.staleTimes.dynamic` to 30 seconds (Next's own default is `0`, i.e. uncached, for exactly this route shape). `useUpdateBrandProfile`'s mutation only updated `BrandProfileView`/`BrandTagPolicyCard`'s own local "saved" state on success — it never called `router.refresh()`. That local state made the just-saved values look correct on the page you were already on, but it did nothing to the Next.js Client Router Cache: a soft navigation away and back inside that 30-second window re-mounted the page from the **stale, pre-edit** cached RSC payload, so contact info, avatar/banner, tag policy, and the auto-approve-verified-buyers toggle would all revert to their old values until the cache aged out or a hard reload forced a fresh fetch. Reproduced as a real test (`BrandTagPolicyCard.integration.test.tsx`'s "refreshes the router on a successful save..." and `BrandProfileView.integration.test.tsx`'s "reflects a saved edit immediately without a manual reload, and refreshes the router") — mocking `next/navigation`'s `useRouter` and asserting `refresh` fires after a successful `PATCH /brands/me` — both failed against the old hook (the mock's `refresh` was never called; confirmed by reverting the fix and re-running). Fixed by having `useUpdateBrandProfile` call `router.refresh()` in its own `onSuccess`, the exact pattern `creator-dashboard`'s `useApplyAsCreator` already uses for the same class of problem (a client mutation invalidating data a Server Component rendered): per Next's docs this clears the Client Cache for the current route without losing unrelated client-side state (the modal closing, the toast, the already-updated local fields), so the fix is invisible on the happy path and only changes what a later revisit sees. A blind concurrent-edit overwrite (e.g. an admin editing the same brand elsewhere while the modal is open) is a separate, considered tradeoff, not a bug: this endpoint has no optimistic-concurrency check, same as `EditOwnProfileCard`'s own profile edit and every other simple profile-style form in this codebase — last write wins.

**The profile edit modal's Contact name/Phone/Instagram fields had no `htmlFor`/`id` pairing.** Every other label/input pair on this exact page — `BrandTagPolicyCard`'s policy `Select` and the creator equivalent `EditOwnProfileCard`'s name/handle inputs — associates the label with its control; these three didn't, so a screen reader landing on the input announced nothing about what it was for. Reproduced as a real test (`BrandProfileView.integration.test.tsx`'s "associates every edit field with its label", using `getByLabelText` the same way `EditOwnProfileCard.integration.test.tsx` already does) — it failed with "found no label" against the old markup. Fixed by adding matching `htmlFor`/`id` pairs (`brand-profile-edit-contact-name`/`-phone`/`-instagram`), same convention as the rest of the page.
