# creator-dashboard

## Purpose

Everything a creator manages about their own account, from their own top-level routes (`/overview`, `/profile`, `/share`, `/earnings`, `/withdraw`, `/progress`, `/badges`, `/challenges`, sharing the same sidebar layout via the `(dashboard)` route group): the at-a-glance dashboard, profile edits, applying to become a creator, posting/editing looks, share links, and earnings. Post viewing/browsing lives in `creator-profile`, not here — this feature owns the mutation side of a creator's posts.

## Structure

- `components/CreatorOverview.tsx` — the `/overview` landing (also the post-login destination for non-admins, see `features/auth/utils/getDefaultRoute.ts`). Three bands: a `StatCard` KPI row (earnings / available / pending / followers / looks / likes), an `<ChartCard>`+`<TrendChart>` area chart of commission earnings per day over 30 days, and the five most recent commissions rendered with `EarningsLedgerRow` (with a "View all" link to `/earnings`). Same `CreatorStatusGate` treatment as `EarningsSection` for a not-yet-approved creator. `api/creatorOverviewApi.ts`/`creatorOverviewSchemas.ts` (reusing `creatorCommissionSchema` for the recent list) and `hooks/useCreatorOverview.ts` mirror the earnings equivalents' shape; the whole page is one `GET /creators/me/overview` call so it has one loading state.
- `components/PostModal.tsx` — create-a-post modal: multi-photo crop/upload, caption, layout
  choice, product tagging. Takes an optional `initialPhotoFile`, imported into the pending-photos
  list the moment the modal opens — how `app/(dashboard)/share-target` pre-loads a photo shared in
  from another app; see `apps/web/src/features/pwa/README.md`'s "Sharing into the app".
- `components/LayoutPicker.tsx` — the Portrait/Square/Tall picker (`PostLayout`, `@outfiqe/utils`)
  shown only in `PostModal`, following the same raw-pill-button local pattern as
  `product-detail/components/SizeSelector.tsx` rather than a new design-system primitive. Disabled
  once a photo has been staged — see rationale below.
- `components/EditPostModal.tsx` — edit-a-post modal wrapper: fetches the look, shows a layout-matched skeleton while loading, then mounts `EditPostForm` once data is ready.
- `components/EditPostForm.tsx` — the actual edit form (photos, caption, tags). Mounted fresh (`key={lookId}`) per post being edited so its local photo/form state always seeds correctly from real data — no effect-driven resync needed. Builds a `reviewByProductId` map from the fetched detail and passes it to `ProductTagPicker`; when any tag isn't `APPROVED` it opens the picker on mount and shows a one-line "your post is live, hidden tags follow brand approval" explainer.
- `components/ProductTagPicker.tsx` — shared tag-picker UI used by both `PostModal` and `EditPostForm`. In the edit case it also renders per-tag brand-review state (`reviewByProductId`, optional — `PostModal` never passes it): an "In review" / "Declined" status chip, and for a declined tag the brand's reason (`utils/tagReviewLabels.ts`) plus its free-text note and a "Request again" button. "Request again" just calls the form's submit (`onReRequestTag`) — the API auto-moves a surviving `REJECTED` tag back to `PENDING` on any update; the button is hidden and a "used all your re-requests" line shown once `canReRequest` is false (the server's cap of `MAX_TAG_RE_REQUESTS`).
- `utils/tagReviewLabels.ts` — creator-facing copy for tag-review state: the status chip labels and the `TagRejectionReason` → plain-sentence map.
- `components/ApplyAsCreatorButton.tsx`, `EarningsSection.tsx`, `ShareSection.tsx` — the other dashboard sections.
- `components/ProgressSection.tsx`, `LevelProgressCard.tsx`, `XpTransactionRow.tsx`, `XpMultiplierBanner.tsx` — the gamification level/XP-bar card + recent-activity list (`/progress`). Unlike `EarningsSection`/`ShareSection`, this one is **not** gated by `CreatorStatusGate` — every user earns and can view their own XP, not just approved creators, so it renders unconditionally for any non-brand account. `api/xpApi.ts`/`xpSchemas.ts`, `hooks/useXpProgress.ts`/`useMyXpTransactions.ts`/`useActiveXpMultiplier.ts` follow the exact same shape as the earnings equivalents. `XpMultiplierBanner` renders nothing when no `XpMultiplier` window is currently live server-side (`GET /xp/multiplier/active`); `useActiveXpMultiplier` polls it every 60s so the banner appears/disappears close to the actual window boundary without needing a socket event for something this low-stakes.
- `components/BadgeCollectionSection.tsx`, `AchievementBadgeCard.tsx`, `AchievementBadgeIcon.tsx`, `BadgeFilterTabs.tsx` — the badge collectible-library UI (`/badges`), same not-creator-gated reasoning as `ProgressSection`. Named `AchievementBadge*`, not `Badge*` — `@outfiqe/design-system` already exports a generic status-pill `Badge` component, which `AchievementBadgeCard` itself imports and reuses for the rarity tag, so a same-named component here would shadow that import on every page needing both. `api/badgeApi.ts`/`badgeSchemas.ts`, `hooks/useBadgeCollection.ts`/`useUpdateBadgeDisplay.ts`/`useUpdateFeaturedBadges.ts`/`useUpdateBadgeTitle.ts` mirror the earnings/progress equivalents' shape. `AchievementBadgeIcon` resolves which of the shared `animate-badge-*` classes (defined in `packages/design-system/tokens.css`, see that package's README) to apply from `designConfig.animation` if the admin set one, falling back to a fixed `RARITY_DEFAULT_ANIMATION` (common/uncommon get none, rising through glow → shimmer → pulse → radiant at the top rarity) when they didn't — never animated while locked, since a grayscale locked badge animating would just look broken, not enticing. Also imported cross-feature by `../creator-leaderboard`'s `CreatorCompetitionBanner` (`isLocked={false}`, previewing a competition's trophy badge) — the icon-rendering logic was written generically enough from the start that a second, unrelated feature could reuse it without any change here. `AchievementBadgeCard` shows a "Sponsored by {brand}" credit (linking to `/brand/:id`) whenever `entry.sponsorBrand` is present — the same field on both a collected and a locked entry, so a brand's credit shows up before someone's even earned the badge, not just after.
- `components/ChallengesSection.tsx`, `ChallengeCard.tsx` — time-boxed goals (`/challenges`), same not-creator-gated reasoning as `ProgressSection`/`BadgeCollectionSection`. Reuses `AchievementBadgeIcon` for the awarded badge's preview rather than a separate icon component, since a challenge's reward literally is a `Badge` — there's no separate visual language to invent. `api/challengeApi.ts`/`challengeSchemas.ts`, `hooks/useChallenges.ts` mirror the badge collection's shape (list read, optional per-viewer progress/completion folded server-side).
- `utils/badgeLabels.ts` — `RARITY_LABEL`/`METRIC_LABEL`, shared between `AchievementBadgeCard` and `ChallengeCard` since both render the same rarity tag and the same per-condition progress rows. `METRIC_LABEL` includes the seven `*_rank` metrics alongside the counter metrics; `isRankMetric`/`RANK_METRICS` let `AchievementBadgeCard` render those conditions as plain "currently #N · need top M" text instead of a `ProgressBar` — a rank shrinks toward its target, the opposite direction a `value`/`max` progress bar assumes, so reusing the bar for one would render a materially misleading fill.
- `components/CreatorStatusGate.tsx` — the shared "not an approved creator yet" state (application under review / become-a-creator pitch + `ApplyAsCreatorButton`), rendered by `EarningsSection`, `ShareSection`, and `app/(dashboard)/profile/page.tsx` whenever `creatorStatus !== APPROVED`.
- `components/GamificationSocketListener.tsx`, `hooks/useGamificationSocket.ts`, `socketEvents.ts` — the real-time achievement-unlock/level-up toast. Lives here alongside `ProgressSection`/`BadgeCollectionSection` since it's the same XP/badge domain, but — unlike everything else in this feature — it isn't rendered from a dashboard page. It's mounted once, globally, from `app/providers.tsx` (any authenticated user can level up or unlock an achievement from anywhere in the app, not just while looking at `/progress`), imported by its direct component path rather than through this feature's `index.ts` barrel — see rationale below.
- `api/creatorLooksApi.ts`, `creatorLooksSchemas.ts` — look create/edit/delete requests + response validation.
- `api/creatorDashboardApi.ts`, `creatorDashboardSchemas.ts` — profile read/update, including `handle`/`heightCm`/`showHeight`/`hideFromLeaderboards`, all edited from `creator-profile`'s edit-profile modal, not from this feature. `handleFieldSchema` itself now lives in `features/users/api/userProfileSchemas.ts` (imported from there) since a second, non-creator profile-edit surface needs the same handle validation — see that feature's README.
- `hooks/useCreateLook.ts`, `useUpdateLook.ts`, `useDeleteLook.ts`, `useLookDetail.ts` — look mutations and the on-demand single-look fetch used to prefill the edit modal.
- `hooks/useUpdateCreatorProfile.ts`, `useTaggableProducts.ts` — profile update and product search for tagging. `PostModal`'s local photo/crop state (`usePendingPhotos`) lives in `@/shared/hooks` — see below (`EditPostForm` manages its own photo state separately, unaffected). The debounced live username-availability check backing the edit modal's username field (`idle | checking | available | taken | invalid`) used to live here as `useHandleAvailability.ts`; it moved to `features/users/hooks/useHandleAvailability.ts` once a second, non-creator profile-edit surface needed the exact same check — `creator-profile`'s edit modal now imports it from there.
- `schemas/lookForm.schema.ts` — `lookFormSchema` (the wire shape: `imageUrls`/`imageAssetIds`/`caption`/`layout`/`taggedProducts`, used by the create request) and `editLookFormSchema` (the `EditPostForm` RHF form itself, which only tracks caption/tags — photos are separate component state, merged in at submit time; `layout` is deliberately absent here, see rationale below).

## Funnel

**User-facing:** a creator opens their own profile (`creator-profile`), taps the floating add-post button to post a new look, or opens the 3-dot menu on one of their existing posts to edit its photos/caption/tags or delete it.

**Technical:** `creator-profile`'s `CreatorProfile`/`CreatorPostThumbnail` render `PostModal`/`EditPostModal` from this feature (cross-feature import, same pattern as `CreatorProfile` already using `useUpdateCreatorProfile` and `explore`'s `AddPostButton`/`PostDetailModal`). `EditPostModal` fetches the look via `useLookDetail` → `creatorLooksApi.getOwn` → `GET /creator-looks/:lookId` for per-tag `sizeWorn` and brand-review state (`reviewStatus`, `rejectionReason`, `rejectionNote`, `canReRequest`) — none of which the public feed-shaped post data carries (pending/declined tags are filtered out of every public read). A `PRODUCT_TAG_REJECTED` / `PRODUCT_TAG_REVOKED` notification deep-links to `/creator/<handle>?edit=<lookId>`, which `creator-profile` reads to open this modal straight onto the declined tag. `EditPostForm` tracks existing image URLs and newly-added local photos separately; on submit it crops the new photos and uploads them through `POST /uploads/pipeline`, then sends the full `imageUrls` list (surviving existing + newly uploaded, in that order) plus an aligned `imageAssetIds` list (`null` for every surviving existing photo, the pipeline asset id for each new one) to `PATCH /creator-looks/:lookId` — that endpoint replaces the look's whole image set. On success, mutations invalidate `["creator-looks"]`, `["explore-feed"]`, and `["saved-posts"]` so the profile grid, explore feed, and saved view all pick up the change.

`useGamificationSocket` acquires the shared ref-counted socket connection (`@/shared/lib/socketClient`, the same singleton `explore`'s `useExploreFeedSocket` uses) only while `useAuth().isAuthenticated` is true, listens for `achievement:unlocked`/`level:up`, and renders each via `toast.success` (`@outfiqe/design-system`). The connection is released on logout/unmount so a signed-out visitor never holds an idle socket open for events they can't receive (`userRoom`-scoped events require auth server-side). `formatAchievementToast` (exported, unit-tested) appends `(sponsored by {brand})` to the toast text when the unlocked badge's `sponsorBrandName` is present — a plain string, not a logo/link, since the toast itself is rendered as flat text with no image slot.

## Non-obvious rationale

- **`EarningsSection` now checks `isError` from both `useEarningsSummary` and `useMyEarnings`, not just `isPending`.** An audit found it previously rendered the KPI tiles as all-zero (`summary?.[key] ?? 0`) and the ledger as the "No earnings yet" empty state whenever either request failed — React Query's `isPending` flips to `false` on a settled error the same as on success, so a failed fetch and a genuinely empty account were visually indistinguishable, silently telling a creator with real (temporarily unreachable) earnings that they had none. Fixed to match the exact pattern `WithdrawSection`/`WithdrawPolicyPanel` already use: `EarningsSummaryTiles` takes an `isError` prop and renders a `FormBanner` instead of the tiles when set, and `EarningsSection` renders a `FormBanner` above the ledger instead of the skeleton/empty-state/list when `useMyEarnings` errors. Covered by `EarningsSection.test.tsx`/`EarningsSummaryTiles.test.tsx`.
- **`/overview` is the post-login landing for every non-admin (creators, brands, shoppers), replacing `/profile`.** `getDefaultRouteForUser` returns `/overview`; the `(dashboard)/overview/page.tsx` route redirects `BRAND_OWNER` to `/profile` for now — the brand variant of the Overview is a later change. A shopper who isn't an approved creator lands on `/overview` and sees `CreatorStatusGate` (the become-a-creator pitch), which is a reasonable first screen for that account type; revisit if a dedicated shopper landing is ever wanted.
- **`ChallengesSection` lives at `/challenges`, gated by the same `requireDashboardSession` + brand-owner redirect as `/badges` — not a genuinely logged-out-visible marketing page.** The backend's `GET /challenges` is `optionalAuth` (it can serve an anonymous request), but nothing here builds a public, unauthenticated surface for it — that's a real, separate product decision (a marketing/landing page, SEO, its own layout) this feature doesn't make on its own. Being logged-in-gated here matches every other gamification page in this feature and is a straightforward call, not a silent scope cut; a public page can be added later against the same already-optional-auth endpoint without any backend change.
- **`ProgressSection`, `BadgeCollectionSection`, and `ChallengesSection` had the identical `isError`-blindness bug `EarningsSection` above already had, in three more places.** `useXpProgress` failing rendered `LevelProgressCard` as a fabricated "Level 1, Newcomer, 0 XP" card — not just an empty state, actively wrong data, since a creator's real level could be much higher. `useMyXpTransactions`, `useBadgeCollection`, and `useChallenges` failing each rendered their own genuinely-empty-state copy ("No XP yet", "No badges match this filter yet", "No challenges are running right now") indistinguishably from a real fetch failure. Fixed the same way as `EarningsSection`: each component now checks `isError` before falling through to the empty-state branch and renders a `FormBanner`-style retry banner instead. `LevelProgressCard` gained `isError`/`error`/`onRetry` props for this. Covered by `ProgressSection.test.tsx`, `BadgeCollectionSection.test.tsx`, `ChallengesSection.test.tsx`.
- **`useGamificationSocket` now dedupes a redelivered achievement-unlock or level-up event instead of double-toasting.** The Redis Streams consumer group backing every domain event in this codebase is at-least-once (`XAUTOCLAIM` can redeliver an unacked entry — see `creator-looks/README.md`'s "Real-time comment replies" for the same property), and this listener had no equivalent of the client-side dedup that module already relies on for exactly this reason. A redelivered `ACHIEVEMENT_UNLOCKED`/`LEVEL_UP` event would show the same toast twice. Fixed with a small bounded recent-keys list (`badge:<badgeId>` / `level:<levelNumber>` — both naturally stable per real event, since a badge unlocks once per user and a user reaches a given level once) that skips a toast whose key was already shown. Covered by `useGamificationSocket.test.ts`.
- **`badgeRepository.awardBadge`'s unlock-race and `updateFeatured`/`updateTitle`'s ownership/cap checks were audited and found already correct, not fixed.** The pre-unlock `alreadyOwned` read is only a fast-path optimization — the actual guarantee is `tx.userBadge.create`'s real DB unique constraint (`userId_badgeId`), caught via `isUniqueConstraintError` and turned into a clean "already awarded" result, the same pattern this codebase already uses for the XP floor check and tag-review approve/reject race. `updateFeaturedBadgesSchema` caps the array server-side at the same `MAX_FEATURED_BADGES` the frontend uses (`.max()` + a no-duplicates refine), and `updateFeatured`/`updateTitle` both verify every referenced badge is owned (and, for title, collected-and-title-eligible) before writing — no IDOR path to feature or title another user's badge.
- **`isDynamicallyActive` is read straight off the API response, never derived client-side.** `AchievementBadgeCard` shows its "not currently active" note only on the exact `=== false` case — `null` (not a dynamic badge, or not collected) must not trigger it, and plain `!isDynamicallyActive` would, since `!null` is `true` in JS. The API already folds the badge's own `isDynamic` flag into that field (`null` unless both collected and dynamic), so the component doesn't need to know about `isDynamic` at all — one field, one meaning, no derived state to keep in sync.

- **`RARITY_LABEL`/`METRIC_LABEL` moved out of `AchievementBadgeCard.tsx` into `utils/badgeLabels.ts`, and `total_views` was added to `METRIC_LABEL`, while relocating it for `ChallengeCard`'s reuse.** The map was missing `total_views` since before this feature had any achievement that used it — a progress row for that metric would have silently fallen back to the raw `"total_views"` string instead of "Total views." Caught while extracting the map for a second consumer, fixed in the same pass rather than carried forward into a second copy.
- **`xpSchemas.ts`'s hand-mirrored `XpActivityType` (and its `packages/types` source) was missing `ACHIEVEMENT_UNLOCKED`, found during chunk 13's polish pass, not by inspection.** `packages/types/src/xp/index.ts` was written in chunk 5, before the achievements engine (chunk 6) started writing `XpTransaction` rows with `activityType: "ACHIEVEMENT_UNLOCKED"` — the mirror was never updated to match. Since `xpTransactionSchema.activityType` is `z.enum(XpActivityType)`, any transaction page containing even one such row failed Zod validation entirely, throwing inside the query rather than rendering a wrong label — for any user who had ever unlocked an achievement or received a manually-awarded badge with an XP reward, `/progress`'s transaction history would error out completely, not just misrender one row. This is exactly the class of drift this codebase's own hand-mirrored-enum convention is fragile to (see the project's `packages/types` pattern notes) — worth double-checking the other hand-mirrored enums here (`BadgeCategory`, `BadgeRarity`, etc.) stay in sync whenever the Prisma schema's gamification enums change, since nothing currently catches this automatically.
- **Follow-up: still no component tests for `ProgressSection`/`BadgeCollectionSection` and most of their children, or for `useGamificationSocket`'s actual socket wiring.** This repo's testing convention expects React Testing Library coverage for components like these (rendered/interacted-with, not just typechecked); most of it shipped verified only via a live end-to-end pass (real login, real data, real toggle interactions for the former; a real connected Socket.IO session receiving a genuine server-published event for the latter) rather than isolated tests with mocked data — no test in this codebase currently mocks a Socket.IO client connection, matching the same gap `explore`'s `useExploreFeedSocket` already has. `AchievementBadgeCard.test.tsx` and `useGamificationSocket.test.ts` exist now, but narrowly — the former covers only the sponsor-credit link (not the toggle/feature button interactions or the progress-bar rendering), the latter covers only `formatAchievementToast`'s pure string output, not the hook's `socket.on`/`acquireSocketConnection` wiring itself. Worth circling back to add proper component specs for `LevelProgressCard`, the rest of `AchievementBadgeCard`'s interactions, and a shared Socket.IO client mock the two hooks could share.
- **`AchievementBadgeIcon.test.tsx` covers the animation-resolution logic (rarity defaults, an explicit override in either direction, the locked/no-animation case, the glow color custom property) via plain render-and-inspect-the-DOM assertions — no timers, no `getComputedStyle`.** The component's `prefers-reduced-motion` handling lives entirely in `packages/design-system/tokens.css`'s media query, not in this component's own logic, so there's nothing for a component test to usefully assert there; what the component itself is responsible for — which class name gets applied and what color the animation reads — is exactly what's tested. Verified once, live, that the actual keyframe animations render and are visually distinct per rarity in a real browser rather than assumed correct from the class names alone.
- **A shared photo is imported via `usePendingPhotos`'s `importFile(file: File)`, not by synthesizing
  a `FileList` for `handleFileSelect`.** A `DataTransfer` object can build a real `FileList` from a
  plain `File` — the standard trick for feeding a file into code written for an `<input type="file">`
  change event — but jsdom doesn't implement `DataTransfer` at all, which would have made
  `PostModal`'s new "open pre-loaded with a shared photo" behavior untestable outside a real browser.
  `handleFileSelect` now just extracts the `File` from the `FileList` and hands off to `importFile`,
  which does the actual HEIC-conversion-then-stage work either way — `PostModal` calls `importFile`
  directly with the file it already has, and picking a file through the normal input still goes
  through `handleFileSelect` exactly as before.
- **"Set as title" is one extra button on the same `AchievementBadgeCard` row as Feature and Show/Hide — shown only for a collected badge that is `isTitleEligible` and currently displayed.** The catalog's `isTitleEligible` flag (admin-set in `apps/admin`'s gamification feature) is what gates the control; the button's label and behaviour flip on `entry.isTitle` (`"Set as title"` → `PATCH /badges/title` with this id, `"Remove title"` → the same endpoint with `null`). It's hidden while the badge is hidden from the profile because the server clears any title the moment its badge is hidden (`badge.repository.ts#updateDisplay`), so offering it there would be a no-op. No drag, no separate panel — the title is a single-slot choice, so a per-card toggle is the whole interaction. The public profile (`creator-profile`) renders the equipped title as an accent pill next to the name plus the avatar ring; this feature only writes the flag.
- **Featuring badges is click-to-toggle, not drag-and-drop.** The PRD's spec 24 describes a drag-reorder UI for featured badges; `BadgeCollectionSection` ships a "Feature"/"Unfeature" button per collected card instead, with order determined by click sequence (append on feature, remove-and-close-the-gap on unfeature), capped at `MAX_FEATURED_BADGES`. A real drag-and-drop interaction needs a DnD library this repo doesn't currently depend on — introducing one is a bigger call than this chunk's scope, so it's flagged as a deliberate simplification rather than silently different from the spec. The backend (`PATCH /badges/featured`, a full-list replace) already supports a real drag-reorder UI without any API change if one gets built later — only this component would need to change.
- **`/creators/me` never gates on creator status** — it returns a profile (including `handle` and `creatorStatus`) for any authenticated user, since it also backs the "become a creator" pitch screens. `/creators/by-handle/:handle` (the public profile, fetched server-side and rendered inline once the creator is approved) _does_ gate on `isCreator`/`APPROVED`. `app/(dashboard)/profile/page.tsx` has to check `creatorStatus === APPROVED` itself before fetching/rendering the public profile — doing so unconditionally would 404 non-approved users against the gated endpoint. There's no `[handle]` route under `/profile` — the URL stays `/profile` for every state (gate screen or the rendered profile); the page just fetches `getCreatorProfileServerPublic(profile.handle)` and renders `CreatorProfile` directly instead of redirecting to a per-handle URL.
- **The not-yet-approved branch of `/profile` now renders `features/users`' `EditOwnProfileCard` above `CreatorStatusGate`, using the same `profile.name`/`handle`/`avatarUrl` this feature's own `getCreatorProfileServer` call already fetches** — no second request. Before this, a shopper or a pending/rejected applicant had no way to edit their display name, username, or avatar anywhere in the product; `PATCH /users/me` already accepted `name` (and, as of this pass, `handle`/`avatarUrl`/`avatarImageAssetId`) for every account regardless of creator status, the gap was purely that no screen exposed it. `EditOwnProfileCard` is deliberately not part of this feature — it has no creator-specific fields (`heightCm`, `showHeight`, `hideFromLeaderboards`) and needs to render for every account type, so it lives in `features/users` alongside the shared handle-change primitives. The username cooldown/uniqueness state (`User.handleChangedAt`) is shared with `PATCH /creators/me`, since both endpoints write the same column — a user who changes their handle here and is later approved as a creator doesn't get a second free change.
- There used to be a standalone "Posts" dashboard section (`/dashboard/posts`, its own sidebar nav item) that just listed a creator's own looks with no edit/delete. It was removed because the creator's profile already shows the same grid — keeping both was duplicated UI with no distinct purpose. Posting now happens from the profile's floating action button; editing/deleting happens from the 3-dot menu on each post thumbnail (`creator-profile/components/PostActionsMenu.tsx`).
- **`PostModal`'s two-pane crop layout is a shared component, not local markup.** `usePendingPhotos`/`resolvePendingPhotoAssets` (`@/shared/hooks/usePendingPhotos.ts`), `PendingPhotoThumbnailRail` and `PhotoCropPane` (`@/shared/components/`), and the outer `MediaFormShell` (fixed photo pane + scrollable fields + sticky footer) were pulled out of this feature once `brand-dashboard`'s product modals needed the same "pick photos, crop one at a time, defer upload to submit" experience — see that feature's README for how it reuses them for products (a domain with a square aspect and optional, already-hosted existing photos instead of a mandatory portrait one). `resolvePendingPhotoAssets` uploads the newly-cropped files through `POST /uploads/pipeline` and returns each photo's final URL plus its `ImageProcessingAsset` id (`null` for photos carried over from an edit), which both features send as parallel `imageUrls` / `imageAssetIds` arrays.
- **Existing photos aren't re-cropped in edit mode**, only added or removed. They were already cropped/stored at post time; `EditPostForm` shows them as plain removable thumbnails and only runs a new photo through `CropSurface` once, at add-time, before it's committed to the list — reusing `PostModal`'s crop pipeline (`cropBoxStyleForAspect`, `getCroppedImageFile`) without needing `usePendingPhotos`, since edit only ever stages one new photo at a time rather than managing a whole multi-photo crop session.
- **A post's layout (Portrait 4:5 default / Square 1:1 / Tall 9:16, `PostLayout` in `@outfiqe/utils`) is chosen once, at creation, and locked forever after.** `PostModal.constants.ts`'s old fixed `PHOTO_ASPECT`/`CROP_BOX_STYLE` became `cropBoxStyleForAspect(aspect)`, driven by whichever layout is selected in `LayoutPicker`; `MediaFormShell`/`PhotoCropPane`/`CropSurface` were already generic over aspect ratio, so no change was needed there. `LayoutPicker` disables itself the moment `pending.photos.length > 0` — `react-easy-crop`'s `onCropComplete` only recomputes the _currently active_ photo, so switching layout after other photos are already cropped would leave them stale at the old aspect with no way to force a re-crop short of removing and re-adding each one; locking the choice before the first photo lands avoids that inconsistency entirely rather than adding reset machinery for it. `EditPostForm` never lets the layout change either (`editLookFormSchema` has no `layout` field) — it reads the post's existing `layout` off `CreatorLookEditDetail` (a read-only field there) to crop any newly-added photo at the _same_ aspect the post was originally created with, instead of a hardcoded constant, so a Square or Tall post never picks up a stray 4:5 photo through the edit flow.
- **`app/providers.tsx` imports `GamificationSocketListener` by its direct file path, never through this feature's `index.ts` barrel.** The barrel also re-exports `getCreatorProfileServer` (`api/getCreatorProfileServer.ts`), which imports `"server-only"` — fine everywhere else this barrel is consumed (from Server Component pages), but `providers.tsx` is a Client Component mounted at the very root of the app, so pulling in the whole barrel there drags a server-only module into client bundling and hard-crashes the page (`'server-only' cannot be imported from a Client Component module`) — caught live rather than shipped, since it only surfaces once something in the barrel is actually consumed from a client-only entry point. Importing the component's own path sidesteps the barrel entirely; this is the standard Next.js App Router mitigation for a barrel that deliberately mixes server-only and client-safe exports, not a sign this barrel needs restructuring today.
- **`EditPostModal`/`EditPostForm` are split on purpose.** `useForm`'s `values` option can't be relied on alone to seed local (non-form) photo state from an async query without a real render-timing race (React Query's `isLoading` can read `false` for one frame right as a disabled query becomes enabled, before the fetch starts) — the wrapper only mounts `EditPostForm` once `lookDetail.data` actually exists, so the form's `useState`/`defaultValues` are always seeded from real data on first render, no `useEffect` resync required.
- **`useActiveXpMultiplier` polls on an interval rather than listening for a real-time event, unlike `useGamificationSocket`'s unlock/level-up toasts.** An XP multiplier turning on or off is a passive, ambient piece of state ("is an event live right now"), not a discrete moment worth a push notification the way a badge unlock is — a 60-second-stale banner is a non-issue for something an admin schedules hours or days in advance, so a plain polling `useQuery` (matching `useXpProgress`'s own shape) was the simpler, sufficient choice over adding a fourth domain event/socket consumer pair to this module for a UI element nobody's staring at waiting for it to flip.
- **`PostModal.integration.test.tsx`/`EditPostForm.integration.test.tsx`'s `searchAndSelectProduct` helper exists purely to dedupe the type-then-select-an-option sequence that four/two tests repeat identically — it does not touch timers.** A `vi.useFakeTimers()` version was tried first, since the tests were intermittently failing with `Test timed out in 5000ms` and the product search goes through a real `setTimeout`-based debounce (`useDebouncedValue`, `SEARCH_DEBOUNCE_MS` in `PostModal.constants.ts`). It was reverted: faking timers made `screen.findByRole` hang for the full test timeout instead of resolving, because MSW's fetch interception and React Query's state updates don't reliably progress under fully-faked timers in this stack — and a fully synchronous test with no timer in it (`"disables Post look until at least one photo is staged"`) was _also_ failing the same way, which ruled out the debounce as the actual root cause. The real cause was `turbo run test` scheduling this project's worker concurrently with `@outfiqe/api#test` (CPU/DB-heavy, single-worker-serial — see `apps/api/src/testing/README.md`), starving this worker of CPU badly enough that even non-async test code occasionally missed the default timeout. Fixed at the actual source: `apps/web/vitest.config.ts`'s `integration` project now sets `testTimeout: 10000` (see `apps/web/src/testing/README.md`) — real headroom for every test in the project, not a per-test workaround.
- **`XpMultiplierBanner.test.tsx` mocks `useActiveXpMultiplier` directly rather than mocking the network layer.** The component's only real logic is "render nothing vs. render this text" based on the hook's return value — the hook itself (a plain `useQuery` wrapper) has no logic of its own worth a separate test, matching the same shallow-mock-the-hook approach `ExploreSearchBox.test.tsx` already established for `useExploreAutocomplete`, rather than standing up MSW for a component this simple.

**Four confirmed Overview/Profile/Share bugs, found and fixed in a QA/audit pass (2026-09-14) — the same audit that swept the Brand dashboard first.**

- **`useCreateLook` only invalidated `["creator-looks"]`, unlike `useUpdateLook`/`useDeleteLook`, which both also invalidate `["explore-feed"]` and `["saved-posts"]`.** A newly created look updated the profile grid but not the explore feed or saved-posts view — a creator posting a new look and immediately switching to `/explore` (or a viewer already on it) wouldn't see it without a manual reload, while editing or deleting the exact same look correctly showed up everywhere. Proved with a component test (`PostModal.integration.test.tsx`'s "invalidates the explore feed and saved posts caches too...") spying on `queryClient.invalidateQueries` and asserting all three keys after a successful `POST /creator-looks` — it failed on the two missing keys against the old hook. Fixed by adding the same two `invalidateQueries` calls `useUpdateLook`/`useDeleteLook` already make.
- **`useUpdateCreatorProfile` never called `router.refresh()` on success — the same class of bug the Brand dashboard audit found and fixed in `useUpdateBrandProfile` first.** `/profile` is Server Component-rendered (`getCreatorProfileServer`/`getCreatorProfileServerPublic`; see the rationale entry below), and `CreatorProfile`'s `saveEdit` only updated its own local `useState` fields on success — correct for the page you're already on, but it never touched the Next.js Client Router Cache. A save, then a soft navigation away and back within the router's stale-time window, re-mounted the page from the stale pre-edit cached render. `useApplyAsCreator` already called `router.refresh()` for exactly this reason (mutating data a Server Component renders); `useUpdateCreatorProfile` was the one outlier missing it. Proved with a component test (`CreatorProfile.integration.test.tsx`'s "refreshes the router on a successful save...") asserting a named `refresh` mock is called after a successful `PATCH /creators/me` — it failed (never called) against the old hook. Fixed by adding the same `onSuccess: () => router.refresh()` `useApplyAsCreator`/`useUpdateBrandProfile` already use.
- **`ShareSection` had no error state for its links list.** `useMyCreatorLinks` (`useInfiniteCursorPage` → `useInfiniteQuery`) already exposes `isError`/`error`/`refetch`, but the component only branched on `isPending` and an empty `links` array — a failed `GET /creator-links/mine` rendered the exact same "No links generated yet — share a product above to get started." empty state as a creator who genuinely has zero links, with no indication anything had gone wrong and no retry short of a full reload. Proved with a component test (`ShareSection.integration.test.tsx`'s "shows a real error banner instead of the empty state...") asserting the empty-state copy did **not** show on a mocked `isError: true` result — it failed (showed the empty-state text) against the old component. Fixed with the same retry-capable error block `ProductsSection` already uses on the Brand side (`getErrorMessage(error)` + a "Try again" button calling `refetch()`), gated so it can't render alongside the empty state.
- **The caption `<textarea>` in both `PostModal` and `EditPostForm` had no accessible name.** Just a `placeholder`, no `aria-label`/`aria-labelledby` and no associated `<label>` — a screen reader landing on the field announced nothing about what it was for, the same accessibility gap the Brand audit found on `BrandProfileView`'s Contact name/Phone/Instagram fields. Proved with a component test on each (`PostModal.integration.test.tsx`/`EditPostForm.integration.test.tsx`'s "labels the caption field for assistive technology") asserting `getByLabelText("Caption")` resolves to the same node as `getByPlaceholderText(...)` — it failed (`getByLabelText` found nothing) against the old markup. Fixed with a visually-hidden (`sr-only`) `<label htmlFor>`/`id` pair on each, matching the pattern `ConditionsEditor.tsx` already uses in `apps/admin` for a labeled-but-not-visibly-labeled field — the caption box keeps its current placeholder-driven look.

**A real concurrent-write race in the tag re-request flow was found but not fixed here — it lives in `creator-looks`, which this audit was scoped to leave untouched.** `creatorLook.repository.ts#update` computes `shouldReRequest = current.reviewStatus === REJECTED && current.reRequestCount < MAX_TAG_RE_REQUESTS` (documented in that module's own README as "a 4th attempt leaves it `REJECTED`") from a row read earlier in the same `$transaction`, then does a plain `tx.creatorLookProduct.update({ where: { creatorLookId_productId }, data: { reRequestCount: { increment: 1 }, ... } })` — the `WHERE` clause carries no `reRequestCount < MAX_TAG_RE_REQUESTS` guard, so two concurrent "Request again" submissions for the same declined tag (a double-click, or two open tabs) can both read the same pre-update count, both pass the in-app check, and both increment — letting the cap be exceeded by however many requests race through, the same class of bug the Brand audit fixed in tag approve/reject with a status-guarded `updateMany`. Reported, not fixed, per this audit's explicit scope; recommended fix is a conditional `updateMany` (`where: { ..., reviewStatus: REJECTED, reRequestCount: { lt: MAX_TAG_RE_REQUESTS } }`, checking `result.count > 0`), the exact pattern `consumeSingleUse` in `creator-links/creatorLink.repository.ts` already uses correctly for single-use link tokens. As defense in depth on the side of this that _is_ in scope, `ProductTagPicker`'s "Request again" button now disables itself (`isReRequestPending`, wired from `EditPostForm`'s existing `isSaving`) while a request is in flight, closing the easy single-tab double-click case — the cross-tab/cross-request race still needs the backend fix above.

**Ruled out, each backed by reading the actual server-side enforcement, not assumed:** `creator-overview` (KPIs, trend, recent commissions) has a real, considered empty state for a brand-new approved creator — the trend query zero-fills every day via SQL (`generate_series` left-joined, never application-side), `getLookAggregates`/`getFollowerCount` default to `0`, and `CreatorOverview.tsx` shows a real chart-empty message and a "No commissions yet" card rather than a blank area; `commissionRepository.listForCreator`'s `orderBy: [{ createdAt: "desc" }, { id: "desc" }]` already gives the recent-commissions list a deterministic tie-break. `creator-links` tokens are DB-unique (`token String @unique`), `creatorId` is always taken from the auth principal (never the client body) on every write and read, and `listForCreator`/`listMine` filter by `creatorId` at the query level — a creator can't view or use another creator's links. A PENDING/REJECTED creator can't reach post create/edit/share server-side: `creatorLookService.create`/`creatorLinkService.createInternal`/`getOrCreateExternal`/`listMine` all call `requireApprovedCreator`, and `update`/`getOwn`/`remove` gate on ownership (`requireOwnedLook`) rather than status — which is sufficient because a never-approved creator can never own a look in the first place (creation itself requires approval), so ownership-gating denies them by construction. `PATCH /creators/me` (profile update) and the photo pipeline (`resolvePendingPhotoAssets`/`uploadWithPipeline` awaited before the create/update mutation ever fires) both fail closed — a partial upload failure aborts before any look is created or updated, never leaving a post referencing a broken image.
