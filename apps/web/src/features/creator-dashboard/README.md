# creator-dashboard

## Purpose

Everything a creator manages about their own account, from their own top-level routes (`/overview`, `/profile`, `/share`, `/earnings`, `/withdraw`, `/progress`, `/badges`, `/challenges`, sharing the same sidebar layout via the `(dashboard)` route group): the at-a-glance dashboard, profile edits, applying to become a creator, posting/editing looks, share links, and earnings. Post viewing/browsing lives in `creator-profile`, not here — this feature owns the mutation side of a creator's posts.

## Structure

- `components/CreatorOverview.tsx` — the `/overview` landing (also the post-login destination for non-admins, see `features/auth/utils/getDefaultRoute.ts`). Three bands: a `StatCard` KPI row (earnings / available / pending / followers / looks / likes), an `<ChartCard>`+`<TrendChart>` area chart of commission earnings per day over 30 days, and the five most recent commissions rendered with `EarningsLedgerRow` (with a "View all" link to `/earnings`). Same `CreatorStatusGate` treatment as `EarningsSection` for a not-yet-approved creator. `api/creatorOverviewApi.ts`/`creatorOverviewSchemas.ts` (reusing `creatorCommissionSchema` for the recent list) and `hooks/useCreatorOverview.ts` mirror the earnings equivalents' shape; the whole page is one `GET /creators/me/overview` call so it has one loading state.
- `components/PostModal.tsx` — create-a-post modal: multi-photo crop/upload, caption, product tagging.
- `components/EditPostModal.tsx` — edit-a-post modal wrapper: fetches the look, shows a layout-matched skeleton while loading, then mounts `EditPostForm` once data is ready.
- `components/EditPostForm.tsx` — the actual edit form (photos, caption, tags). Mounted fresh (`key={lookId}`) per post being edited so its local photo/form state always seeds correctly from real data — no effect-driven resync needed.
- `components/ProductTagPicker.tsx` — shared tag-picker UI used by both `PostModal` and `EditPostForm`.
- `components/ApplyAsCreatorButton.tsx`, `EarningsSection.tsx`, `ShareSection.tsx` — the other dashboard sections.
- `components/ProgressSection.tsx`, `LevelProgressCard.tsx`, `XpTransactionRow.tsx`, `XpMultiplierBanner.tsx` — the gamification level/XP-bar card + recent-activity list (`/progress`). Unlike `EarningsSection`/`ShareSection`, this one is **not** gated by `CreatorStatusGate` — every user earns and can view their own XP, not just approved creators, so it renders unconditionally for any non-brand account. `api/xpApi.ts`/`xpSchemas.ts`, `hooks/useXpProgress.ts`/`useMyXpTransactions.ts`/`useActiveXpMultiplier.ts` follow the exact same shape as the earnings equivalents. `XpMultiplierBanner` renders nothing when no `XpMultiplier` window is currently live server-side (`GET /xp/multiplier/active`); `useActiveXpMultiplier` polls it every 60s so the banner appears/disappears close to the actual window boundary without needing a socket event for something this low-stakes.
- `components/BadgeCollectionSection.tsx`, `AchievementBadgeCard.tsx`, `AchievementBadgeIcon.tsx`, `BadgeFilterTabs.tsx` — the badge collectible-library UI (`/badges`), same not-creator-gated reasoning as `ProgressSection`. Named `AchievementBadge*`, not `Badge*` — `@outfiqe/design-system` already exports a generic status-pill `Badge` component, which `AchievementBadgeCard` itself imports and reuses for the rarity tag, so a same-named component here would shadow that import on every page needing both. `api/badgeApi.ts`/`badgeSchemas.ts`, `hooks/useBadgeCollection.ts`/`useUpdateBadgeDisplay.ts`/`useUpdateFeaturedBadges.ts` mirror the earnings/progress equivalents' shape. `AchievementBadgeIcon` resolves which of the shared `animate-badge-*` classes (defined in `packages/design-system/tokens.css`, see that package's README) to apply from `designConfig.animation` if the admin set one, falling back to a fixed `RARITY_DEFAULT_ANIMATION` (common/uncommon get none, rising through glow → shimmer → pulse → radiant at the top rarity) when they didn't — never animated while locked, since a grayscale locked badge animating would just look broken, not enticing. Also imported cross-feature by `../creator-leaderboard`'s `CreatorCompetitionBanner` (`isLocked={false}`, previewing a competition's trophy badge) — the icon-rendering logic was written generically enough from the start that a second, unrelated feature could reuse it without any change here. `AchievementBadgeCard` shows a "Sponsored by {brand}" credit (linking to `/brand/:id`) whenever `entry.sponsorBrand` is present — the same field on both a collected and a locked entry, so a brand's credit shows up before someone's even earned the badge, not just after.
- `components/ChallengesSection.tsx`, `ChallengeCard.tsx` — time-boxed goals (`/challenges`), same not-creator-gated reasoning as `ProgressSection`/`BadgeCollectionSection`. Reuses `AchievementBadgeIcon` for the awarded badge's preview rather than a separate icon component, since a challenge's reward literally is a `Badge` — there's no separate visual language to invent. `api/challengeApi.ts`/`challengeSchemas.ts`, `hooks/useChallenges.ts` mirror the badge collection's shape (list read, optional per-viewer progress/completion folded server-side).
- `utils/badgeLabels.ts` — `RARITY_LABEL`/`METRIC_LABEL`, shared between `AchievementBadgeCard` and `ChallengeCard` since both render the same rarity tag and the same per-condition progress rows. `METRIC_LABEL` includes the seven `*_rank` metrics alongside the counter metrics; `isRankMetric`/`RANK_METRICS` let `AchievementBadgeCard` render those conditions as plain "currently #N · need top M" text instead of a `ProgressBar` — a rank shrinks toward its target, the opposite direction a `value`/`max` progress bar assumes, so reusing the bar for one would render a materially misleading fill.
- `components/CreatorStatusGate.tsx` — the shared "not an approved creator yet" state (application under review / become-a-creator pitch + `ApplyAsCreatorButton`), rendered by `EarningsSection`, `ShareSection`, and `app/(dashboard)/profile/page.tsx` whenever `creatorStatus !== APPROVED`.
- `components/GamificationSocketListener.tsx`, `hooks/useGamificationSocket.ts`, `socketEvents.ts` — the real-time achievement-unlock/level-up toast. Lives here alongside `ProgressSection`/`BadgeCollectionSection` since it's the same XP/badge domain, but — unlike everything else in this feature — it isn't rendered from a dashboard page. It's mounted once, globally, from `app/providers.tsx` (any authenticated user can level up or unlock an achievement from anywhere in the app, not just while looking at `/progress`), imported by its direct component path rather than through this feature's `index.ts` barrel — see rationale below.
- `api/creatorLooksApi.ts`, `creatorLooksSchemas.ts` — look create/edit/delete requests + response validation.
- `api/creatorDashboardApi.ts`, `creatorDashboardSchemas.ts` — profile read/update, including `heightCm`/`showHeight`/`hideFromLeaderboards` (edited from `creator-profile`'s edit-profile modal, not from this feature).
- `hooks/useCreateLook.ts`, `useUpdateLook.ts`, `useDeleteLook.ts`, `useLookDetail.ts` — look mutations and the on-demand single-look fetch used to prefill the edit modal.
- `hooks/useUpdateCreatorProfile.ts`, `useTaggableProducts.ts` — profile update and product search for tagging. `PostModal`'s local photo/crop state (`usePendingPhotos`) lives in `@/shared/hooks` — see below (`EditPostForm` manages its own photo state separately, unaffected).
- `schemas/lookForm.schema.ts` — `lookFormSchema` (the wire shape: `imageUrls`/`caption`/`taggedProducts`, used by both create and update requests) and `editLookFormSchema` (the `EditPostForm` RHF form itself, which only tracks caption/tags — photos are separate component state, merged in at submit time).

## Funnel

**User-facing:** a creator opens their own profile (`creator-profile`), taps the floating add-post button to post a new look, or opens the 3-dot menu on one of their existing posts to edit its photos/caption/tags or delete it.

**Technical:** `creator-profile`'s `CreatorProfile`/`CreatorPostThumbnail` render `PostModal`/`EditPostModal` from this feature (cross-feature import, same pattern as `CreatorProfile` already using `useUpdateCreatorProfile` and `explore`'s `AddPostButton`/`PostDetailModal`). `EditPostModal` fetches the look via `useLookDetail` → `creatorLooksApi.getOwn` → `GET /creator-looks/:lookId` to get per-tag `sizeWorn`, which the public feed-shaped post data doesn't carry. `EditPostForm` tracks existing image URLs and newly-added local photos separately; on submit it crops+uploads only the new photos, then sends the full `imageUrls` list (surviving existing + newly uploaded, in that order) to `PATCH /creator-looks/:lookId` — that endpoint replaces the look's whole image set. On success, mutations invalidate `["creator-looks"]`, `["explore-feed"]`, and `["saved-posts"]` so the profile grid, explore feed, and saved view all pick up the change.

`useGamificationSocket` acquires the shared ref-counted socket connection (`@/shared/lib/socketClient`, the same singleton `explore`'s `useExploreFeedSocket` uses) only while `useAuth().isAuthenticated` is true, listens for `achievement:unlocked`/`level:up`, and renders each via `toast.success` (`@outfiqe/design-system`). The connection is released on logout/unmount so a signed-out visitor never holds an idle socket open for events they can't receive (`userRoom`-scoped events require auth server-side). `formatAchievementToast` (exported, unit-tested) appends `(sponsored by {brand})` to the toast text when the unlocked badge's `sponsorBrandName` is present — a plain string, not a logo/link, since the toast itself is rendered as flat text with no image slot.

## Non-obvious rationale

- **`/overview` is the post-login landing for every non-admin (creators, brands, shoppers), replacing `/profile`.** `getDefaultRouteForUser` returns `/overview`; the `(dashboard)/overview/page.tsx` route redirects `BRAND_OWNER` to `/profile` for now — the brand variant of the Overview is a later change. A shopper who isn't an approved creator lands on `/overview` and sees `CreatorStatusGate` (the become-a-creator pitch), which is a reasonable first screen for that account type; revisit if a dedicated shopper landing is ever wanted.
- **`ChallengesSection` lives at `/challenges`, gated by the same `requireDashboardSession` + brand-owner redirect as `/badges` — not a genuinely logged-out-visible marketing page.** The backend's `GET /challenges` is `optionalAuth` (it can serve an anonymous request), but nothing here builds a public, unauthenticated surface for it — that's a real, separate product decision (a marketing/landing page, SEO, its own layout) this feature doesn't make on its own. Being logged-in-gated here matches every other gamification page in this feature and is a straightforward call, not a silent scope cut; a public page can be added later against the same already-optional-auth endpoint without any backend change.
- **`isDynamicallyActive` is read straight off the API response, never derived client-side.** `AchievementBadgeCard` shows its "not currently active" note only on the exact `=== false` case — `null` (not a dynamic badge, or not collected) must not trigger it, and plain `!isDynamicallyActive` would, since `!null` is `true` in JS. The API already folds the badge's own `isDynamic` flag into that field (`null` unless both collected and dynamic), so the component doesn't need to know about `isDynamic` at all — one field, one meaning, no derived state to keep in sync.

- **`RARITY_LABEL`/`METRIC_LABEL` moved out of `AchievementBadgeCard.tsx` into `utils/badgeLabels.ts`, and `total_views` was added to `METRIC_LABEL`, while relocating it for `ChallengeCard`'s reuse.** The map was missing `total_views` since before this feature had any achievement that used it — a progress row for that metric would have silently fallen back to the raw `"total_views"` string instead of "Total views." Caught while extracting the map for a second consumer, fixed in the same pass rather than carried forward into a second copy.
- **`xpSchemas.ts`'s hand-mirrored `XpActivityType` (and its `packages/types` source) was missing `ACHIEVEMENT_UNLOCKED`, found during chunk 13's polish pass, not by inspection.** `packages/types/src/xp/index.ts` was written in chunk 5, before the achievements engine (chunk 6) started writing `XpTransaction` rows with `activityType: "ACHIEVEMENT_UNLOCKED"` — the mirror was never updated to match. Since `xpTransactionSchema.activityType` is `z.enum(XpActivityType)`, any transaction page containing even one such row failed Zod validation entirely, throwing inside the query rather than rendering a wrong label — for any user who had ever unlocked an achievement or received a manually-awarded badge with an XP reward, `/progress`'s transaction history would error out completely, not just misrender one row. This is exactly the class of drift this codebase's own hand-mirrored-enum convention is fragile to (see the project's `packages/types` pattern notes) — worth double-checking the other hand-mirrored enums here (`BadgeCategory`, `BadgeRarity`, etc.) stay in sync whenever the Prisma schema's gamification enums change, since nothing currently catches this automatically.
- **Follow-up: still no component tests for `ProgressSection`/`BadgeCollectionSection` and most of their children, or for `useGamificationSocket`'s actual socket wiring.** This repo's testing convention expects React Testing Library coverage for components like these (rendered/interacted-with, not just typechecked); most of it shipped verified only via a live end-to-end pass (real login, real data, real toggle interactions for the former; a real connected Socket.IO session receiving a genuine server-published event for the latter) rather than isolated tests with mocked data — no test in this codebase currently mocks a Socket.IO client connection, matching the same gap `explore`'s `useExploreFeedSocket` already has. `AchievementBadgeCard.test.tsx` and `useGamificationSocket.test.ts` exist now, but narrowly — the former covers only the sponsor-credit link (not the toggle/feature button interactions or the progress-bar rendering), the latter covers only `formatAchievementToast`'s pure string output, not the hook's `socket.on`/`acquireSocketConnection` wiring itself. Worth circling back to add proper component specs for `LevelProgressCard`, the rest of `AchievementBadgeCard`'s interactions, and a shared Socket.IO client mock the two hooks could share.
- **`AchievementBadgeIcon.test.tsx` covers the animation-resolution logic (rarity defaults, an explicit override in either direction, the locked/no-animation case, the glow color custom property) via plain render-and-inspect-the-DOM assertions — no timers, no `getComputedStyle`.** The component's `prefers-reduced-motion` handling lives entirely in `packages/design-system/tokens.css`'s media query, not in this component's own logic, so there's nothing for a component test to usefully assert there; what the component itself is responsible for — which class name gets applied and what color the animation reads — is exactly what's tested. Verified once, live, that the actual keyframe animations render and are visually distinct per rarity in a real browser rather than assumed correct from the class names alone.
- **Featuring badges is click-to-toggle, not drag-and-drop.** The PRD's spec 24 describes a drag-reorder UI for featured badges; `BadgeCollectionSection` ships a "Feature"/"Unfeature" button per collected card instead, with order determined by click sequence (append on feature, remove-and-close-the-gap on unfeature), capped at `MAX_FEATURED_BADGES`. A real drag-and-drop interaction needs a DnD library this repo doesn't currently depend on — introducing one is a bigger call than this chunk's scope, so it's flagged as a deliberate simplification rather than silently different from the spec. The backend (`PATCH /badges/featured`, a full-list replace) already supports a real drag-reorder UI without any API change if one gets built later — only this component would need to change.
- **`/creators/me` never gates on creator status** — it returns a profile (including `handle` and `creatorStatus`) for any authenticated user, since it also backs the "become a creator" pitch screens. `/creators/by-handle/:handle` (the public profile, fetched server-side and rendered inline once the creator is approved) _does_ gate on `isCreator`/`APPROVED`. `app/(dashboard)/profile/page.tsx` has to check `creatorStatus === APPROVED` itself before fetching/rendering the public profile — doing so unconditionally would 404 non-approved users against the gated endpoint. There's no `[handle]` route under `/profile` — the URL stays `/profile` for every state (gate screen or the rendered profile); the page just fetches `getCreatorProfileServerPublic(profile.handle)` and renders `CreatorProfile` directly instead of redirecting to a per-handle URL.
- There used to be a standalone "Posts" dashboard section (`/dashboard/posts`, its own sidebar nav item) that just listed a creator's own looks with no edit/delete. It was removed because the creator's profile already shows the same grid — keeping both was duplicated UI with no distinct purpose. Posting now happens from the profile's floating action button; editing/deleting happens from the 3-dot menu on each post thumbnail (`creator-profile/components/PostActionsMenu.tsx`).
- **`PostModal`'s two-pane crop layout is a shared component, not local markup.** `usePendingPhotos`/`resolvePendingPhotoUrls` (`@/shared/hooks/usePendingPhotos.ts`), `PendingPhotoThumbnailRail` and `PhotoCropPane` (`@/shared/components/`), and the outer `MediaFormShell` (fixed photo pane + scrollable fields + sticky footer) were pulled out of this feature once `brand-dashboard`'s product modals needed the same "pick photos, crop one at a time, defer upload to submit" experience — see that feature's README for how it reuses them for products (a domain with a square aspect and optional, already-hosted existing photos instead of a mandatory portrait one).
- **Existing photos aren't re-cropped in edit mode**, only added or removed. They were already cropped/stored at post time; `EditPostForm` shows them as plain removable thumbnails and only runs a new photo through `CropSurface` once, at add-time, before it's committed to the list — reusing `PostModal`'s crop pipeline (`CROP_BOX_STYLE`, `PHOTO_ASPECT`, `getCroppedImageFile`) without needing `usePendingPhotos`, since edit only ever stages one new photo at a time rather than managing a whole multi-photo crop session.
- **`app/providers.tsx` imports `GamificationSocketListener` by its direct file path, never through this feature's `index.ts` barrel.** The barrel also re-exports `getCreatorProfileServer` (`api/getCreatorProfileServer.ts`), which imports `"server-only"` — fine everywhere else this barrel is consumed (from Server Component pages), but `providers.tsx` is a Client Component mounted at the very root of the app, so pulling in the whole barrel there drags a server-only module into client bundling and hard-crashes the page (`'server-only' cannot be imported from a Client Component module`) — caught live rather than shipped, since it only surfaces once something in the barrel is actually consumed from a client-only entry point. Importing the component's own path sidesteps the barrel entirely; this is the standard Next.js App Router mitigation for a barrel that deliberately mixes server-only and client-safe exports, not a sign this barrel needs restructuring today.
- **`EditPostModal`/`EditPostForm` are split on purpose.** `useForm`'s `values` option can't be relied on alone to seed local (non-form) photo state from an async query without a real render-timing race (React Query's `isLoading` can read `false` for one frame right as a disabled query becomes enabled, before the fetch starts) — the wrapper only mounts `EditPostForm` once `lookDetail.data` actually exists, so the form's `useState`/`defaultValues` are always seeded from real data on first render, no `useEffect` resync required.
- **`useActiveXpMultiplier` polls on an interval rather than listening for a real-time event, unlike `useGamificationSocket`'s unlock/level-up toasts.** An XP multiplier turning on or off is a passive, ambient piece of state ("is an event live right now"), not a discrete moment worth a push notification the way a badge unlock is — a 60-second-stale banner is a non-issue for something an admin schedules hours or days in advance, so a plain polling `useQuery` (matching `useXpProgress`'s own shape) was the simpler, sufficient choice over adding a fourth domain event/socket consumer pair to this module for a UI element nobody's staring at waiting for it to flip.
- **`PostModal.integration.test.tsx`/`EditPostForm.integration.test.tsx`'s `searchAndSelectProduct` helper exists purely to dedupe the type-then-select-an-option sequence that four/two tests repeat identically — it does not touch timers.** A `vi.useFakeTimers()` version was tried first, since the tests were intermittently failing with `Test timed out in 5000ms` and the product search goes through a real `setTimeout`-based debounce (`useDebouncedValue`, `SEARCH_DEBOUNCE_MS` in `PostModal.constants.ts`). It was reverted: faking timers made `screen.findByRole` hang for the full test timeout instead of resolving, because MSW's fetch interception and React Query's state updates don't reliably progress under fully-faked timers in this stack — and a fully synchronous test with no timer in it (`"disables Post look until at least one photo is staged"`) was _also_ failing the same way, which ruled out the debounce as the actual root cause. The real cause was `turbo run test` scheduling this project's worker concurrently with `@outfiqe/api#test` (CPU/DB-heavy, single-worker-serial — see `apps/api/src/testing/README.md`), starving this worker of CPU badly enough that even non-async test code occasionally missed the default timeout. Fixed at the actual source: `apps/web/vitest.config.ts`'s `integration` project now sets `testTimeout: 10000` (see `apps/web/src/testing/README.md`) — real headroom for every test in the project, not a per-test workaround.
- **`XpMultiplierBanner.test.tsx` mocks `useActiveXpMultiplier` directly rather than mocking the network layer.** The component's only real logic is "render nothing vs. render this text" based on the hook's return value — the hook itself (a plain `useQuery` wrapper) has no logic of its own worth a separate test, matching the same shallow-mock-the-hook approach `ExploreSearchBox.test.tsx` already established for `useExploreAutocomplete`, rather than standing up MSW for a component this simple.
