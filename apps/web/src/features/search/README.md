# Search

## Purpose

Two search results pages, one per `ShopExploreToggle` mode: `/search` (products, shop mode) and `/explore/search` (creators + posts, explore mode). Same nav search boxes drive both — which page they submit to depends on which mode you're currently in. Neither results page has its own input; every search box lives in the nav. Both modes' nav boxes live-suggest results as you type — shop mode suggests products, explore mode suggests creators and posts together in one grouped dropdown.

## Structure

- `components/SearchResults.tsx` — `/search`. Reads `q` from the URL and renders the paginated product grid under a plain header-style title.
- `components/ExploreSearchResults.tsx` — `/explore/search`. Same URL-driven shape, but renders two independent sections — a `Creators` list and a `Posts` masonry grid (reusing `features/explore`'s own `PostGridCard`/`PostDetailModal`) — each with its own infinite-scroll pagination, since they're two unrelated ranked result sets from two different endpoints.
- `components/ProductSearchBox.tsx` — the shop-mode nav search box (not a results-page component — rendered by `SiteHeader.tsx`/`MobileNav.tsx` in place of `ExploreSearchBox` whenever `!isExploreRoute`). Built on the design system's `Autocomplete`/`AutocompleteInput`/`AutocompleteContent`/`AutocompleteItem` primitives: debounces the typed value, live-fetches `GET /products/autocomplete`, and shows a small thumbnail dropdown — Enter with a suggestion highlighted jumps straight to `/product/:id`, Enter with nothing highlighted (or a plain click on the search icon/submit) falls through to the normal full `/search?q=...` results page.
- `components/ExploreSearchBox.tsx` — the explore-mode nav search box, rendered in place of `ProductSearchBox` whenever `isExploreRoute`. Same debounce/`Autocomplete` shape as `ProductSearchBox`, but fires two queries in parallel (`GET /creators/autocomplete`, `GET /creator-looks/autocomplete`) via `useExploreAutocomplete` and renders them as two labeled sections — `AutocompleteGroup label="Creators"` then `AutocompleteGroup label="Posts"` — inside one dropdown, since (like the results page) they're two independent ranked result sets, not one list. Selecting a creator suggestion routes to `/creator/:handle`; selecting a post suggestion also routes to `/creator/:handle` (the post's creator) rather than opening `PostDetailModal` directly — there's no public single-post-by-id endpoint to deep-link a specific post the way a product suggestion deep-links to `/product/:id` (see `apps/api/src/modules/creator-looks/README.md`). Enter with nothing highlighted still falls through to `/explore/search?q=...`, same as `ProductSearchBox`.
- `api/exploreSearchApi.ts`, `exploreSearchSchemas.ts` — `GET /creators/search`/`GET /creators/autocomplete` and `GET /creator-looks/search`/`GET /creator-looks/autocomplete` clients (`creators`/`posts` for full results, `autocompleteCreators`/`autocompletePosts` for suggestions — named explicitly per resource since, unlike `productsApi`, this one file's methods aren't already namespaced by an enclosing per-resource module). Products has no equivalent local `api/` — search _and_ autocomplete both reuse `features/products/api/productsApi.ts` (`list` extended with `q`/`minPrice`/`maxPrice`/`inStock`, plus a new `autocomplete`) since both are just different views on the existing product listing; creators/posts don't have an existing browse-listing feature to extend the same way, so they get their own thin client here.
- `hooks/useExploreSearch.ts` — `useCreatorSearch`/`useLookSearch`, both thin `useInfiniteCursorPage` wrappers over `exploreSearchApi`, backing the results page.
- `hooks/useExploreAutocomplete.ts` — fires `autocompleteCreators`/`autocompletePosts` as two parallel `useQuery`s behind one debounced/`enabled` query string, backing `ExploreSearchBox`. The product-autocomplete hook (`useProductAutocomplete`) lives in `features/products/hooks/` instead, alongside `useInfiniteProducts`, for the same reuse-the-products-feature reason as the api client above.
- `search.constants.ts` — `MIN_QUERY_LENGTH`, `AUTOCOMPLETE_DEBOUNCE_MS`.

## Funnel

**User-facing:** type into one of the two real search boxes — the desktop navbar's inline box (`SiteHeader.tsx`, `lg` and up) or the mobile hamburger menu's box (`MobileNav.tsx`, below `lg`). In shop mode, suggestions appear as you type (`ProductSearchBox`) — pick one to go straight to that product, or press Enter to see the full ranked results page instead. In explore mode, suggestions also appear as you type (`ExploreSearchBox`), grouped into a "Creators" section and a "Posts" section in one dropdown — pick a creator to go to their profile, pick a post to go to its creator's profile (see rationale below), or press Enter with nothing highlighted to land on `/explore/search?q=...` instead (a `Creators` row list, a `Posts` grid, or both — whichever have matches, and a post's match can come from its own caption/hashtags _or_ its creator's name/handle, so searching a creator also surfaces their posts). Tapping a creator or post on that results page behaves exactly like it would from `/explore` itself (creator row → profile page, post tile → `PostDetailModal`).

**Technical:** both nav boxes are now fully controlled, same shape: typed value → `useDebouncedValue` (`AUTOCOMPLETE_DEBOUNCE_MS`) → an autocomplete hook → suggestion endpoint(s) (see the api module READMEs for the memory+Redis cache behind each), rendered into an `AutocompleteContent` dropdown. The shop-mode box (`ProductSearchBox`) fires one query (`useProductAutocomplete` → `GET /products/autocomplete?q=...`) into a flat list; the explore-mode box (`ExploreSearchBox`) fires two in parallel (`useExploreAutocomplete` → `GET /creators/autocomplete?q=...` and `GET /creator-looks/autocomplete?q=...`) into two `AutocompleteGroup`s. Selecting an item or submitting either form both clear the input and call the same `onNavigate` callback (used to close the mobile drawer) before routing. Which path either box's Enter-fallback pushes to comes from `searchPathFor(pathname)` (`@/shared/lib/exploreMode.ts`), the same `pathname.startsWith("/explore")` check `ShopExploreToggle` uses to decide which mode is "active" — all three were duplicating that check inline before this shared helper existed. `SearchResults` calls `useInfiniteProducts({ q })` → `GET /products?q=...` (see `apps/api/src/modules/products/README.md`). `ExploreSearchResults` calls `useCreatorSearch`/`useLookSearch` → `GET /creators/search` / `GET /creator-looks/search` (see `apps/api/src/modules/creators/README.md` and `apps/api/src/modules/creator-looks/README.md`) in parallel, independently paginated.

## Non-obvious rationale

- **No server prefetch, deliberately, on either results page.** Both page components are `"use client"` from the top with no `queryClient.prefetchQuery`/`HydrationBoundary`, unlike `/shop`/`/explore`/`(home)`. There's nothing to prefetch before a query exists, and the query itself is inherently client-driven, so the usual SSR-then-hydrate shape other pages use would add complexity for no payoff here.
- **No input box on either results page itself.** An earlier version of `/search` put a second input on the page (desktop: none, since the navbar's is always visible; mobile: one, since the navbar had only an icon). That duplicated the mobile hamburger menu's own search box for no reason once it was wired up properly — one input per surface (nav, not results page) is simpler and matches how `/shop`/`/explore` also have no on-page filters box, just URL-driven state. `/explore/search` follows the same rule from the start.
- **No frontend LRU cache for autocomplete**, only a backend one (api module README). TanStack Query's query cache already memoizes each autocomplete hook's results per query key for the configured `staleTime` — a separate client-side LRU library would just duplicate that for no benefit, since it's a single-session, single-tab cache either way.
- **Creator search/autocomplete results don't have a Follow button.** The API's `CreatorSearchResult` doesn't carry `isFollowing` (see the api module README for why), so a Follow button here would either always say "Follow" even for someone you already follow, or need a second round trip per result to check. The row links to the creator's profile instead, where following already works correctly.
- **Two independent infinite-scroll sections on one page, not one merged feed** (and the same split carries into `ExploreSearchBox`'s dropdown as two `AutocompleteGroup`s, not one flat list). Creators and posts are two structurally different, separately-ranked result sets (a person vs. a photo post) from two different endpoints — interleaving them into one ranked list would need a merge-ranking scheme across two unrelated scoring functions, which neither the API nor the product-search precedent this was built from does. Instagram-style "top accounts row, then a content grid" — same shape, two independent `useInfiniteCursorPage`s and sentinels on the results page, two independent `useQuery`s and `AutocompleteGroup`s in the dropdown — was the simpler, correct fit both times.
