# creator-profile

## Purpose

Renders a creator's public profile — avatar, stats, follow/edit-profile, and their post grid. Used both for the public `/creator/[handle]` page and the dashboard's static `/profile` route (same `CreatorProfile` component, gated by `isOwnProfile`).

## Structure

- `components/CreatorProfile.tsx` — the page: header/stats, follow or edit-profile action, a Share button (native share sheet where the browser has one, otherwise copies the profile link — `apps/web/src/features/pwa`'s `shareOrCopyLink`), post grid, and (when `isOwnProfile`) the add/edit/delete post affordances. The edit-profile modal also has a height (cm) field, a "Show height on my profile" checkbox, and a "Hide me from leaderboards" checkbox, backed by `User.heightCm`/`showHeight`/`hideFromLeaderboards` (see `../creator-dashboard/README.md` and `apps/api/src/modules/creators/README.md`). Also renders `titleBadge` (spec 53 — singular, prominent, a colored pill next to the display name) and `featuredBadges` (spec 24–27 — multiple, subtle, up to `MAX_PROFILE_FEATURED_BADGES` shown as a small icon row below it via `AchievementBadgeIcon` from `@outfiqe/design-system`). Neither has its own toggle here — an owner manages which badges are featured and which one is their title from `/badges` (`creator-dashboard`'s badge collection page); this component only renders whatever the API already resolved. See rationale below for why the title badge doesn't use `AchievementBadgeIcon` and why the on-profile featured count differs from the server-enforced max.
- `components/CreatorPostThumbnail.tsx` — one grid tile; shows a bottom gradient + truncated caption over the image when the post has one, and renders `PostActionsMenu` on top when viewing your own profile. Clicking anywhere on the tile opens `explore`'s `PostDetailModal` for the full post.
- `components/PostActionsMenu.tsx` — the 3-dot menu (Edit / Delete) overlaid on a post thumbnail.
- `components/CreatorPostGridSkeleton.tsx`, `CreatorProfilePageSkeleton.tsx` — loading states.
- `api/creatorProfileApi.ts`, `creatorProfileSchemas.ts` — profile + paginated posts fetch.
- `hooks/useInfiniteCreatorLooks.ts` — infinite-scroll post grid data.

## Funnel

**User-facing:** anyone can view a creator's profile and browse their posts. If it's your own profile, a floating "Post" button (bottom-right, reused from `explore`) opens the create-post modal, and each of your post tiles has a 3-dot menu to edit its caption/tags or delete it (with a confirm step).

**Technical:** `CreatorProfile` fetches posts via `useInfiniteCreatorLooks` → `creatorProfileApi.listLooks` → `GET /creators/by-handle/:handle/looks` (feed-shaped posts, no auth required). Posting/editing/deleting are handled by `creator-dashboard`'s `AddPostButton`/`PostModal`/`EditPostModal`/`useDeleteLook` (cross-feature import — this feature owns display, `creator-dashboard` owns mutation). A successful edit/delete invalidates the `creator-looks` query family, so the grid refetches; delete also decrements the local `postsCount` immediately since that stat isn't part of the paginated post list.

**Deep-linking a specific post:** the open post is driven by the `?look={id}` URL param (`useSearchParams`), not local component state — clicking a grid tile updates the param with `window.history.replaceState` (App Router keeps `useSearchParams` in sync and does not re-run the route), closing clears it the same way, and `PostDetailModal` opens whenever it resolves to a real post. `router.replace` was used here originally, but on this route it re-executed the `app/creator/[handle]/page.tsx` server component — including its `getCreatorProfileServerPublic(handle)` fetch — on every open and close, which made the modal noticeably slow to appear on this page specifically. A hard load or shared `?look=` link still renders server-side as before. That post is looked up in the already-loaded grid pages first (`posts.find`); if it isn't there (e.g. a notification linking to a post from months ago that hasn't been paged to), `explore`'s `usePublicLook(lookId)` fetches it directly via `GET /creator-looks/:lookId/public`. Because `useSearchParams` requires a Suspense boundary, `app/creator/[handle]/page.tsx` wraps `<CreatorProfile>` in `<Suspense fallback={<CreatorProfilePageSkeleton />}>`.

## Non-obvious rationale

Post management used to live in a separate `/dashboard/posts` page with no edit/delete. It was folded into the profile grid because the profile already displays the same posts — see `creator-dashboard`'s README for the full reasoning.

`heightCm` in the fetched `CreatorProfile` is already visibility-masked server-side (`null` unless the creator turned `showHeight` on, or you're viewing your own profile) — the component never needs to hide it itself, and can seed the edit modal's draft height straight from the fetched value even when `showHeight` is currently off, since the API reveals the real number back to the owner.

`hideFromLeaderboards` rides the same public `CreatorProfile` response as `showHeight`, unmasked for every viewer, not just the owner. It's a low-sensitivity preference flag, not the underlying stats the creator-leaderboard scores are built from — whether someone opted out isn't private the way an unrevealed height is, so unlike `heightCm` there's no masking to do, and the edit modal seeds `draftHideFromLeaderboards` straight from the fetched value the same way it does for `showHeight`.

`GET /creators/by-handle/:handle` (`apps/api/src/modules/creators/creator.service.ts`) has resolved `featuredBadges`/`titleBadge` since the badges chunk landed, but `creatorProfileSchema` never declared those two fields — Zod strips unlisted keys by default, so the data arrived on the wire and was silently discarded before this component ever saw it, and nothing rendered on the profile despite the badge collection page's "Feature"/"Show on profile" toggles genuinely writing real data. Fixed by adding `featuredBadgeSchema` (mirroring the API's `FeaturedBadgeView`) to `creator-dashboard/api/badgeSchemas.ts` and referencing it from both new fields here — a reminder that a field missing from a Zod response schema fails silently (no thrown error, no visible bug in the network tab), not loudly, so a new API response field needs the schema updated in the same change, not assumed to "just work" because the backend already sends it.

**The profile row only ever renders the first `MAX_PROFILE_FEATURED_BADGES` (3) of a user's featured badges, even though `MAX_FEATURED_BADGES` (6) is the real, server-enforced cap on how many a user can mark featured.** These are deliberately two different numbers for two different jobs: 6 is how many an owner is _allowed to curate_ from their badge collection page (a bigger number gives room to swap badges in and out without losing the rest), while 3 is how many actually _show_ on the compact profile header so it doesn't get visually noisy. The extra 3 a user has featured still exist and are still returned by the API — a future "view all featured badges" surface could show them — this component just slices the array for display, it doesn't call any endpoint that enforces a lower limit.

**The title badge renders inside a colored pill (icon + uppercase label), and that same accent color carries over to the avatar's ring — both derived from the one equipped title badge, not independently styled.** `badgeAccentColor()` reads the badge's own `designConfig.primaryColor` (falling back to `TITLE_BADGE_FALLBACK_COLOR` only for a studio-designed badge with no single `primaryColor`). The featured-badge row and the title pill's icon both use the real `AchievementBadgeIcon` component (not a hand-rolled icon), specifically so any badge shown there — not just the title — gets the same rarity-driven animation automatically, rather than the profile silently looking more static than the badge collection grid.

**The avatar's "equipped" ring is a rotating `conic-gradient` (an Instagram/Discord-style story ring) plus a soft static glow, not `AchievementBadgeIcon`'s own rarity-ring/pulse treatment.** That treatment (`RARITY_RING` + a pulsing `box-shadow` animation) is right for a badge-sized icon but read as a flat "neon blink" at avatar scale — a deliberate product call, not a technical limitation, made after trying the badge-icon treatment directly on the avatar first. The ring is built as two layers: an absolutely-positioned `inset-0` div carrying the spinning gradient (`--animate-avatar-ring-spin`, a dedicated token in `packages/design-system/tokens.css`, separate from the badge `--animate-badge-*` tokens and included in the same `prefers-reduced-motion: reduce` opt-out) plus a static `box-shadow` glow in the same accent color, sitting _behind_ the actual avatar image. The gap that reveals the ring is real padding (`p-1.5`) on the outer wrapper, not a `ring-*` box-shadow utility on the avatar itself — a box-shadow ring paints in the same space as a box-shadow glow on the layer behind it, so the first version of this used `ring-4 ring-background` and the glow/gradient was invisible except for a flash during initial paint before the box-shadow settled. Real layout space (padding) doesn't have that overlap problem.
