# challenges

## Purpose

A promotional, time-boxed layer on top of the achievement engine (spec 36–37): admins run a named, bannered "challenge" ("Post 3 looks this week and get 100 likes") with a fixed start and end date; any user who meets its conditions inside that window earns the linked badge and its XP, exactly the way any other achievement does. This module owns the presentation wrapper and its admin/public reads and writes only — it never evaluates conditions itself.

## Structure

- `challenge.schemas.ts` — `createChallengeSchema`/`updateChallengeSchema`, built by spreading `badgeCoreFields` (minus `assignmentLimit`, which a challenge never accepts — see rationale) from `../badges` and `achievementConditionSchema` from `../achievements`, plus the challenge's own copy fields (`challengeName`, `challengeDescription`, `bannerImageUrl`) and a required (not optional) `activeFrom`/`activeUntil` pair, since a challenge is time-boxed by definition. `.strict()` on both, `.refine()` for "must end after it starts."
- `challenge.types.ts` — `ChallengeAdminRecord` (the full shape the admin list/form needs), `PublicChallengeView` (the promotional-page shape: status, dates, badge preview, and — only for a signed-in viewer — completion state and progress), `ChallengeStatus`.
- `challenge.utils.ts` — `computeChallengeStatus`, the one pure function here (`UPCOMING`/`OPEN`/`ENDED` from `activeFrom`/`activeUntil`/`now`). Unit tests live here.
- `challenge.repository.ts` — Prisma queries only. `createChallengeWithAchievementAndBadge`/`updateChallengeWithAchievementAndBadge` write `Badge`, `Achievement`, and `Challenge` together (a triple-nested `create`, or a three-statement transaction for updates) — see rationale for why the relation chain runs `Challenge → Achievement → Badge`, not `Challenge → Badge`. `listActiveChallenges`/`findActiveChallengeById` (both filtered to `Challenge.isActive` and `Badge.isActive`), `listAllChallengesAdmin` (everything, for the admin list).
- `challenge.service.ts` — `listActiveChallengesForViewer`/`findActiveChallengeForViewer` (the public reads — load the challenge(s), then, only if a `viewerId` is present, batch-fetch completion state and per-condition progress and fold it in), plus thin pass-throughs for the admin CRUD (`listAllChallengesAdmin`, `createChallenge`, `updateChallenge`).
- `challenge.controller.ts` / `challenge.routes.ts` — `GET /challenges` and `GET /challenges/:challengeId` (`optionalAuth`, public), `GET /challenges/admin`, `POST /challenges`, `PATCH /challenges/:challengeId` (`requireRole(ADMIN)`).

## Funnel

**User-facing:** a signed-in user (creator account, matching the rest of this domain — see `xp`/`badges`' READMEs) opens **Challenges** from the dashboard sidebar, sees every currently-running or upcoming challenge with its banner, XP reward, dates, and — for one they haven't finished — a live progress readout per condition. Meeting the conditions doesn't require visiting this page at all: the badge unlocks automatically through the normal achievement pipeline the moment the underlying event fires, exactly like any other badge, and the toast/real-time unlock moment (`achievements/README.md`) fires the same way.

**Technical:** this module never touches evaluation. `POST /challenges` and `PATCH /challenges/:challengeId` write an ordinary `Badge` + `Achievement` pair (with a required seasonal window) plus a `Challenge` row that only carries presentation fields and a pointer to the achievement. The moment those rows exist, `achievements`' own event-driven engine (`achievement.events.ts`) picks the new achievement up exactly like it does every other one — nothing here subscribes to domain events or calls `badgeRepository.awardBadge`. `GET /challenges` reads `challengeRepository.listActiveChallenges()`, then — only for an authenticated request — calls `achievementService.listProgressForUser(viewerId)` once (not once per challenge) and `badgeRepository.findOwnedBadgeIds` once, and folds both into each entry by matching on `achievementId`/`badgeId`.

## Non-obvious rationale

**The relation chain is `Challenge → Achievement → Badge`, not `Challenge → Badge` (with achievement reached through the badge).** The first design pointed `Challenge.badgeId` straight at `Badge`, reaching the achievement via `badge.achievement` — but `listActiveChallenges` needs to sort by `achievement.activeUntil` (soonest-ending first), and Prisma's `orderBy` only supports ordering by a field on a relation one hop away, not two. Pointing `Challenge.achievementId` directly at `Achievement` instead (and reaching the badge via `achievement.badge`, which already existed) makes the sort a one-hop `orderBy: { achievement: { activeUntil: ... } }` — a real constraint that shaped the schema, not an arbitrary choice. This was caught by `tsc`, not assumed: the first version type-checked against a stale generated client and only broke once the client was regenerated against the corrected schema.

**A challenge never accepts `assignmentLimit`, and the schema says so instead of silently ignoring it.** `badgeCoreFields` (shared with `../badges`' own admin form) includes `assignmentLimit`, but a challenge is meant to be completable by every user who meets its conditions inside the window, not a "first N winners" prize — that competitive shape is a different, not-yet-built feature (the plan's "creator competitions," which pairs a challenge with a leaderboard). Rather than accepting an `assignmentLimit` value from the request and quietly hard-coding it to `null` regardless of what was sent, `challenge.schemas.ts` destructures it out of the spread fields entirely — the field genuinely isn't part of this API's contract, not a value that's accepted and then thrown away.

**The badge's own name/description and the challenge's promotional name/description are two separate pairs of fields, not one shared pair.** `POST /challenges` takes both `name`/`description` (the badge's catalog identity — what shows in a user's badge collection once earned) and `challengeName`/`challengeDescription` (the promotional copy on the challenges page — "August Style Sprint," say, versus the badge's own "Style Sprint" catalog name). They're allowed to read identically if an admin wants that, but forcing them to always match would mean giving up the ability to write challenge-page copy that reads differently from a permanent catalog description, which is exactly the kind of thing a promotional page needs.

**Progress and completion state are computed in one batched call across every listed challenge, not once per challenge.** `loadViewerContext` calls `achievementService.listProgressForUser` and `badgeRepository.findOwnedBadgeIds` exactly once for the whole list (or the single challenge, for the detail read) and then does an in-memory `Map`/`Set` lookup per entry — the same "batch once, look up per item" shape `achievement.service.ts`'s own `buildMetricSnapshot` already uses for a single user's achievements, applied here across a list of challenges instead of a list of achievements.

**An `UPCOMING` or `ENDED` challenge shows `conditions: null` for a signed-in viewer, not stale or zeroed progress.** `achievementRepository.findEligibleAchievements` (see `achievements/README.md`) already excludes an achievement outside its own window from evaluation entirely, so `listProgressForUser` simply never returns an entry for one — this module doesn't add any extra filtering to get that result, it falls out of the seasonal-window work for free. `isCompleted` stays meaningful in every status, though: whether a user finished the challenge before it ended is worth showing even after the window closes.
