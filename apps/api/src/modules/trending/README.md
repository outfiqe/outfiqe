# Trending — product trend scoring

## Purpose

Computes which approved products are "trending" for the homepage rail (`GET /products/trending`, unchanged route/shape) from real activity — purchases, cart adds, saves, creator tags, tag clicks — instead of the old `orderBy: reviewedAt desc` placeholder. Runs entirely on infrastructure this codebase already has: the same interval-job scheduler running the commission/payment sweeps, and the same Redis cache-aside pattern backing the explore feed's trending snapshot.

## Structure

- `trending.constants.ts` — job intervals, signal weights, decay/momentum/baseline tuning constants, diversity/rotation limits. Plain module constants, no admin UI to edit them, same as `CommissionTier`'s own tier constants started out.
- `trending.types.ts` — `MetricBucket`, `ProductTrendMeta`, `ProductScoreBreakdown`, `TrendDebugSnapshot`.
- `trending.utils.ts` — the entire scoring pipeline as pure functions (decay weight, log1p-weighted bucket activity, windowed decayed-activity sums, baseline computation, `scoreProduct`, diversity, weighted rotation). No DB or Redis access in this file on purpose — every function here is a plain data transform, unit-testable without a database.
- `trending.repository.ts` — the five per-signal aggregation upserts (raw SQL, `INSERT ... ON CONFLICT DO UPDATE`), retention delete, and the two read queries the scoring pass needs (`listRecentMetricBuckets`, `listActiveProductMeta`).
- `trending.service.ts` — orchestration: the two scheduled jobs (`runAggregation`, `runScoring`), the cache-read-with-fallback used by the homepage rail `GET /products/trending` (`getTrendingProductIds`), the session-snapshot cursor pagination used by the paginated `GET /products?sort=trending` browse (`listTrendingProductIds`), and the admin debug endpoint (`getDebugSnapshot`).
- `trending.schemas.ts` / `trending.controller.ts` / `trending.routes.ts` — the two routes this module owns directly: `GET /api/admin/trending/products` (top-N ranked candidates, for the admin debug page's overview list) and `GET /api/admin/trending/products/:productId/debug` (one product's full breakdown).
- `trending.utils.test.ts` — unit tests for the pure scoring pipeline (`bucketActivity`, baselines, `pickBaseline`, `scoreProduct`'s cold-start/zero-baseline/momentum-cap/freshness-boundary edge cases, `applyDiversity`'s brand-grouping wrapper).
- `trending.integration.test.ts` — real-DB/Redis tests for the aggregation boundary fix, the read-time revalidation guarantee, pagination cursor resume, and ranking determinism/diversity, described below.

## Funnel

**User-facing:** nothing changes about what a shopper sees — the homepage "Trending" rail is still `GET /products/trending`. What's different is _why_ a product is there: real purchases/cart-adds/saves/creator-tags/tag-clicks from the last few hours and days, weighted toward genuine spikes rather than raw volume, refreshed roughly every 30 minutes.

**Technical:**

1. Every checkout, cart add, wishlist save, look-tag, and tag click already writes to its own table for its own reason (`OrderItem`, `CartItem`, `SavedProduct`, `CreatorLookProduct`, `CreatorLookTagClick`) — this module adds nothing to those write paths.
2. `trending-aggregation` (every 15 min, `startIntervalScheduler`) recomputes the current, still-open hour's `ProductTrendMetric` row per product per signal from scratch (`recompute`, not `increment` — see rationale below), then deletes buckets older than 14 days.
3. `trending-scoring` (every 30 min) reads the trailing 14 days of buckets once, computes decayed activity / velocity / baseline lift / momentum / freshness / score per product (`scoreProduct` in `trending.utils.ts`), takes the top 50, applies a max-2-per-brand diversity pass, applies a seeded weighted-rotation shuffle within score tie-bands, and writes the ranked list to `cache:product-trending:global` (TTL 40 min).
4. `productService.listTrending()` (`../products/product.service.ts`) asks `trendingService.getTrendingProductIds()` for the ranked IDs, then hydrates them via `productRepository.listApprovedByIds()` (order-preserving) and reuses this session's real `withSalesStats`/`toPublicProduct` pipeline for the card fields.
5. If the cache is cold (miss or expired past its grace window), `getTrendingProductIds` falls back to scoring synchronously from `ProductTrendMetric` directly — cheap, because the expensive part (scanning `order_items`/`cart_items`/etc.) already happened in the aggregation job; this mirrors `buildTrendingSnapshot`'s existing fail-open fallback in `creator-looks`.

## Non-obvious rationale

**No write-per-view, because there's no "view" signal.** The classic reason this kind of system reaches for Redis hot-counters is to avoid a database write on every raw pageview. None of the five v1 signals are raw high-frequency pings — they're all already-persisted, already-necessary business events. Raw view/impression tracking is deliberately not built here; it's the one signal that actually would need a write-buffering layer, and it's cut from v1 rather than half-built.

**Recompute-and-overwrite, not increment.** Each aggregation run recomputes the entire current hour bucket from its source table, not `SET col = col + delta`. This makes every run idempotent — a double-run from a scheduler hiccup just writes the same correct number twice, never a doubled one. No dedup table, no idempotency key needed.

**Each aggregation cycle finalizes the previous hour's bucket too, bounded to exactly that hour, not just the open one.** The five upsert queries used to be `WHERE created_at >= bucketStart` with no upper bound, and `trending-aggregation` fires on a plain `setInterval(15 min)` phased off process boot time, not aligned to `:00/:15/:30/:45`. So whichever run happened to be the last one before an hour rolled over sealed that hour's row at whatever point it fired — anywhere up to 15 minutes before the boundary — and the next run only ever looked at `created_at >= <the new hour's start>`. Anything that happened in that gap (a purchase, a cart add, a save, a creator tag, a tag click) belonged to neither bucket and was silently dropped from every trending score, permanently, every single hour. Reproduced as a real test (`trending.integration.test.ts`'s "finalizes an hour's bucket with activity that arrives after aggregation has already moved on to the next hour" and its purchase-units sibling) before the fix: two saves on the same product an hour apart, the second landing after the first hour's only aggregation pass — only 1 of 2 ever got counted, and a purchase logged with `oi.created_at` inside the already-sealed hour never got counted at all. Fixed by bounding every upsert to `created_at >= bucketStart AND created_at < bucketStart + 1h` (so a bucket only ever holds its own hour's activity, never spilling into a neighbor) and having `upsertHourlyMetrics` recompute both the current, still-open hour and the immediately preceding one on every cycle. Whatever the last live update to an hour missed, the very next cycle's pass over that now-closed hour — bounded, so it can't double up with the new hour — picks up in full. No change to the scheduler itself was needed: this closes the gap regardless of how the 15-minute interval happens to be phased against the clock. `deleteMetricsOlderThan`'s 14-day retention cutoff never conflicts with this: the bucket a finalization pass touches is at most ~2 hours old.

**`candidates.sort` breaks ties on `productId`, and `listRecentMetricBuckets` orders its own read, for the same reason `../creator-looks` had to fix this for its own post/creator momentum sort.** `ProductTrendMetric` rows were read with no `orderBy`, and the final ranking sort was `candidates.sort((a, b) => b.score - a.score)` with no tiebreaker — so two products with an identical score (common; a product with sparse activity often ties another at the same decayed-activity value) sorted in whatever order Postgres happened to return that scan, which is undefined without an `ORDER BY`. Reproduced as a real test (`trending.integration.test.ts`'s "breaks equally-scored candidates by productId instead of leaving the order to chance"): two products seeded with byte-for-byte identical bucket activity, with the lexically-larger id's row written to the table first — pre-fix, that larger id came back ranked first; post-fix, the smaller id always does, regardless of write order. Fixed by adding `orderBy: [{ productId: "asc" }, { bucketStart: "asc" }]` to `listRecentMetricBuckets` and a `|| a.productId.localeCompare(b.productId)` tiebreaker to the ranking sort, so two tied candidates always resolve to the same order across requests instead of visibly reshuffling.

**"Category" baseline uses `Product.productTypeId`, not the `categories` relation.** A product's `categories` are many-to-many (`Product.categories: Category[]`), which has no single well-defined "the category" to group a baseline by. The garment type (`Product.productTypeId` — see `../product-types`) is the single-valued classification this codebase uses elsewhere for exactly this kind of grouping (e.g. `SizeOption` is keyed by it), so the baseline fallback hierarchy is product → type → global, not product → category → global as worded in the original design brief. The baselines are keyed by `productTypeId` (opaque grouping key — the values never leave this module).

**Scoring runs in application code over pre-aggregated rows, not as one large SQL query.** `ProductTrendMetric` rows are fetched with a single bounded Prisma query (`listRecentMetricBuckets`), then every decay/velocity/baseline/momentum calculation happens in plain TypeScript (`trending.utils.ts`). This is the one place this module doesn't reach for raw SQL despite the "computed-value ordering" convention elsewhere in this codebase (see `creator-looks/README.md`) — the formula has too many interdependent steps (two time windows, a three-level baseline fallback, a capped geometric mean) to stay readable as SQL, and keeping it in TypeScript makes every step directly unit-testable against the worked examples from the design doc, which SQL wouldn't be.

**The candidate pool, diversity pass, and rotation are recomputed fresh every scoring run, not incrementally.** `applyDiversity` (max 2 per brand) and `applyWeightedRotation` (seeded weighted shuffle within a 10% score tie-band, keyed by the scoring cycle's timestamp) both run once per `runScoring()` call over the full sorted candidate list — same shape as the diverse-pick logic used for the creator-looks featured-look rail. The rotation seed is derived from `Math.floor(now / SCORING_INTERVAL_MS)`, not per-request, so the order is stable for one 30-minute cycle and only reshuffles when the next scoring run lands.

**Cold-start fallback.** If `trendingService.getTrendingProductIds()` returns an empty list — no product anywhere has scored activity yet, which is the real state of a fresh environment before any orders/carts/saves exist — `productService.listTrending()` falls back to the old `orderBy: reviewedAt desc` query (`productRepository.listTrending()`, kept around for exactly this). This is a deliberate bootstrap path, not dead code: a brand-new deployment shouldn't show an empty trending rail for its first two weeks of data collection.

**A session's page cursor resumes at the same depth in a freshly-built list, rather than rewinding to page one, if its snapshot cache expires mid-scroll.** `cache:product-trending-snapshot:<sessionId>` (`PRODUCT_TRENDING_SNAPSHOT`, 20 min, refreshed on every page read) holds one browsing session's paginated id list. A session idle long enough for that key to actually expire used to lose its place entirely: `resolveTrendingSnapshotSource` minted a new session id _and_ reset `offset` to `0` on a miss, so the next `sort=trending` page load silently jumped back to page one instead of continuing. Reproduced as a real test (`trending.integration.test.ts`'s "resumes from where it left off instead of rewinding to page one when the session snapshot expires mid-scroll"): fetch page one, delete the session's Redis key to simulate the TTL lapsing, fetch "page two" with the original cursor — got page one's product again, pre-fix. Fixed by reusing the cursor's own `sessionId` (re-populating the same key instead of minting a new one) and clamping the cursor's `offset` into the freshly-built list instead of discarding it. The freshly-built list can still reorder slightly if real activity happened in between — an inherent property of any live-ranked feed, not something a pagination fix can or should paper over — but the common case (nothing changed) resumes exactly where the browser left off.

**Cached candidate-id snapshots are re-validated at read time, not trusted blindly.** Both `getTrendingProductIds` (rail) and `listTrendingProductIds` (paginated browse) return bare ids straight out of a cache that can be up to 40 minutes (score cache) or 20 minutes (session snapshot) stale. Unlike `../creator-looks`' `hydrateFeedPosts` — which only checked the creator's `accountStatus` and let a soft-deleted look stay visible until its cache expired — this module's only hydrate path back to a client is `productRepository.listApprovedByIds` (`productService.listTrending`/`listPublic`), and it already re-filters `status: APPROVED`, `deletedAt: null`, `brand.accountStatus: ACTIVE` on every call, order-preserving. Verified rather than assumed: `trending.integration.test.ts`'s "drops a product from the trending rail once it's deleted, even while the score cache is warm" test scores and caches a product, soft-deletes it, and confirms a second `GET /api/products/trending` with the warm cache no longer returns it.

**`listTopTrendingProducts` depends on `products`, the reverse of the usual direction.** Every other call in this module goes `products → trending` (`productService.listTrending`/`listPublic` ask `trendingService` for ranked IDs). The admin overview list needs the opposite — real candidate scores hydrated with product name/brand/image for display — so `trending.service.ts` imports `productRepository.listApprovedByIds` directly (already order-preserving and approval-filtered, built for this exact "IDs in, display-ready products out" shape). Not circular: `product.repository.ts` has no dependency on `trending` at all, only `product.service.ts` does.

**The homepage rail and the paginated browse rank from the same candidates but never share a page shape.** `getTrendingProductIds` (rail) applies `applyDiversity` + `applyWeightedRotation` to a short, capped list — right for 5–30 cards that need brand variety and shouldn't reshuffle on every request. `listTrendingProductIds` (paginated `sort=trending`) skips both and paginates the full score-sorted candidate list instead — a "see more" page is expected to show the objectively highest-scoring items in order, not a diversity-shuffled sample, and a user paging through it needs stable results across requests within one session, which is what the cached per-session snapshot (`{ sessionId, offset }` cursor, mirroring `creator-looks`' own trending-feed pagination) provides instead of rotation.

**`Product.wornByCount`, `PublicProduct.creatorBuyerCount`/`.unitsSold`, and `ProductTrendMetric.creatorTags`/`.purchaseUnits` are three different things, not duplicated numbers.** `wornByCount` (tag-based, shown as "seen on creators") and `creatorBuyerCount`/`unitsSold` (purchase-based, shown on the product card) are both display metrics computed elsewhere — see `../products/README.md`. `ProductTrendMetric`'s own `creatorTags`/`purchaseUnits` columns are raw per-hour counts feeding the trending score, sourced from the same underlying tables but never read from or written to those display metrics, and vice versa.
