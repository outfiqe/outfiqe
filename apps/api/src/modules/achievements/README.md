# achievements

## Purpose

The achievement rule engine: evaluates a user's live platform stats against admin-configured conditions (spec 16), and — when every condition is met — awards the linked `Badge` (`UserBadge`) and its XP reward. Owns evaluation only; the badge catalog itself (creation, rarity, design, collection reads) belongs to `badges` (a later chunk). Also owns the dynamic-badge re-check job (Phase 2 item 18) — a periodic sweep that can _revoke_ eligibility for a badge whose condition is no longer met, something the normal event-triggered path never needs to do since every other metric only ever climbs.

## Structure

- `achievement.constants.ts` — `ACHIEVEMENT_METRIC` (the closed set of metrics the engine currently understands, including seven `*_rank` metrics — see rationale below), `RANK_METRIC_CATEGORY` (the `*_rank` metrics' reverse lookup into `CreatorLeaderboardCategory`, used only by the dynamic-recheck candidate search), `CONDITION_OPERATOR` (`gte`/`gt`/`eq`/`lte`/`lt`), `RANK_CANDIDATE_OPERATORS` (`lte`/`lt` — the only operators a "top N" rank condition can search candidates for), `CONDITION_NODE_TYPE` (`AND`/`OR`/`NOT`, spec 17's generalized compound rules — see rationale below), `ACHIEVEMENT_XP_SOURCE`, `UNRANKED_METRIC_VALUE`/`TOP_RANK_POSITION_OFFSET` (rank-metric fetcher constants), `DYNAMIC_BADGE_RECHECK_INTERVAL_MS`.
- `achievement.schemas.ts` — `achievementConditionSchema` (one leaf: `{ metric, operator, value }` — still the only shape the admin badge-creation form at `../badges` produces) and `achievementConditionNodeSchema`, a recursive `z.lazy()` union of a leaf with `{ type: "AND" | "OR", conditions: [...] }`/`{ type: "NOT", condition: ... }` group nodes. `achievementRequirementConfigSchema` (`{ conditions: [...] }`, the Zod validator for `Achievement.requirementConfig`'s JSON shape) types its array as `achievementConditionNodeSchema[]`, so a stored requirementConfig can freely mix bare leaves and nested groups at the top level — the untyped-JSON-boundary validation CLAUDE.md's data-model conventions call for, not a blind cast.
- `achievement.types.ts` — `EligibleAchievementRecord` (a parsed, ready-to-evaluate achievement — `conditions: AchievementConditionNode[]`, plus `badgeName`/`badgeIcon`/`sponsorBrandName` carried along purely so `unlockAchievement` can publish a complete unlock event without a second query — see `../badges`' README for why the sponsor name has to be threaded in here rather than looked up from that module), `MetricSnapshot`, `AchievementProgressView` (`conditions: AchievementConditionProgress[]`, always the _flattened leaves_ of whatever tree the achievement stored — see rationale below).
- `achievement.utils.ts` — pure functions only, no DB access, unit tests live here: `isConditionMet`/`currentValueForCondition` (leaf evaluation), `isConditionLeaf` (the leaf/group type guard — a node is a leaf iff it has no `type` key), `evaluateConditionNode` (the recursive AND/OR/NOT evaluator), `areAllConditionsMet` (the top-level entry point — treats the `conditions` array itself as an implicit AND, unchanged signature from before spec 17's generalization), `collectLeafConditions` (recursively flattens a tree into its leaves, for metric-snapshot building and progress display).
- `achievement.repository.ts` — Prisma queries only: `findEligibleAchievements` (active, non-admin-award achievements the user hasn't already unlocked, and — spec 35 seasonal badges — currently inside their `activeFrom`/`activeUntil` window, if one is set), `findActiveDynamicAchievements` (the dynamic-recheck job's equivalent query: same active/window filter, but scoped to `badge.isDynamic: true` instead of "not already unlocked" — a dynamic achievement is evaluated for every candidate regardless of whether they already hold the badge, see rationale below), and one query per counter metric (`countActiveLooks`, `sumLikesReceived`, `countCommentsMade`, `countPurchases`, `countSalesGenerated`, `sumViewsReceived`). Awarding the badge itself is `../badges`' `badgeRepository.awardBadge`, called directly (not via `badgeService`) — see that module's README for why.
- `achievement.service.ts` — `evaluateForUser` (the engine entry point: load eligible achievements → build one batched metric snapshot → award whichever now pass), `listProgressForUser` (the read-only spec 18 equivalent, same snapshot logic, no awarding), and `recheckDynamicBadges` (the periodic job entry point — see rationale below for its candidate-search strategy).
- `achievement.events.ts` — `registerAchievementEventConsumers()`: an independent second consumer group (`achievement-check`) on the same domain event streams `xp.events.ts` already subscribes to — Redis Streams supports multiple independent consumer groups per stream, so this doesn't interfere with or depend on the `xp` module's own consumers.
- `achievement.socket.ts` — `registerAchievementSocketEventConsumer()`: a third, independent `socket-broadcast` consumer group on `DomainEvents.ACHIEVEMENT_UNLOCKED` (published by `unlockAchievement` itself) that emits `SOCKET_EVENTS.ACHIEVEMENT_UNLOCKED` to the unlocking user's own room. Same shape as `xp/xp.socket.ts` and `leaderboard.socket.ts`'s event consumer.
- `achievement.schemas.ts` (query) / `achievement.controller.ts` / `achievement.routes.ts` — `GET /api/achievements/me/progress` (spec 18), `requireAuth`-only.

## Funnel

**Technical:** a triggering domain event (`LOOK_CREATED`, `LOOK_LIKED`, `LOOK_COMMENTED`, `PRODUCT_PURCHASED`, `SALE_GENERATED`, `LOOK_VIEWED`) fires → `achievement.events.ts` calls `evaluateForUser(relevantUserId)` → the service loads every active, not-yet-unlocked achievement for that user, computes the union of metrics their conditions reference, fetches each exactly once (batched, in parallel), and checks every eligible achievement against that one snapshot. Anything that now passes calls `badgeRepository.awardBadge` (`../badges`) for the `UserBadge` row — race-safe against `assignmentLimit` even though eligible achievements are never `ADMIN_AWARD`-typed, since a rule-based badge can still carry an `assignmentLimit` — then publishes `DomainEvents.ACHIEVEMENT_UNLOCKED` (picked up by `achievement.socket.ts` for the real-time toast) and, if the award succeeded and the badge carries an XP reward, an `ACHIEVEMENT_UNLOCKED` (the `XpActivityType`, a different enum in a different namespace from the domain event of the same name) transaction via `xpService.grantFixedXp` — which can itself publish a further `LEVEL_UP` domain event if the grant crosses a level boundary (see `xp/README.md` for why this bypasses the normal config-gated `awardXp` path). An award that comes back `awarded: false` (a badge deactivated or capped between the eligibility query and the write — a narrow window, not the normal case) is logged and skipped rather than treated as an error, and no unlock event is published; the achievement stays eligible and will be picked up by `evaluateForUser`'s query again if state changes.

**User-facing:** the unlock/level-up toast (`achievement.socket.ts`/`xp/xp.socket.ts` → `apps/web`'s `useGamificationSocket`) — everything else here is still backend-only. A user's badge collection becomes visible once the `badges` module builds the collection/profile-showcase surface on top of `UserBadge`.

**Dynamic badges, technical:** every `DYNAMIC_BADGE_RECHECK_INTERVAL_MS` (15 minutes, matching `creator-leaderboard`'s own recompute cadence, since rank metrics are only as fresh as that module's last write), `recheckDynamicBadges` loads every active `Badge{isDynamic: true}`'s achievement, and for each one builds a bounded candidate set: everyone who currently holds the badge (`badgeRepository.listOwnersOfBadge`, so a holder can lose it) unioned with the top-N members of any leaderboard category a `*_rank` condition in that achievement references (`creatorLeaderboardRepository.topN`, so a brand-new qualifier can be found at all). Every candidate gets the exact same single-user metric-snapshot-and-evaluate pass `evaluateForUser` uses, just reused for one achievement instead of a user's whole eligible set. A non-owner who now qualifies goes through `unlockAchievement` — the identical award-badge-then-XP-then-event path the real-time engine uses, so a dynamic badge earned this way looks no different to the rest of the system than one earned through an event. An owner who now fails calls `badgeRepository.setDynamicEligibility(..., false)`; one who was failing and now passes again calls it with `true`. Nothing is ever deleted or re-awarded.

## Non-obvious rationale

**Full re-evaluation per triggering event, not a metric-to-achievement dependency graph.** On every qualifying event, `evaluateForUser` re-checks _all_ of a user's still-locked, active achievements — not just the one whose metric the triggering event obviously touches. With a 14-badge catalog and 6 metrics this is cheap, and it sidesteps a real correctness gap a narrower "only re-check achievements that use this event's metric" design would have: a compound achievement's last-needed condition can be satisfied by a _different_ event than the one that finally pushes it over the line (see the `level` note below). Revisit with a proper dependency graph only if the catalog grows enough for this to matter.

**Compound (multi-condition) achievements are eventually consistent, not live.** `Fashion Mentor` (`comments_made >= 100 AND level >= 5`) only gets re-checked on events that are wired as achievement triggers — currently `LOOK_CREATED`/`LOOK_LIKED`/`LOOK_COMMENTED`/`PRODUCT_PURCHASED`/`SALE_GENERATED`. Every metric a seeded achievement uses (including `level`, which changes as a side effect of _any_ XP-earning event) is read fresh from the DB at check time, so this is never _wrong_ — but if a user's final qualifying condition is satisfied by an event nothing subscribes to for achievement purposes (there currently isn't one, since XP-earning events and achievement-trigger events are the same set), the unlock would simply wait for the next qualifying event instead of firing instantly. Adding a new metric later means adding whichever event(s) can move it to `achievement.events.ts` too — it doesn't happen automatically.

**`ADMIN_AWARD`-type achievements are excluded at the query level, not filtered after the fact.** `findEligibleAchievements` never returns them — `requirementType: { not: ADMIN_AWARD }` — so `Outfiqe OG`'s empty `{ conditions: [] }` requirementConfig (which would otherwise fail `achievementRequirementConfigSchema`'s `.min(1)`) never reaches the parser. Manual-only badges are awarded through the admin chunk's own path, never by this engine.

**Eligibility (not "is this badge still valid") is the only re-unlock guard, and that's deliberate.** "Not yet unlocked" is checked via `badge.userBadges.none({ userId })` — a badge the user already has, even one an admin has since _removed_ (`UserBadge.removedAt` set, spec 33's "reversible, always logged" — the row is never deleted), is never re-evaluated or re-awarded. The engine only ever awards a badge once per user, full stop; re-instating a manually-removed badge is an admin action, not something a future qualifying event should silently undo.

**`purchases_count`/`sales_count` don't reverse on cancellation or void**, matching the same accepted simplification already made for `PRODUCT_PURCHASED`/`SALE_GENERATED` XP (see `xp/README.md`) — a cancelled COD order or a voided commission still counts toward these metrics once it's happened. Consistent with the rest of this build's "speculative, not retroactively reversed" XP philosophy, not an oversight.

**`unlockAchievement` imports `badgeRepository`, never `badgeService`.** `badges` already depends on this module (`badgeService.listCollectionForUser` reads `achievementService.listProgressForUser` for locked-badge progress) — importing `badgeService` back from here would create a circular service dependency, a first for this codebase. Reaching one level deeper into `../badges`' repository instead keeps the dependency one-directional; see that module's README ("`awardBadge` lives in `badge.repository.ts`...") for the full reasoning.

**Seasonal badges (spec 35) reuse the existing `Achievement.isActive` flag's semantics — a window is just a time-scoped way of getting to the same "don't evaluate this" state, not a second gate.** `activeFrom`/`activeUntil` are both nullable `DateTime` columns on `Achievement`; `findEligibleAchievements` filters `AND: [{ OR: [{ activeFrom: null }, { activeFrom: { lte: now } }] }, { OR: [{ activeUntil: null }, { activeUntil: { gte: now } }] }]` — a bare top-level `OR` key works for one "field is null OR in range" group, but two independent OR-groups (one per boundary) need to be wrapped in an explicit `AND` array since a single JS object literal can only have one `OR` key. A closed-window achievement stops being evaluated automatically once `activeUntil` passes — no scheduled job needed, no `isActive` flip required — matching spec 35's "the achievement becomes inactive, the badge stays" exactly: already-awarded `UserBadge` rows are untouched, only future eligibility is affected. An admin can still additionally set `Achievement.isActive: false` by hand (chunk 12/14's admin form exposes this as "achievement active", separate from the badge's own `isActive`) to pause evaluation outside of any window — the two mechanisms compose via a plain `AND` in the query, they don't conflict.

**Seasonal window fields live only on the rule-based branch of the badge admin schema, never on `ADMIN_AWARD` badges.** An admin-award achievement is never read by `findEligibleAchievements` in the first place (`requirementType: { not: ADMIN_AWARD }`), so a window on one would be silently inert — `badge.repository.ts`'s `seasonalWindowFor` hard-codes `{ activeFrom: null, activeUntil: null }` for that branch rather than accepting (and ignoring) values a form might send, so the stored data can never claim a window that does nothing.

**Compound conditions (spec 17) generalize to an arbitrary AND/OR/NOT tree without a migration, because the _shape that was already being stored_ is the degenerate case of the new shape.** Before this chunk, `requirementConfig.conditions` was `AchievementCondition[]` — a flat array of leaves, implicitly AND'd together by `areAllConditionsMet`. The new `AchievementConditionNode[]` type keeps that exact same top-level array-is-an-AND contract; the only change is that an _element_ of the array can now be a `{ type: "OR" | "AND", conditions: [...] }` or `{ type: "NOT", condition: ... }` group instead of only ever a leaf. Every row written by MVP (chunk 6) or the admin form (chunk 12/14) — a flat array of leaves — parses against `achievementConditionNodeSchema` unchanged, since a leaf is a valid node. No backfill, no schema version field, no dual-parsing code path.

**`isConditionLeaf` discriminates on the _absence_ of a `type` key, not a `"leaf"` tag.** A leaf condition (`{ metric, operator, value }`) never had a `type` field before this chunk and still doesn't — adding one just to make the discriminant explicit would mean every already-stored row needs rewriting to add it. Checking `!("type" in node)` gets the same discrimination for free from the shape that was already there.

**Progress display (`AchievementProgressView.conditions`) flattens the whole tree to its leaves — it does not attempt to render the AND/OR/NOT structure.** `collectLeafConditions` walks every branch (including inside a `NOT`) and returns every leaf it finds, each still paired with its own `currentValue` via the existing per-leaf `metric`/`operator`/`value` shape. This is a deliberate simplification, not an oversight: spec 18's locked-badge progress bars are inherently a "here's how close you are on each front" UI, and a `NOT`-negated or `OR`-branched leaf doesn't have a meaningfully different progress-bar meaning than a plain one — showing "likes: 250/1000" is still useful context even when it's one branch of an `OR` the user could clear a different way. Rendering the boolean structure itself (which branches are satisfied, whether an `OR` only needs one more) is a real UI project of its own, not built here — this chunk is the engine capability, not a new progress-bar design.

**No admin UI ships in this chunk for _authoring_ a nested tree.** The badge admin form (`../badges`, `apps/admin`) still only ever submits a flat array of leaves — `createBadgeSchema`/`updateBadgeSchema`'s `conditions` field type didn't change. A compound achievement (this chunk's own integration test seeds one directly via Prisma) can only be created by a script or a future admin surface today. This is deliberately scoped the same way spec 35's seasonal-window engine work landed before its own admin fields did in chunk 14 — a natural admin UI for this is the kind of thing chunk 16 (Challenges, which reuses this same expression tree) is positioned to need first, not invented speculatively here.

**Rank metrics (`top_xp_rank`, `top_creator_rank`, `most_likes_rank`, `most_engaged_rank`, `top_seller_rank`, `rising_creator_rank`, `most_achievements_rank`) are one metric per `../creator-leaderboard` category, not a single "rank" metric that also takes a category parameter.** Every existing metric is a bare `AchievementMetric` string with no side parameters — `achievementConditionSchema` has no field for "which leaderboard" a rank should be read from, and adding one would mean every non-rank metric now carries a meaningless, always-empty parameter too. Seven flat metrics fit the existing `{ metric, operator, value }` leaf shape with zero schema changes anywhere (Zod validation, the admin condition editor, the progress-flattening logic) — the cost is a fixed, closed list instead of an open one, which is fine since `creator-leaderboard`'s own category set is itself fixed and rarely changes.

**A rank is read as 1-indexed and an unranked user reads as `UNRANKED_METRIC_VALUE` (`Number.MAX_SAFE_INTEGER`), never `0` or `Infinity`.** `creatorLeaderboardRepository.rankOf` returns Redis's own 0-indexed `ZREVRANK` (or `null` if the user isn't a ZSET member at all). Adding `TOP_RANK_POSITION_OFFSET` (`1`) before handing it to the comparator means an admin-authored `top_xp_rank <= 10` reads exactly like "top 10 users" the way a person would say it, not "top 11, 0-indexed." Mapping `null` to a real (very large) number rather than leaving the metric out of the snapshot matters because `currentValueForCondition`'s missing-metric fallback is `0` — if an unranked user's rank metric silently defaulted to `0`, they'd satisfy _every_ `<=` rank condition in existence, the opposite of "not ranked."

**The dynamic-recheck candidate set is deliberately bounded, not "every user" — a stated scope cut, not an oversight.** Re-evaluating every achievement against every platform user on a schedule would be exactly the unbounded full-table sweep CLAUDE.md's Database Queries section warns against. Because the _only_ metrics that can ever newly qualify a user who wasn't eligible before are the rank metrics (every counter metric is monotonic — see the next note — so a counter-only dynamic achievement can only ever be satisfied by someone who was already going to be caught by the normal event-triggered path), the candidate search only needs `topN(category, week, N)` for each `<=`/`<` rank condition present (current existing owners are always included too, so revocation is still checked for everyone who has the badge, regardless of which metrics their achievement uses). An achievement whose only conditions are non-rank counters and is marked `isDynamic` anyway still works correctly — its owners get re-checked and never fail (counters don't reverse) — it just never discovers a _new_ qualifier through this job, since the counter-based path for that is what event-triggered evaluation already does.

**`UserBadge.isDynamicallyEligible` is a second, engine-owned flag — deliberately kept separate from `isDisplayed`, which stays a pure user preference.** The obvious cheaper design would have been reusing `isDisplayed` itself for revocation (set it `false` when a dynamic badge stops qualifying). That breaks the moment a user manually hides _any_ badge for their own reasons: the engine can't tell "this is hidden because the user chose to hide it" from "this is hidden because the engine revoked it," so a requalifying dynamic badge would either silently override a real user choice (re-showing something they deliberately turned off) or never automatically come back at all (leaving a hidden badge stuck even after the user re-qualifies, indistinguishable from a manual hide). A separate boolean, defaulting `true` and touched only by `recheckDynamicBadges`, means the two concerns never collide: a dynamic badge's actual visibility is `isDisplayed && isDynamicallyEligible`, computed at read time in `../badges`' `listCollectionForUser`/`listFeaturedForUser`/`findTitleForUser`, and each half of that AND is owned by exactly one actor.

**`findActiveDynamicAchievements` doesn't exclude already-unlocked achievements the way `findEligibleAchievements` does.** The normal path's `badge.userBadges: { none: { userId } }` filter encodes "once unlocked, never re-evaluated" — permanent-unlock semantics that are exactly wrong for a dynamic badge, whose entire point is being re-evaluated after it's been unlocked. Dropping that filter and instead checking `badge.isDynamic: true` means the same achievement can be read by both queries without conflict: a non-dynamic badge only ever appears in `findEligibleAchievements`'s results (until someone unlocks it, then never again), and a dynamic one only ever appears in `findActiveDynamicAchievements`'s (an achievement can't sensibly be both, and nothing currently enforces that as a DB constraint — it's a convention the admin form doesn't yet violate because it doesn't expose picking both at once in a way that matters).

**Challenges (`../challenges`) explicitly can't be marked dynamic — `isDynamic` is destructured out of the fields that module reuses from `badgeCoreFields`, the same way it already excludes `assignmentLimit`.** A challenge badge is a time-boxed compound achievement that, once won, is meant to stay won for that challenge instance — re-checking it periodically and silently revoking it after the challenge window closes (or reawarding it to someone whose stats later regress and recover) would contradict spec 36–37's own "once you've completed a challenge, it's yours" framing. `challenge.repository.ts` hard-codes `isDynamic: false` on every challenge badge it creates, the same explicit style already used for `assignmentLimit: null` there.
