# badges

## Purpose

The badge catalog and a user's collection of it: what badges exist, which ones a given user has collected, their visibility/featured/title state, and the public profile showcase. Owns `Badge`/`UserBadge` reads and writes — including the single canonical "award this badge to this user" path (`badgeRepository.awardBadge`), used by both `achievements`' rule engine and (once built) admin manual assignment (spec 31, spec 52).

## Structure

- `badge.constants.ts` — `MAX_FEATURED_BADGES` (6), `BADGE_SHAPE` (the fixed shape enum spec 14's MVP `designConfig` supports).
- `badge.schemas.ts` — `badgeDesignConfigSchema` (the Zod validator for `Badge.designConfig`'s untyped JSON — `{ shape, primaryColor }`), plus the request schemas for the display-toggle, featured-order, and title endpoints.
- `badge.types.ts` — raw repository record shapes (`designConfig: unknown`, unparsed) vs. the parsed response shapes (`BadgeCollectionEntry`, `FeaturedBadgeView`) — the same "repository returns raw, service parses" split `achievements` already uses for `requirementConfig` — plus `AwardBadgeInput`/`AwardBadgeResult` (an outcome object, not a throw, matching `xp`'s `AwardXpResult` shape).
- `badge.repository.ts` — Prisma queries only: `listActiveBadges`, `listUserBadgeStates`, `updateDisplay`, `findOwnedBadgeIds` (ownership check for the featured-order write), `clearFeatured`/`setFeatured`/`clearTitle`/`setTitle` (take a `DbClient` so `badge.service.ts` can compose them inside one transaction), `listFeaturedForUser`, `findTitleForUser`, `findOwnedTitleEligibleBadgeId`, and `awardBadge` — the race-safe "give this user this badge" primitive (see rationale below).
- `badge.service.ts` — `listCollectionForUser` (the spec 19–23 combined collected+locked view), `updateDisplay`, `updateFeatured`, `listFeaturedForUser` (consumed by `../creators`' public profile, not just this module's own routes), `getTitleBadgeForUser`, `updateTitle`, and `awardBadge` (wraps `badgeRepository.awardBadge` with the badge's XP reward via `xpService.grantFixedXp`) — the entrypoint any _other_ module or an admin controller should call to award a badge; `achievements` itself calls `badgeRepository.awardBadge` directly instead (see rationale below).
- `badge.controller.ts` / `badge.routes.ts` — `GET /badges/collection`, `PATCH /badges/:badgeId/display`, `PATCH /badges/featured`, `PATCH /badges/title`. All `requireAuth`-only, scoped to the caller's own collection — there's no "view someone else's full collection" endpoint yet, only the public-profile featured/title subset (`../creators`).

## Funnel

**User-facing:** nothing yet for the collection/title UI — this chunk is backend only. The collectible-library UI (spec 19, filters, locked-badge progress bars, drag-reorder) lands in a later chunk on top of these endpoints.

**Technical:** `GET /badges/collection` reads the full active badge catalog, the caller's `UserBadge` rows, and — via `achievementService.listProgressForUser` — live progress for everything still locked, then merges all three into one array per badge (`isCollected`, and either the unlock timestamp/display state or a `progress` breakdown, never both). Both write endpoints touch only rows the caller actually owns (`removedAt: null`); featuring re-validates ownership explicitly before touching anything, on top of the same guard the repository's `WHERE userId = ...` already provides. `achievement.service.ts`'s `unlockAchievement` calls `badgeRepository.awardBadge` directly to write the `UserBadge` row, then grants XP itself exactly as before — `awardBadge` only centralizes the actually-hard-to-get-right part (assignment-limit race safety + the ownership/uniqueness check), not the XP call, which stays a couple of near-identical lines in each caller.

## Non-obvious rationale

**`Badge.isPublic` gates _locked_ visibility, not collected visibility.** A badge with `isPublic: false` is omitted from `listCollectionForUser` entirely while locked (a "secret" badge that doesn't spoil itself by appearing as a mystery placeholder) — but once collected, every badge shows regardless of `isPublic`, since hiding something a user has actually earned would contradict "collectible achievement library." None of the MVP catalog uses `isPublic: false` yet (all seeded `true`); this exists for when an admin sets one later.

**Featuring is a full-replace, not an incremental add/remove.** `PATCH /badges/featured` (kept as `PATCH`, matching this codebase's REST convention — the shared `apiClient` only exposes `get`/`post`/`patch`/`del`, `PUT` doesn't appear anywhere in this repo) still replaces the _whole_ featured set in one call: `updateFeatured(userId, badgeIds)` clears every currently-featured badge for the user and re-sets exactly the given ordered list in one transaction, matching how a drag-reorder UI naturally submits ("here's my new featured lineup") rather than a sequence of individual position edits that could race against each other.

**Featured and displayed are independent flags, not coupled.** A badge can be `isFeatured: true` while `isDisplayed: false` — it simply won't appear in `listFeaturedForUser`'s output (which requires both). This matches spec 24's literal wording ("only badges marked visible appear in that order on the public profile") rather than assuming a user always wants a featured badge shown; forcing the coupling would be a product decision this module doesn't need to make unilaterally.

**Design-config parse failures skip the badge, they don't fail the whole request.** `parseDesignConfig` (used by both `listCollectionForUser` and `listFeaturedForUser`) logs and returns `null` on an invalid `designConfig` rather than throwing — the same fail-open shape `achievements` already uses for a malformed `requirementConfig`. One admin-edited bad JSON value shouldn't take down a user's entire collection view or someone else's public profile.

**`awardBadge` lives in `badge.repository.ts`, not only `badge.service.ts`, specifically so `achievements` can call it without creating a circular module dependency.** `badges` already depended on `achievements` (`listCollectionForUser` calls `achievementService.listProgressForUser` for locked-badge progress) before this chunk. Having `achievement.service.ts`'s `unlockAchievement` call `badgeService.awardBadge` back would make `badges` and `achievements` depend on each other's _service_ layer — a genuine cycle, and a first for this codebase (verified: `orders` depends on `payments`/`commissions`, never the reverse, and nowhere else in this repo do two modules' services import each other). Putting the race-safety-critical logic in the repository instead — which imports nothing from `achievements` — lets `achievement.service.ts` import `badgeRepository` (a one-directional, data-access-level dependency, the same shape `commissions` already reads `Order`/`OrderItem` through) while `badge.service.ts`'s own `awardBadge` (for admin/other future callers) wraps the same repository function with its XP grant. The cost is that XP-granting is duplicated across the two callers rather than centralized — a few lines, not the risky part — flagged here as the deliberate tradeoff rather than left implicit.

**Assignment-limit enforcement is a real atomic `UPDATE ... WHERE assignmentCount < assignmentLimit`, not a read-then-write race.** `Badge.assignmentCount` is a denormalized counter incremented via `tx.badge.updateMany({ where: { assignmentCount: { lt: assignmentLimit } }, data: { increment: 1 } })` — the exact same "conditional atomic write, read the outcome off the affected-row count" pattern `../creator-looks` already uses for view-count dedup and this codebase's existing like/save toggles. Two concurrent award attempts for a `assignmentLimit: 1` badge can't both win: Postgres evaluates and applies the `WHERE`+`increment` atomically per statement, so only one `UPDATE` sees `assignmentCount: 0 < 1` and succeeds; the other sees `1 < 1` and affects zero rows. Verified under real concurrency, not just reasoned about: `badge.integration.test.ts` fires three simultaneous `awardBadge` calls at a `assignmentLimit: 1` badge and asserts exactly one succeeds.

**`awardBadge` checks "does this user already own it" _before_ touching `assignmentCount`, not after.** An earlier version checked the assignment limit first; a re-award attempt to a user who already held a now-full badge incorrectly reported `ASSIGNMENT_LIMIT_REACHED` instead of the more accurate `ALREADY_AWARDED`, and would have silently over-incremented `assignmentCount` on a caller that retried before checking the response. The ownership pre-check (a plain `findUnique` on the `(userId, badgeId)` unique index) is a separate, tiny race window of its own — two truly simultaneous re-award attempts for the same already-owning user could both pass it — but the `tx.userBadge.create(...)` inside the transaction still has the real `@@unique([userId, badgeId])` constraint as the final authority, caught and mapped to `ALREADY_AWARDED` via `isUniqueConstraintError`, so no duplicate `UserBadge` row can ever land regardless of what the pre-check saw.

**Hiding a badge clears its title, unconditionally, in the same `updateMany` as the visibility flip.** `badgeRepository.updateDisplay` sets `isTitle: false` alongside `isDisplayed: false` in one statement rather than reading whether the badge was currently titled first — cheaper, and correct either way, since clearing a title that was never set is a no-op. This is spec 53's "graceful fallback" (a hidden badge can never be the active title) for the half that doesn't need dynamic badges to mean anything yet; "auto-promote to the next-highest eligible title" waits on Phase 2's dynamic badges (item 18), since without them there's no live-recomputed ranking to promote _to_.

**`updateTitle`'s "set" and "clear" paths share one clear-then-set transaction, mirroring `updateFeatured`.** Whether `badgeId` is a real id or `null`, the handler always calls `badgeRepository.clearTitle` first, then conditionally `setTitle` — the same "clear everything, then set exactly what was asked for" shape `updateFeatured` already uses for the (multi-badge) featured list, applied here to a single-badge field. `UserBadge.isTitle` has no DB-level "at most one true row per user" constraint, same reasoning as `isFeatured`: the clear-then-set transaction is the actual guarantee, a partial-unique index would be redundant with it.
