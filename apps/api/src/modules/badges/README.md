# badges

## Purpose

The badge catalog and a user's collection of it: what badges exist, which ones a given user has collected, their visibility/featured/title state, and the public profile showcase. Owns `Badge`/`UserBadge` reads and writes — including the single canonical "award this badge to this user" path (`badgeRepository.awardBadge`), used by both `achievements`' rule engine and admin manual assignment (spec 31, spec 52) — plus the full admin surface: badge catalog CRUD (spec 15/30), manual award/removal with a mandatory reason (spec 31/33), and the badge-side of the gamification stats dashboard (spec 29).

## Structure

- `badge.constants.ts` — `MAX_FEATURED_BADGES` (6), `BADGE_SHAPE` (the fixed shape enum spec 14's MVP `designConfig` supports), `BADGE_ANIMATION` (spec 13/14's animated-badge presets — see rationale below).
- `Badge.sponsorBrandId` — an optional FK to `../brands`' `Brand`, admin-set on the same badge-edit form as everything else. A badge with a sponsor shows a "Sponsored by {brand}" credit wherever it renders (collection grid, locked-progress card — both the same `BadgeCollectionEntry`, see below — and the real-time unlock toast); see rationale below for why this lives on `Badge` alone, not duplicated onto `Achievement`, and why `../challenges`/`../creator-competitions` explicitly opt out of it.
- `badge.schemas.ts` — `badgeDesignConfigSchema` (the Zod validator for `Badge.designConfig`'s untyped JSON — `{ shape, primaryColor, animation? }`), the display-toggle/featured-order/title request schemas, and the admin schemas: `createBadgeSchema`/`updateBadgeSchema` (a `.strict()` discriminated union on `requirementType` — the `ADMIN_AWARD` branch has no `conditions`/`activeFrom`/`activeUntil` fields at all, the rule-based branches require `conditions.min(1)` and accept the optional seasonal-window fields (spec 35) and, on update only, `achievementIsActive`; see rationale below for why `.strict()` matters here), `awardBadgeSchema`, `removeUserBadgeSchema`. Cross-field validation ("active-until must be after active-from") is a `.refine()` applied to the whole `discriminatedUnion(...)` result, not to an individual branch — Zod's discriminant introspection needs each branch to stay a plain `ZodObject`, so any check spanning fields from a specific branch has to live on the union as a whole.
- `badge.types.ts` — raw repository record shapes (`designConfig: unknown`, unparsed) vs. the parsed response shapes (`BadgeCollectionEntry`, `FeaturedBadgeView`) — the same "repository returns raw, service parses" split `achievements` already uses for `requirementConfig` — plus `AwardBadgeInput`/`AwardBadgeResult` (an outcome object, not a throw, matching `xp`'s `AwardXpResult` shape — the success variant carries `badgeName`/`badgeIcon` alongside `userBadgeId`/`xpReward`, sourced from the same `Badge` row `badgeRepository.awardBadge` already fetches for `isActive`/`assignmentLimit`, purely so `badge.service.ts`'s `awardBadge` can publish a complete `ACHIEVEMENT_UNLOCKED` event without a second query), `BadgeAdminRecord` (its `achievement` field carries `isActive`/`activeFrom`/`activeUntil` alongside `requirementType`/`requirementConfig`, so the admin catalog view can distinguish "badge disabled" from "achievement paused" from "outside its seasonal window"), `BadgeAdminStats`, `ManualAwardRecord`.
- `badge.repository.ts` — Prisma queries only: `listActiveBadges`, `listUserBadgeStates`, `updateDisplay`, `findOwnedBadgeIds` (ownership check for the featured-order write), `clearFeatured`/`setFeatured`/`clearTitle`/`setTitle` (take a `DbClient` so `badge.service.ts` can compose them inside one transaction), `listFeaturedForUser`, `findTitleForUser`, `findOwnedTitleEligibleBadgeId`, `listOwnersOfBadge`/`setDynamicEligibility` (read/write `UserBadge.isDynamicallyEligible`, called only by `../achievements`' dynamic-recheck job — see that module's README), and `awardBadge` — the race-safe "give this user this badge" primitive (see rationale below). Admin: `listAllBadgesAdmin`/`findBadgeAdminById`/`createBadgeWithAchievement`/`updateBadgeWithAchievement` (nested `Badge`+`Achievement` writes in one call/transaction, mirroring `prisma/seed.ts`'s own combined-create shape — `seasonalWindowFor`/`requirementConfigFor` derive the achievement's window/conditions from the request, both hard-coded to `null`/`{ conditions: [] }` on the `ADMIN_AWARD` branch regardless of what the form sends), `removeUserBadge`, `listManualAwards`, and the stats counters (`countAwardedBadges`/`countEngineAwardedBadges`/`countManualAwardedBadges`/`findMostAwardedBadge`).
- `badge.service.ts` — `listCollectionForUser` (the spec 19–23 combined collected+locked view), `updateDisplay`, `updateFeatured`, `listFeaturedForUser` (consumed by `../creators`' public profile, not just this module's own routes), `getTitleBadgeForUser`, `updateTitle`, and `awardBadge(input, xpSource?)` (wraps `badgeRepository.awardBadge` with the badge's XP reward via `xpService.grantFixedXp`, tagged with `xpSource` — defaults to `XP_SOURCE.ADMIN` — and, on a successful award, publishes `DomainEvents.ACHIEVEMENT_UNLOCKED` so the real-time unlock toast fires for this path too, not just the achievement engine's own) — the entrypoint any _other_ module or an admin controller should call to award a badge; `achievements` itself calls `badgeRepository.awardBadge` directly instead (see rationale below). Admin: `listAllBadgesAdmin`, `createBadge`/`updateBadge`, `awardBadgeManually` (calls `awardBadge` with `awardedById`/`awardReason` set, then maps each `AwardBadgeResult` failure reason to a client-safe message), `removeUserBadge`, `listManualAwards`, `getAdminStats`.
- `badge.controller.ts` / `badge.routes.ts` — `GET /badges/collection`, `PATCH /badges/:badgeId/display`, `PATCH /badges/featured`, `PATCH /badges/title`. All `requireAuth`-only, scoped to the caller's own collection — there's no "view someone else's full collection" endpoint yet, only the public-profile featured/title subset (`../creators`). Admin-only (`requireRole(ADMIN)`): `GET /badges/admin` (full catalog, active + inactive), `POST /badges`, `PATCH /badges/:badgeId` (badge deactivation is folded into this — see rationale below, there's no `DELETE`), `POST /badges/:badgeId/award`, `POST /badges/user-badges/:userBadgeId/remove`, `GET /badges/user-badges/manual`, `GET /badges/stats`.

## Funnel

**User-facing:** the collection/title UI (spec 19, filters, locked-badge progress bars, featuring) lives in `apps/web`'s `creator-dashboard` feature. The admin surface (catalog CRUD, manual award/removal, XP-adjacent stats) lives in `apps/admin`'s `gamification` feature — an admin creates a badge (choosing rule-based-with-conditions or admin-award-with-an-optional-assignment-limit), can hand-award any active badge to a specific user with a reason, and can remove a manual award later, also with a reason.

**Technical:** `GET /badges/collection` reads the full active badge catalog, the caller's `UserBadge` rows, and — via `achievementService.listProgressForUser` — live progress for everything still locked, then merges all three into one array per badge (`isCollected`, and either the unlock timestamp/display state or a `progress` breakdown, never both). A collected badge also carries `isDynamicallyActive` (`null` unless the badge is `isDynamic`, in which case it mirrors the raw `isDynamicallyEligible` column) so `apps/web` can show a "not currently active" note without conflating that with the user's own `isDisplayed` toggle — see the `../achievements` README for why the two flags stay separate. Both write endpoints touch only rows the caller actually owns (`removedAt: null`); featuring re-validates ownership explicitly before touching anything, on top of the same guard the repository's `WHERE userId = ...` already provides. `achievement.service.ts`'s `unlockAchievement` calls `badgeRepository.awardBadge` directly to write the `UserBadge` row, then grants XP itself exactly as before — `awardBadge` only centralizes the actually-hard-to-get-right part (assignment-limit race safety + the ownership/uniqueness check), not the XP call, which stays a couple of near-identical lines in each caller. `POST /badges` and `PATCH /badges/:badgeId` write the `Badge` and its 1:1 `Achievement` together (a nested `create`/two-statement transaction) — every badge in this catalog has exactly one `Achievement` row, even an `ADMIN_AWARD` one with empty `conditions`, matching what `prisma/seed.ts` has always done; the admin form never creates a bare `Badge` with no linked `Achievement`.

## Non-obvious rationale

**`Badge.isPublic` gates _locked_ visibility, not collected visibility.** A badge with `isPublic: false` is omitted from `listCollectionForUser` entirely while locked (a "secret" badge that doesn't spoil itself by appearing as a mystery placeholder) — but once collected, every badge shows regardless of `isPublic`, since hiding something a user has actually earned would contradict "collectible achievement library." None of the MVP catalog uses `isPublic: false` yet (all seeded `true`); this exists for when an admin sets one later.

**Featuring is a full-replace, not an incremental add/remove.** `PATCH /badges/featured` (kept as `PATCH`, matching this codebase's REST convention — the shared `apiClient` only exposes `get`/`post`/`patch`/`del`, `PUT` doesn't appear anywhere in this repo) still replaces the _whole_ featured set in one call: `updateFeatured(userId, badgeIds)` clears every currently-featured badge for the user and re-sets exactly the given ordered list in one transaction, matching how a drag-reorder UI naturally submits ("here's my new featured lineup") rather than a sequence of individual position edits that could race against each other.

**Featured and displayed are independent flags, not coupled.** A badge can be `isFeatured: true` while `isDisplayed: false` — it simply won't appear in `listFeaturedForUser`'s output (which requires both). This matches spec 24's literal wording ("only badges marked visible appear in that order on the public profile") rather than assuming a user always wants a featured badge shown; forcing the coupling would be a product decision this module doesn't need to make unilaterally.

**Design-config parse failures skip the badge, they don't fail the whole request.** `parseDesignConfig` (used by both `listCollectionForUser` and `listFeaturedForUser`) logs and returns `null` on an invalid `designConfig` rather than throwing — the same fail-open shape `achievements` already uses for a malformed `requirementConfig`. One admin-edited bad JSON value shouldn't take down a user's entire collection view or someone else's public profile.

**`awardBadge` lives in `badge.repository.ts`, not only `badge.service.ts`, specifically so `achievements` can call it without creating a circular module dependency.** `badges` already depended on `achievements` (`listCollectionForUser` calls `achievementService.listProgressForUser` for locked-badge progress) before this chunk. Having `achievement.service.ts`'s `unlockAchievement` call `badgeService.awardBadge` back would make `badges` and `achievements` depend on each other's _service_ layer — a genuine cycle, and a first for this codebase (verified: `orders` depends on `payments`/`commissions`, never the reverse, and nowhere else in this repo do two modules' services import each other). Putting the race-safety-critical logic in the repository instead — which imports nothing from `achievements` — lets `achievement.service.ts` import `badgeRepository` (a one-directional, data-access-level dependency, the same shape `commissions` already reads `Order`/`OrderItem` through) while `badge.service.ts`'s own `awardBadge` (for admin/other future callers) wraps the same repository function with its XP grant. The cost is that XP-granting is duplicated across the two callers rather than centralized — a few lines, not the risky part — flagged here as the deliberate tradeoff rather than left implicit.

**Assignment-limit enforcement is a real atomic `UPDATE ... WHERE assignmentCount < assignmentLimit`, not a read-then-write race.** `Badge.assignmentCount` is a denormalized counter incremented via `tx.badge.updateMany({ where: { assignmentCount: { lt: assignmentLimit } }, data: { increment: 1 } })` — the exact same "conditional atomic write, read the outcome off the affected-row count" pattern `../creator-looks` already uses for view-count dedup and this codebase's existing like/save toggles. Two concurrent award attempts for a `assignmentLimit: 1` badge can't both win: Postgres evaluates and applies the `WHERE`+`increment` atomically per statement, so only one `UPDATE` sees `assignmentCount: 0 < 1` and succeeds; the other sees `1 < 1` and affects zero rows. Verified under real concurrency, not just reasoned about: `badge.integration.test.ts` fires three simultaneous `awardBadge` calls at a `assignmentLimit: 1` badge and asserts exactly one succeeds.

**`awardBadge` checks "does this user already own it" _before_ touching `assignmentCount`, not after.** An earlier version checked the assignment limit first; a re-award attempt to a user who already held a now-full badge incorrectly reported `ASSIGNMENT_LIMIT_REACHED` instead of the more accurate `ALREADY_AWARDED`, and would have silently over-incremented `assignmentCount` on a caller that retried before checking the response. The ownership pre-check (a plain `findUnique` on the `(userId, badgeId)` unique index) is a separate, tiny race window of its own — two truly simultaneous re-award attempts for the same already-owning user could both pass it — but the `tx.userBadge.create(...)` inside the transaction still has the real `@@unique([userId, badgeId])` constraint as the final authority, caught and mapped to `ALREADY_AWARDED` via `isUniqueConstraintError`, so no duplicate `UserBadge` row can ever land regardless of what the pre-check saw.

**Hiding a badge clears its title, unconditionally, in the same `updateMany` as the visibility flip.** `badgeRepository.updateDisplay` sets `isTitle: false` alongside `isDisplayed: false` in one statement rather than reading whether the badge was currently titled first — cheaper, and correct either way, since clearing a title that was never set is a no-op. This is spec 53's "graceful fallback" (a hidden badge can never be the active title) for the half that doesn't need dynamic badges to mean anything yet; "auto-promote to the next-highest eligible title" waits on Phase 2's dynamic badges (item 18), since without them there's no live-recomputed ranking to promote _to_.

**`updateTitle`'s "set" and "clear" paths share one clear-then-set transaction, mirroring `updateFeatured`.** Whether `badgeId` is a real id or `null`, the handler always calls `badgeRepository.clearTitle` first, then conditionally `setTitle` — the same "clear everything, then set exactly what was asked for" shape `updateFeatured` already uses for the (multi-badge) featured list, applied here to a single-badge field. `UserBadge.isTitle` has no DB-level "at most one true row per user" constraint, same reasoning as `isFeatured`: the clear-then-set transaction is the actual guarantee, a partial-unique index would be redundant with it.

**`createBadgeSchema`/`updateBadgeSchema` needed an explicit `.strict()` on every discriminated-union branch — Zod object schemas silently strip unknown keys by default.** Caught live while testing the admin form, not by inspection: an `ADMIN_AWARD` request that also included a `conditions` array validated successfully with `conditions` just dropped, instead of being rejected — meaning an admin form bug (or a scripted request) could _appear_ to save conditions on a badge that would never actually check them, with no error to explain why. `.strict()` on each branch turns that into a `422 unrecognized_keys` response instead. This is the kind of gap that only shows up when you actually POST a real request through the validator, not from reading the schema — flagged here so the next discriminated-union schema in this codebase remembers `.strict()` isn't optional when the whole point of the union is "these fields must not coexist."

**There's no `DELETE /badges/:badgeId` — badge removal is folded into the same `PATCH` that handles everything else, via `isActive`.** A `Badge` is referenced by `Achievement` (`onDelete: Cascade`) and every `UserBadge` anyone has ever earned (also cascading) — a real delete would silently erase other users' earned badges the moment an admin removed a catalog entry, which is never the intent ("remove this from the catalog" should never mean "un-earn it for everyone who already has it"). `isActive: false` is the only removal semantics that make sense here, matching `Level`'s identical constraint-driven reasoning (see `xp/README.md`) and this codebase's broader "void, don't delete" convention. `listActiveBadges` (the public collection catalog) already filters `isActive: true`; `listAllBadgesAdmin` deliberately doesn't, so an admin can see and re-activate anything they've turned off.

**`Achievement.isActive` (achievement-level) and `Badge.isActive` (badge-level) are two independent flags, both surfaced separately in the admin update form.** Deactivating the badge (`isActive: false`) hides it from the public catalog and blocks new collection entirely. Deactivating just the achievement (`achievementIsActive`, update-only — a brand-new badge always starts with its achievement active, so create has no equivalent field) pauses the engine's evaluation of that one rule without touching the badge's own catalog visibility or anyone's already-earned `UserBadge` rows — the intended use is pausing a rule that's misbehaving or under review without also yanking the badge from view. The `ADMIN_AWARD` branch never carries this field at all: those achievements are already excluded from evaluation at the query level (see `achievements/README.md`), so "is the engine evaluating this" isn't a meaningful question for them, and `badge.repository.ts`'s `updateBadgeWithAchievement` hard-codes `isActive: true` for that branch rather than accepting an unused value from the form.

**`awardBadgeManually` maps each `AwardBadgeResult` failure reason to a specific, human-readable message rather than a generic "couldn't award this badge."** `badgeRepository.awardBadge`'s reasons (`BADGE_NOT_FOUND`, `BADGE_INACTIVE`, `ALREADY_AWARDED`, `ASSIGNMENT_LIMIT_REACHED`) are meant for programmatic branching, not display — an admin submitting the manual-award form needs to know _which_ of those happened, not just that something failed, so the controller surfaces the mapped message as the `AppError`'s `message` (with the raw reason kept as `code`) rather than collapsing all four into one string.

**"Who removed this manual award" is logged, not persisted to a column, matching `commissions`' own "void" convention.** `UserBadge` already has `removedAt`/`removedReason` (set by `removeUserBadge`) but no `removedById` field — the admin's identity for a removal is written to `logger.info` only, the same choice `commission.service.ts`'s `void`/`markPaid` already made for "who approved/voided this" rather than adding a dedicated column. Awarding is different: `awardedById` _is_ a real column, because `awardBadge` is the shared path the achievement engine also writes through (where "who awarded this" — `null` vs a real admin id — is load-bearing data the collection UI and public profile need to read back, not just an audit note).

**`Badge.isDynamic` shipped as a schema column back in the MVP chunk but stayed unreachable from the admin API until now — this chunk is what wires it up.** `badgeCoreFields` (shared by the badge admin schema and, minus `assignmentLimit`, by `../challenges`) didn't include `isDynamic` at all, so `createBadgeWithAchievement`/`updateBadgeWithAchievement` never wrote it and every badge silently kept the column's `@default(false)`. Adding it to `badgeCoreFields` means `../challenges` picked it up too by the same spread — deliberately destructured back out there, since a challenge badge is never meant to be dynamic (see that reasoning in `../achievements`' README); every existing challenge test payload needed no change once that exclusion was back in place, since the field simply isn't part of that schema.

**`listFeaturedForUser`/`findTitleForUser` gained an `OR: [{ isDynamicallyEligible: true }, { badge: { isDynamic: false } }]` clause — read as "not currently suppressed by the dynamic engine," not "is dynamic."** The second branch (`badge.isDynamic: false`) is what makes this a no-op for the other 100% of badges that were never marked dynamic in the first place — `isDynamicallyEligible` defaults `true` for everyone, but a non-dynamic badge's value is never actually meaningful, so gating purely on the column without the `isDynamic` escape hatch would still happen to work today, but only by coincidence of the default; the explicit `OR` makes the real invariant ("this check only matters for dynamic badges") visible in the query itself rather than relying on a default nobody explicitly touches.

**`designConfig.animation` is one optional field with five values (`none`/`glow`/`shimmer`/`pulse`/`radiant`), not three independent `glow`/`shadow`/`animation` toggles, even though spec 13/14 names glow and shadow as separate ideas.** In practice a "glow" effect already _is_ an animated shadow, and this codebase's existing rarity-driven visual escalation (`RARITY_RING` in `apps/web`'s `AchievementBadgeIcon.tsx`) already gives every badge a static shadow that scales with rarity — three independent knobs would let an admin build combinations (a glow with no shadow, an animation with no glow) that don't compose into anything coherent, for no real gain over one enum that names the whole visual treatment. This is also the reason it's optional and defaults to `undefined` rather than `"none"`: `undefined` means "let the rarity decide" (see `apps/web`'s `RARITY_DEFAULT_ANIMATION`), while an explicit `"none"` is a real admin choice to force a normally-animated rarity to stay static — the two are different states and the schema keeps them distinguishable.

**No migration for this field.** `Badge.designConfig` is already an untyped `Json` column — extending what `badgeDesignConfigSchema` accepts inside it is a validation-layer change only, the same way `assignmentLimit`/`isTitleEligible` etc. didn't need one when they were columns, but `designConfig`'s own internal shape never needs one at all since it was never typed at the database level in the first place.

**`awardBadge`'s domain-event publish and `xpSource` parameter were added for `../creator-competitions`, but land on the shared wrapper every caller goes through — not a competitions-specific special case bolted on afterward.** Before this, only `../achievements`' own `unlockAchievement` published `DomainEvents.ACHIEVEMENT_UNLOCKED` (via `badgeRepository.awardBadge` directly, sidestepping this wrapper specifically to avoid a circular import — see below), so an admin's manual award never triggered the real-time unlock toast a user gets from an engine-driven unlock. Now every caller of this wrapper — manual admin awards, and `../creator-competitions`' weekly settlement — gets the toast for free, which is a real behavior change to manual awards, not just new behavior for the new caller; flagged here since it's the kind of side effect that's easy to miss reading only the new module's own README. `xpSource` exists because the XP grant this wrapper makes was previously hardcoded to `XP_SOURCE.ADMIN` — accurate when the only caller was an actual admin action, wrong the moment a second, non-admin caller exists. Defaulting the parameter to `XP_SOURCE.ADMIN` means the existing `awardBadgeManually` call site needed zero changes.

**`sponsorBrandId` lives on `Badge` only, never duplicated onto `Achievement`, `Challenge`, or `CreatorCompetition`.** Every one of those is either a 1:1 wrapper around a `Badge` (`Achievement.badgeId`, `Challenge.achievementId`) or references one directly (`CreatorCompetition.badgeId`) — `Badge` is already the single entity every display surface (collection grid, locked-progress card, admin catalog, unlock toast) ultimately resolves to before rendering anything, so one field there covers all of them with no join-through-two-tables anywhere. `../challenges` and `../creator-competitions` both destructure `sponsorBrandId` back out of `badgeCoreFields` (the same exclusion pattern they already use for `assignmentLimit`/`isDynamic`) — not an oversight, a deliberate scope cut: sponsoring a time-boxed challenge or a weekly competition trophy is a real, plausible future extension of the same mechanism, but it wasn't asked for here, and shipping it speculatively on two already-tested flows risked breaking either for a use case nobody's confirmed wants it yet. Turning it on later is a one-line change to each schema's destructuring, not a new field.

**A badge's unlock toast carries `sponsorBrandName`, not a full `sponsorBrand` object, and two independent call sites had to be updated to add it.** `achievement.service.ts`'s `unlockAchievement` publishes `DomainEvents.ACHIEVEMENT_UNLOCKED` itself (it calls `badgeRepository.awardBadge` directly, not this module's `awardBadge` wrapper — see the circular-import rationale above), so the sponsor name has to reach it through its own read path: `achievementRepository`'s two eligibility queries now `include: { badge: { include: { sponsorBrand: { select: { name: true } } } } }`, threaded through `EligibleAchievementRecord`. `badge.service.ts`'s own `awardBadge` gets it the other way, from `badgeRepository.awardBadge`'s existing badge lookup gaining the same nested select. Both funnel into the same `AchievementUnlockedPayload`/toast shape — a plain string, not a brand id/logo — because the toast is rendered as flat text (`toast.success(string)`) with no image slot; a name is all it can use, and keeping the socket payload to a name avoids a second brand fetch on the client for a one-line credit.

**Creating or updating a badge with a `sponsorBrandId` validates the brand exists before writing, in the service layer, not by letting the FK constraint reject it.** `badge.service.ts`'s `assertSponsorBrandExists` reuses `../brands`' own `brandRepository.findManyByIds` (the same cross-module repository-to-repository read `commissions` already does for `Order`/`OrderItem`) rather than a raw `try/catch` around the Prisma write — a bad id turns into a clean `422 SPONSOR_BRAND_NOT_FOUND` with a safe message, not a raw constraint-violation error reaching the admin form (this codebase's Security section explicitly bans DB error objects/messages from ever reaching a response). The FK's `onDelete: SetNull` is still the real safety net for the case validation can't catch — a brand deleted sometime _after_ it was set as a sponsor — at which point the badge just quietly loses its credit rather than becoming unreadable or cascading away.
