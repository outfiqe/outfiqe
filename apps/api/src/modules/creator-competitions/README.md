# creator-competitions

## Purpose

Ongoing, admin-defined weekly competitions: "the top N creators in [leaderboard category] each week win [badge]." A composition of `../creator-leaderboard` (the ranking data) and the badge-award mechanics `../badges`/`../achievements` already established, not a new scoring or ranking engine of its own — see rationale below for why this shape was chosen over a one-off dated event.

## Structure

- `creatorCompetition.constants.ts` — `MIN_COMPETITION_WINNERS`/`MAX_COMPETITION_WINNERS` (1–10, the same ceiling `../creator-leaderboard`'s own `CREATOR_LEADERBOARD_TOP_N` uses, since a competition can never have more winners than the leaderboard tracks ranks for), `COMPETITION_XP_SOURCE` (the `XpTransaction.source` value competition wins are tagged with).
- `creatorCompetition.schemas.ts` — `createCreatorCompetitionSchema`/`updateCreatorCompetitionSchema`, reusing `badgeCoreFields` minus `assignmentLimit`/`isDynamic` (the same exclusion `../challenges` already makes, for the same reason — see rationale below), plus `name` (the competition's own display name), `leaderboardCategory` (`CreatorLeaderboardCategory`, deliberately not called `category` — see rationale below), and `topN`.
- `creatorCompetition.types.ts` — `CreatorCompetitionAdminRecord`, `PublicCreatorCompetitionView` (the trimmed-down public shape — no badge description/xpReward/permanence flags, a viewer only needs enough to know what they're competing for).
- `creatorCompetition.utils.ts` — `toPublicView`, the one pure mapper, unit-tested directly against a hand-built minimal object rather than a full Prisma payload (see rationale below).
- `creatorCompetition.repository.ts` — Prisma queries only: `createWithBadge`/`updateWithBadge` (nested `Badge` write in one call/transaction, mirroring `../challenges`' own `createChallengeWithAchievementAndBadge`/`updateChallengeWithAchievementAndBadge` exactly, minus the `Achievement` layer competitions don't need), `listAllAdmin`, `listActive` (active competition + active badge, used by both the public read and the settlement job).
- `creatorCompetition.service.ts` — `settleWeeklyCompetitions(now)` (the real settlement logic, takes an explicit `now` so it's directly testable) and `runWeeklySettlement()` (the zero-arg wrapper the job scheduler calls, matching every other boundary job's `run: () => Promise<unknown>` shape — see `../creator-leaderboard`'s own `runRecompute` for the identical split). Also `listActiveForViewers`, `listAllAdmin`, `createCompetition`, `updateCompetition`.
- `creatorCompetition.controller.ts` / `creatorCompetition.routes.ts` — `GET /creator-competitions` (public, no auth), `GET /creator-competitions/admin`, `POST /creator-competitions`, `PATCH /creator-competitions/:competitionId` (all three `requireRole(ADMIN)`).

## Funnel

**User-facing:** on `apps/web`'s `/leaderboard/creators` page, a banner appears above whichever leaderboard category currently has an active competition attached, naming the trophy badge and how many people win it each week. Winning is entirely passive — a creator does nothing beyond whatever activity already drives their rank in that category; there's no "enter this competition" action anywhere.

**Technical:** every Monday at 00:00 ISO time — the exact same boundary `../creator-leaderboard`'s own weekly recompute already fires at (`nextIsoWeekStart`, registered as its own separate `BoundaryJob` in `src/jobs/scheduled-jobs.ts`) — `runWeeklySettlement` calls `settleWeeklyCompetitions(now)`, which resolves `previousIsoWeekKey(now)` (the week that just ended) and, for every active competition, reads `creatorLeaderboardRepository.topN(category, thatWeek, topN)` directly — the exact same Redis ZSET the leaderboard page itself reads from, not a second computation — and calls `badgeService.awardBadge` for each of the top N members, tagged with `COMPETITION_XP_SOURCE` instead of the admin default. A creator who already won a previous week (or was independently awarded the same badge some other way) is silently skipped via the same `ALREADY_AWARDED` outcome `awardBadge` already returns for any repeat award — no special-casing needed here. A competition tied to a category an admin has since disabled (`../creator-leaderboard`'s own toggle) is skipped for that week rather than awarded off stale or incomplete data.

## Non-obvious rationale

**This chunk deliberately builds "a recurring weekly rule," not "a one-off dated competition instance" — a real fork in what the plan's own "creator competitions" phrase could have meant, resolved by asking rather than assuming.** A one-off dated event (like a `Challenge`) would need its own scoped ranking computation for an arbitrary date range, since `../creator-leaderboard`'s data is always bucketed by ISO week — a genuinely new scoring engine. The recurring-weekly shape needs none of that: it reuses the leaderboard's own already-computed, already-weekly-resetting data as-is, and settles at the exact boundary the leaderboard itself already resets at. This is the whole reason the plan's "not a new primitive" framing holds true in practice, not just in spirit.

**No settlement-tracking table, and no attempt to prevent a duplicate run of `settleWeeklyCompetitions` for the same week.** A second run for a week already settled recomputes the exact same `topN` from the exact same frozen Redis data (a past week's ZSET is never rewritten once the week ends) and calls `awardBadge` again for the same winners — which safely no-ops via `ALREADY_AWARDED` for anyone who already has it. Idempotency falls out of the existing `UserBadge` uniqueness constraint for free; a dedicated ledger to prevent re-processing would be solving a problem the award path's own real DB constraint already solves.

**A repeat win — the same creator finishing top N again in a later week — doesn't do anything, by design, not by oversight.** `Badge`/`UserBadge` in this codebase is fundamentally "collect each badge once"; there's no repeat-award or win-count concept anywhere in the schema, and building one (a badge-per-week, or a separate win-streak ledger) is real new scope this chunk doesn't take on. A creator who wins twice gets no second badge and no second XP grant — flagged here as an accepted MVP limitation, not solved silently. Worth a follow-up (a win-count field on `UserBadge`, or a small separate ledger) if recurring winners turn out to be common enough that this feels anticlimactic in practice.

**Competitions are never `isDynamic`, for the identical reason `../challenges` already excludes it (`assignmentLimit`/`isDynamic` are destructured out of the shared `badgeCoreFields` the same way there).** A competition's badge is awarded once, permanently, the moment a week settles — there is no "keep re-checking and revoke it if they fall out of rank" behavior here, unlike `../achievements`' dynamic-badge recheck job. The two mechanisms look superficially similar (both key off `../creator-leaderboard` rank data) but serve opposite philosophies: dynamic badges track _current_ standing and can be lost; a competition win is a permanent record of _having placed_ in a specific week, never revoked afterward.

**`leaderboardCategory`, not `category`, for the `CreatorLeaderboardCategory` field — a real naming collision caught before it shipped, not a style preference.** `badgeCoreFields` (spread into this schema, same as `../challenges`) already has its own `category: BadgeCategory` field (the badge's catalog category — `BEGINNER`/`SPECIAL`/etc.). A second field also named `category` in the same object literal would silently shadow the first one — the badge's real category would never reach the database, replaced by whatever `CreatorLeaderboardCategory` value the admin picked, since the schema is built by spreading `badgeCoreFields` first and adding explicit keys after (the later key always wins in a JS object literal). Caught by re-reading the schema and repository together before running it, not by a test failure — a genuine near-miss worth flagging for the next entity that composes `badgeCoreFields` with any concept that might also want to be called "category."

**`toPublicView` takes a small hand-declared `CompetitionForPublicView` type, not the full Prisma-generated `CreatorCompetitionRecordWithBadge` payload it's actually called with.** The function only ever reads five fields off the badge and four off the competition; typing its parameter as the full payload would mean its unit test needs a complete, realistic Prisma-shaped mock object (every `Badge` column, every `CreatorCompetition` column) just to satisfy the type — and CLAUDE.md's ban on `as unknown as` rules out silencing that with a cast. A narrower structural type that only names what the function actually touches lets the real call site (`competitions.map(toPublicView)`, where `competitions` really is the full Prisma payload) keep working unchanged — a wider object always structurally satisfies a narrower required shape — while the test constructs a plain, minimal, fully-real literal with no assertion anywhere.

**`badgeService.awardBadge` gained a domain-event publish (`DomainEvents.ACHIEVEMENT_UNLOCKED`) and a second `xpSource` parameter as part of this chunk, not a follow-up.** Before this chunk, only `../achievements`' own `unlockAchievement` published that event (calling `badgeRepository.awardBadge` directly, bypassing the service wrapper specifically to avoid a circular import — see `../badges`' README) — meaning an admin's manual badge award, or now a competition win, never triggered the real-time unlock toast `../achievements`' engine-driven unlocks already get. Adding the publish to the shared `badgeService.awardBadge` wrapper instead of duplicating unlock-and-announce logic a third time here means every current and future caller of that wrapper gets the toast for free; the `xpSource` parameter (defaulting to `XP_SOURCE.ADMIN`, preserving the existing manual-award behavior with zero changes needed at that call site) exists because the wrapper's XP grant was previously hardcoded to attribute every award to "admin," which would have mislabeled every competition win's ledger entry as an admin action it isn't.
