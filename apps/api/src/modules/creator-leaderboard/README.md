# creator-leaderboard — weekly creator rankings

## Purpose

Public, real-time weekly rankings of creators across seven categories (spec 36–37): Top XP, Top Creator, Most Likes, Most Engaged, Top Seller, Rising Creator, Most Achievements. A different dimension from `../leaderboard`, which ranks brands, not creators — this module reuses that module's architecture (weekly ISO-week Redis ZSETs, a boundary scheduler for the Monday-rollover gap, an empty-week fallback), not its code, since the two rank a different entity against different data.

## Structure

- `creatorLeaderboard.types.ts` — `CreatorLeaderboardSnapshot`, `CreatorStatsRow` (the one per-creator stats row every category derives its score from), `ZsetMember`, `CreatorLeaderboardCategoryState`. Re-exports `CreatorLeaderboardCategory` (a real Prisma enum, see rationale) and `CreatorLeaderboardEntry` (`#socket/socket.types.js`, shared by the REST response and the socket broadcast payload).
- `creatorLeaderboard.constants.ts` — `CREATOR_LEADERBOARD_TOP_N`, the recompute interval, ZSET key retention, `TOP_CREATOR_FOLLOWER_WEIGHT` (how many XP-equivalent points one follower is worth in the Top Creator composite), `RISING_CREATOR_SURGE_SCORE` (a creator with XP this week but none last week — division-by-zero — gets this fixed high score instead of `Infinity` or being excluded, same idea as `../leaderboard`'s fastest-growing "surge" score).
- `creatorLeaderboard.utils.ts` — pure functions only: `scoreForCategory` (derives one category's score from a `CreatorStatsRow`), `deriveGrowthScore` (the Rising Creator week-over-week percentage), `formatCreatorScoreLabel`, `toZsetMembers`. No DB/Redis access — unit tests live here.
- `creatorLeaderboard.repository.ts` — Redis ZSET wrappers (mirroring `../leaderboard`'s), one raw SQL query (`fetchCreatorStats`) that computes every category's base numbers for every eligible creator in a single pass (see rationale), and `CreatorLeaderboardCategoryConfig` CRUD for the admin per-category enable/disable toggle.
- `creatorLeaderboard.service.ts` — `runRecompute` (the one scheduled job: fetch stats once, derive and write all seven categories), `getTop` (hydrates a ZSET's top N with creator profile data + week-over-week rank movement + the category's current enabled state), `listCategoryStates`/`setCategoryEnabled` (admin read/write).
- `creatorLeaderboard.schemas.ts` / `.controller.ts` / `.routes.ts` — `GET /api/creator-leaderboard?category=...` (public), `GET /api/creator-leaderboard/categories` (public, lists all seven with their enabled state, for building tabs), `PATCH /api/creator-leaderboard/categories/:category` (`platform:gamification:manage` via `requirePlatformRole` + `requirePlatformNavItem("gamification")`, see `platform-access/README.md`).
- `creatorLeaderboard.socket.ts` — same two-halves shape as `../leaderboard`'s: `registerCreatorLeaderboardSocketHandlers()` (per-category subscribe/unsubscribe rooms) and `registerCreatorLeaderboardEventConsumer()` (domain-event → Socket.IO relay).

## Funnel

**User-facing:** the `/leaderboard` page's Creators tab group shows all seven category tabs (fewer, if an admin has disabled some) with live-updating rows — rank, avatar, name, handle, score. A user's own profile has a "Hide me from leaderboards" toggle (`../creators`' `updateCreatorProfileSchema`) that removes them from every category's ranking without touching their actual XP/likes/sales/achievements anywhere else in the product.

**Technical:**

1. One scheduled job (`creator-leaderboard-recompute`, every 15 minutes, plus a boundary job that fires within seconds of every Monday 00:00 ISO rollover) calls `fetchCreatorStats()` once — a single raw SQL query joining `users`/`user_progress`/`creator_looks`/`creator_commissions`/`user_badges` — and derives all seven categories' scores from that one snapshot, `ZADD`-overwriting each category's weekly ZSET and publishing `DomainEvents.LEADERBOARD_CREATOR_UPDATED` per category.
2. `registerCreatorLeaderboardEventConsumer()` picks up that event, re-reads the fresh top N for the affected category via `getTop()`, and emits it to that category's room (`leaderboard:creator:<category>`) only.
3. `GET /api/creator-leaderboard?category=...` serves the same `getTop()` for first paint; the client then joins the matching socket room.

## Non-obvious rationale

**`CreatorLeaderboardCategory` is a real Prisma enum, not a `@outfiqe/types`-mirrored string constant like `../leaderboard`'s `LeaderboardCategory`.** The brand leaderboard's category type predates having any DB-level representation at all — it only ever needed to exist as a TS union plus a runtime object for Redis keys/socket rooms. This module needs a genuine DB column (`CreatorLeaderboardCategoryConfig.category`, the admin per-category toggle's primary key) from the start, so it follows this _domain's_ own established convention instead — the same shape `XpActivityType`/`AchievementRequirementType`/`BadgeCategory` already use in `xp`/`achievements`/`badges` — and that one enum is used everywhere (Redis keys, socket rooms, REST query params) rather than maintaining a second, parallel string representation the way the brand leaderboard has to for historical reasons.

**All seven categories are recompute-based; none is a live `ZINCRBY` on a domain event, unlike `../leaderboard`'s most-loved.** Brand leaderboard's most-loved has a single, reliable choke point (`follow()`/`unfollow()`) to increment on. None of these seven categories do — each is an aggregate over a creator's _entire history_ (total XP, total likes ever received, total achievements ever earned), and `xp.service.ts` deliberately does **not** publish a domain event on every XP grant (only on a level-up) specifically because that would fire on nearly every user action on the platform. Recomputing from source tables on an interval, the same solution `../leaderboard` already uses for its own three recompute categories, avoids threading a new event-publish call into `xp`/`badges`/`creator-looks`/`commissions` for every write path that could conceivably move one of these seven numbers.

**One raw SQL query computes the base numbers for all seven categories, not seven separate recompute functions each re-querying the database.** Unlike brand leaderboard's four categories (four genuinely different data sources: purchases, follows, a trending score, a purchases diff), six of these seven creator categories are just different combinations/weightings of the _same_ underlying per-creator numbers — XP, follower count, likes, engagement, sales, achievement count. `fetchCreatorStats()` gathers all of them in one pass (one query, `LEFT JOIN`ed and `GROUP BY`ed per source table), and `scoreForCategory` is a pure, unit-tested function that picks/combines the right numbers per category from that one snapshot. This is also what sidesteps a real sequencing question: Rising Creator and Top Creator both need XP data that, in a "one recompute function per category" design, might not have run yet on a given tick — here there's only one data-fetch to sequence against.

**Rising Creator is the one category not derived from `fetchCreatorStats()` directly — it diffs the just-written Top XP ZSET against last week's.** Mirrors `../leaderboard`'s fastest-growing exactly: it can only be computed _after_ the current week's Top XP scores exist, so `runRecompute` always writes Top XP (and the other five stats-derived categories) before deriving Rising Creator from the fresh current-week and stale previous-week Top XP ZSETs. No coordination primitive was added for this beyond ordering the two calls within `runRecompute` — same "no coordination primitive, sequencing lives in the function that needs it" acceptance `../leaderboard`'s own recompute jobs already made.

**An admin-disabled category returns `entries: []`, not the real ranking with a client-side "hidden" hint.** `getTop()` checks `isCategoryEnabled` first and short-circuits before touching Redis at all when a category is off — the point of the toggle (spec 37: "leaderboards should stay optional") is that a disabled category's ranking genuinely isn't available through the public API, not just hidden by convention in a UI a client could bypass. The recompute job keeps writing a disabled category's ZSET regardless (cheap — it's one more `ZADD` in an already-single-query pass), so re-enabling it later doesn't need to wait for the next tick.

**`fetchCreatorStats()` excludes a creator with `hideFromLeaderboards: true` at the query's own `WHERE` clause, not as a post-filter.** `User.hideFromLeaderboards` (edited via `../creators`' `PATCH /creators/me`, alongside `heightCm`/`showHeight`) means an opted-out creator's numbers never enter any category's ZSET in the first place — there's no risk of a stale cached entry lingering for someone who just opted out, since the very next recompute tick simply won't include them.

**`TOP_SELLER`'s sum excludes `VOIDED` commissions, unlike every other "don't reverse" number in this gamification build.** `xp`/`achievements`' own README files document a deliberate, accepted simplification: XP and achievement-progress metrics (`purchases_count`, `sales_count`) never reverse when an order is cancelled or a commission voided — XP is treated as "speculative, not retroactively reversed." A public _leaderboard_ ranking real earned money is a different fairness bar: a creator's rank shouldn't be inflated by sales that turned out to be fraud, a cancellation, or a refund. `fetchCreatorStats()`'s sales aggregate is the one place in this feature that filters `status != 'VOIDED'`, a deliberate, stated departure from the rest of this build's XP philosophy, not an inconsistency.

**Every stats-derived category only ranks creators with a real, positive score — zero-activity creators are never written into the ZSET.** `writeStatsDerivedCategories` used to write every eligible creator's row regardless of score, including a flat `0` for anyone with no XP/likes/engagement/sales/achievements at all — on a small or early platform where few creators have done anything yet, this meant Top Seller, Top XP, and the rest ranked people who had earned or sold literally nothing, 1st/2nd/3rd, tie-broken by Redis's own lexicographic ordering on the creator-id member (deterministic, but meaningless as a ranking — it just looked arbitrary). `RISING_CREATOR` already filtered `score > 0` before writing; the other six categories never got the same treatment. Fixed by filtering every category's entries to `score > 0` before the `ZADD`, matching Rising Creator's own existing pattern — a genuinely empty week now correctly renders the list's own "No creators ranked yet this week" empty state (`CreatorLeaderboardList.tsx`, already built and already correct, just never exercised) instead of a fabricated top 10. Proved with a real integration test that a zero-activity creator never appears in any of the six categories while an active creator's real scores are unaffected.

**`RISING_CREATOR` also excludes a creator whose XP dropped week-over-week, not just those with none.** `deriveGrowthScore` can return a negative percentage when this week's total XP is lower than last week's — reachable now that admin XP corrections can move a creator's total down (see `../xp/README.md`'s downward-adjustment fix) — and nothing filtered that out before writing to the ZSET, so a demoted creator could show up on a "Rising" leaderboard with a `-40%` badge. Fixed with a second `.filter(({ score }) => score > 0)` after computing growth, so only creators who are actually rising ever rank there.

**`getTop()` re-validates every candidate's `accountStatus`/`creatorStatus`/`hideFromLeaderboards` at read time, not just at the last recompute.** The public ranking hydrates from a Redis ZSET that's only rewritten every 15 minutes and kept for 14 days — `userRepository.findManyByIds` (the hydrate step) doesn't filter by status at all, so a creator banned, de-approved, or who opted out _after_ the last recompute stayed visible on the live public leaderboard until the next tick caught up. Same staleness class already fixed in `../creator-looks` (`hydrateFeedPosts`), `../trending`, and `../follows` this same pass. Fixed with an `isEligibleForLeaderboard` guard applied to each hydrated creator before it's allowed into `entries`; proved with a real integration test that bans a creator between two `getTop()` calls and confirms they disappear from the second one while the cached ZSET is still warm. This also incidentally exposed and fixed a rank-numbering bug: `rank: index + 1` used the candidate's position in the _pre-filter_ list, so filtering out an ineligible creator mid-list left a gap in the displayed ranks (1, 2, 4, 5, skipping 3) — now `rank: entries.length + 1`, numbered off what's actually being returned.

**The "empty week, awaiting first recompute" fallback used to re-surface a stale, pre-fix zero-score entry instead of showing an honest empty board.** `getTop()` falls back to last week's ZSET when this week's is empty, on the assumption that emptiness means the recompute job simply hasn't ticked yet since Monday's rollover. Once the zero-activity fix above shipped, that assumption broke: a category with zero real activity genuinely computes to an _empty_ current-week ZSET (every candidate filtered out), which is indistinguishable from "never computed" by length alone — so the fallback kept reaching back to last week's ZSET, which (until it ages out after 14 days) still held the exact zero-score entries the fix was supposed to remove. This is why "Top XP"/"Top Seller"/"Most Achievements" kept showing real creators ranked 1st–3rd with 0 XP/Rs. 0/0 badges even after the fix shipped. Fixed by writing an explicit `leaderboard:creator:computed:<category>:<week>` marker (`replaceWeeklyScores`, unconditionally, even when it writes zero entries) and basing `isAwaitingFirstRecompute` on that marker instead of on emptiness — a week that has genuinely been computed and found nothing now renders the real empty state, while a week that's truly never run yet still bridges to last week's numbers as before. Proved with two integration tests: one confirms a computed-but-empty week returns `entries: []` even with a stale positive-looking entry sitting in last week's ZSET, the other confirms the legitimate bridge still works when this week truly hasn't run yet.

**`TOP_SELLER`'s exact sum is exercised through a real `Product`→`Order`→`OrderItem`→`CommissionTier`→`CreatorCommission` fixture chain, not just the zero-row case.** Every other integration test in this file exercises the same raw SQL query's `sales_stats` `LEFT JOIN` with zero matching rows (proving the `COALESCE(..., 0)` fallback works and the query doesn't error), which left the actual summing/`VOIDED`-exclusion behavior unverified. `giveSale()` reuses the same fixture chain `creator-overview`'s own integration tests already built (`creator-overview.integration.test.ts`'s `seedCommission`), rather than inventing a second copy — a creator with an `APPROVED`, a `PENDING`, and a `VOIDED` sale is asserted to rank at exactly the sum of the first two.
