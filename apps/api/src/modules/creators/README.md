# Creators

## Purpose

Creator applications (a `User` opting in to become a creator), the admin approve/reject queue, and public creator profile/discovery reads — `GET /creators/by-handle/:handle`, its posts, `GET /creators/search`, and `GET /creators/autocomplete`. Creator _content_ (posts, likes, comments) is owned by `../creator-looks`; this module owns the creator as a person/account.

## Structure

- `creator.service.ts` — `apply`/`getMine`/`updateMe` (a user's own creator profile), `getPublicProfile`/`listLooksByHandle` (public reads), `search` (public discovery), `autocomplete` (typeahead), `list`/`approve`/`reject` (admin queue).
- `creator.controller.ts`, `creator.routes.ts` — thin HTTP layer. `POST /creators/apply`, `GET/PATCH /creators/me` need auth; `GET /creators/by-handle/:handle`(`/looks`), `GET /creators/search`, and `GET /creators/autocomplete` are public; `GET /creators` (the admin queue) and `POST /:userId/approve`/`reject` require `ADMIN`.
- `creator.schemas.ts` — zod schemas + inferred query/body types.
- `creator.types.ts`, `creator.utils.ts` — `CreatorProfile` (own profile, includes `email`), `PublicCreatorProfile` (full profile page), `CreatorSearchResult` (search-card shape, also reused as the autocomplete suggestion shape) and the `UserRecord → *` mappers (`toProfile`, `toSearchResult`).
- `creator.constants.ts` — `AUTOCOMPLETE_LIMIT`, `MIN_HEIGHT_CM`/`MAX_HEIGHT_CM` (bounds enforced on `updateCreatorProfileSchema`'s `heightCm`).
- No local `creator.repository.ts` — this module reads/writes the `users` table directly through `../users/user.repository.ts` (`userRepository`) rather than duplicating a second data-access layer over the same table; `creator.service.ts` is the only place that turns those raw `UserRecord`s into creator-shaped responses.

## Funnel

**User-facing:** a signed-in customer applies via their dashboard → `creatorStatus` goes `NONE → PENDING`, sitting in the admin's approve/reject queue → once `APPROVED`, `isCreator` flips true and their `/creator/:handle` profile and posts become publicly visible. Anyone (signed in or not) can search for a creator by name or handle from `/explore/search`, with live suggestions appearing as they type in the nav search box (see `apps/web/src/features/search/README.md`).

**Technical:** `creator.service.search` calls `userRepository.searchCreatorIds` (`Prisma.$queryRaw` against the hand-written `search_creators` Postgres function — see `../products/README.md` for the general pg_trgm/full-text pattern this follows), then `userRepository.findManyByIds` to hydrate full rows in ranked order, same ids-then-hydrate shape `../products/product.service.ts` and `../creator-looks/creatorLook.repository.ts` (`searchLooks`) both use. Offset-based pagination via `encodeCursor`/`decodeCursor` (`#lib/pagination.utils.js`), same as product search — rank isn't a stable column to keyset-paginate on. `creator.service.autocomplete` calls the same `searchCreatorIds`, just capped at `AUTOCOMPLETE_LIMIT` (4) with no offset.

## Non-obvious rationale

`search_creators` (migration `20260818150000_add_creator_and_look_search`, tuned in `20260818153000_tune_creator_search_trigram_threshold`) only matches `handle`/`name`, filtered to `is_creator = true AND creator_status = 'APPROVED'` — there's no bio/description field on `User` to weight in, unlike products' brand/category join. It uses a **higher** trigram threshold (`0.5`) than product search's `0.4`: names and handles are short, mostly single tokens, so the same threshold that correctly separated real product typos from noise let through real false positives here — searching "kastha" matched "Sabin **Shrestha**" at a `word_similarity` of `0.43`, well above product search's `0.4` cutoff but nowhere near a genuine typo match (`0.75`+ in this same dataset for an actual near-miss spelling). Mismatching a person's account reads worse than mismatching a product, so this module errs further toward precision.

Creator search results don't carry `isFollowing` or a Follow button (`../follows` already has a _different_ existing endpoint, `GET /follows/suggested-creators`, for the "who to follow" sidebar rail, which by construction excludes people you already follow — search doesn't have that guarantee). Adding a Follow action here needs `isFollowing` threaded through `search_creators`/`CreatorSearchResult` first, which hasn't been done — the search card links to the creator's profile instead, where following already works correctly.

`GET /creators/autocomplete` exists to give the explore-mode nav search box the same live-typeahead UX `GET /products/autocomplete` already gives the shop-mode one — see `apps/web/src/features/search/README.md` for the frontend side. It deliberately reuses `CreatorSearchResult` rather than introducing a separate `CreatorSuggestion` type: unlike `ProductSuggestion` (a pared-down slice of a much heavier `PublicProduct`), `CreatorSearchResult` is already suggestion-sized (`userId, name, handle, avatarUrl, followerCount`), so a second, narrower type would just duplicate it. Caching mirrors `product.service.ts`'s `autocomplete` exactly — an in-process `LRUCache` (500 entries, keyed by normalized query) in front of `cacheService`/Redis (`CACHE_TTL.CREATOR_AUTOCOMPLETE`, 120s) — for the same reason: autocomplete fires on every keystroke, and the same partial queries repeat heavily across users typing the same prefixes.

`PublicCreatorProfile.featuredBadges` (spec 24–27's public showcase) is fetched via `badgeService.listFeaturedForUser`, not `badgeRepository` directly — a service-to-service call, same cross-module read pattern `xp`/`achievements` already use elsewhere in this build. Only badges that are both `isFeatured` **and** `isDisplayed` (and not admin-removed) ever appear here; toggling either off in `../badges` is enough to pull a badge off a public profile without un-earning it.

`PublicCreatorProfile.titleBadge` (spec 53) is the analogous single-badge read via `badgeService.getTitleBadgeForUser`, gated the same way (`isTitle && isDisplayed && removedAt: null`) and returning the same `FeaturedBadgeView` shape rather than a separate type — `featuredBadges` and `titleBadge` are structurally identical (id/name/icon/designConfig/rarity), only their selection rule differs, so a second type would just duplicate the first. Distinct from `featuredBadges` in spec, not just in code: featured is admin-toggled-visible, multiple, subtle; title is user-chosen, singular, meant to read "like a rank or role" next to the creator's name. Propagating `titleBadge` into the feed, comments, or search cards is follow-on UI work, not assumed here. `getPublicProfile` filters the equipped `titleBadge` out of `featuredBadges` before returning — a creator can mark the same badge featured **and** as their title, and without this it would render twice on the profile (once as the title pill, once in the featured row). `titleBadge` also carries `showProfileRing` (from `Badge`, via `FeaturedBadgeView`) — the web profile only draws the rotating avatar ring when that's true, so a plain title badge gets the pill without the ring.

`User.heightCm`/`User.showHeight` (migration `20260820042407_add_user_show_height`) let a creator set a height and independently choose whether it's public — `showHeight` defaults to `false`, so height stays private until a creator opts in from the profile edit modal. `getPublicProfile` masks `heightCm` to `null` for any viewer except the profile owner (`showHeight || viewerId === id`), while `showHeight` itself is always returned as-is — it's a low-sensitivity preference flag, not the height value. `PATCH /creators/me` (`updateMe`) is the only write path for both fields; `product.repository.ts#listSeenOnCreators` applies the identical `showHeight`-gated mask to the height shown on a product's "seen on creators" rail, since that surface reads from the same `User` row via a different join.

`User.hideFromLeaderboards` rides the same `PATCH /creators/me` write path as `heightCm`/`showHeight` — one more boolean preference field on `UpdateCreatorProfileBody`, no new endpoint. Unlike `showHeight`, it isn't a display mask this module reads anywhere itself; it's consumed entirely by `../creator-leaderboard`'s stats query (`WHERE u.hide_from_leaderboards = false`), which excludes an opted-out creator from every leaderboard category at the source rather than filtering them out after the fact.

`handle` (username) change follows that same precedent: one more optional field on `UpdateCreatorProfileBody`, riding `PATCH /creators/me` rather than a separate endpoint or flow. The cooldown/availability/race-handling logic itself now lives in `../users`' `user.service.ts` (`prepareHandleChange`, `writeProfile`) rather than being duplicated here — `updateMe` just calls `userService.prepareHandleChange(user, input.handle)` to get back a `handleChangedAt` (only set when a real change is happening; re-saving other fields never touches the cooldown/uniqueness logic) and `userService.writeProfile` to perform the write. A change is still gated by the same **14-day cooldown** (`User.handleChangedAt`) — the same abuse/squatting concern most social platforms address with a cooldown — surfaced as a `HANDLE_CHANGE_COOLING_DOWN` 409 with the eligible date computed server-side, and availability is still checked twice: a pre-check inside `prepareHandleChange` (`userService.assertHandleAvailable`) gives a fast, friendly `HANDLE_TAKEN` 409 for the common case, and `writeProfile`'s try/catch still maps a P2002 on `users.handle` (`uniqueConstraintTargetIncludes`, `shared/utils/prisma.utils.ts`) to that same `HANDLE_TAKEN` 409 for the TOCTOU race the pre-check alone can't close. The `handle-change` rate limit (10/day, only when `req.body.handle` is present) now lives in `#middlewares/handle-change-rate-limit.ts` (`rateLimitHandleChangesOnly`) rather than as a local helper in `creator.routes.ts`, since `../users`' `PATCH /users/me` needs the exact same conditional limiter for its own now-generic handle-change path — see that module's README.

**Resolved gap:** `PATCH /creators/me` used to have no role/`isCreator` gate at all (`requireAuth` only), so a `BRAND_OWNER` — or, before this change, any signed-in account — could hit it directly and change `name`/`avatarUrl`/`heightCm`/`handle` despite the route being creator-scoped in intent. That's no longer an accidental gap: handle/name/avatar changes are now a deliberately generic, first-class capability of every `User` via `../users`' `PATCH /users/me`, and `PATCH /creators/me` only adds the creator-specific fields (`heightCm`, `showHeight`, `hideFromLeaderboards`) on top. `BRAND_OWNER`'s `handle` still isn't surfaced anywhere in the product (brand pages key off `Brand.id`).

**Known, accepted limitation:** a notification that deep-links to `/creator/<handle>?edit=<lookId>` (see `apps/web/src/features/creator-dashboard/README.md`) bakes the handle in at send time — an old unread notification's link 404s if the handle has since changed. Same class of issue every handle-based-URL platform has; not solved here (would mean resolving those deep-links by `userId` server-side instead).
