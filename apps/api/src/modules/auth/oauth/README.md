# OAuth (Google / Facebook sign-in)

## Purpose

Google and Facebook social login for `../` (the parent `auth` module) — a second way to prove identity and get the same session (JWT access token + rotating refresh token) the email/password flow already issues, not a parallel auth system. Also owns connecting/disconnecting a provider on an existing account, both proactively (Account Settings) and when sign-in discovers a provider email that already belongs to a password account.

## Structure

- `oauth.constants.ts` — `OAuthProviderParam` (enum: `GOOGLE = "google"`, `FACEBOOK = "facebook"`, the lowercase route/query-facing identifier), `OAuthFlowIntent` (enum: `SIGN_IN`, `LINK` — which of the two start/callback flows a given PKCE state belongs to), `OAuthCallbackStatus` (enum: `SIGNED_IN`, `LINK_REQUIRED`, `LINK_COMPLETED`), plus the PKCE state TTL and every route's rate-limit thresholds.
- `oauth.types.ts` — `OAuthProfile`, the normalized identity shape every provider adapter returns regardless of which provider it came from; `OAuthCodeExchangeInput`, the normalized input every adapter takes; `OAuthStateRecord` (a discriminated union on `intent` — the sign-in variant carries `redirectAfter`, the link variant carries `linkForUserId`); `OAuthLinkPendingRecord`, the Redis-stored sign-in-collision handoff shape; `OAuthIdentityResolution`, the service layer's callback outcome (a 3-way discriminated union on `status`).
- `oauth.schemas.ts` — zod request validation: `oauthProviderParamsSchema` (`:provider` route param against `OAuthProviderParam`), `oauthStartQuerySchema`, `oauthCallbackQuerySchema`, `oauthLinkConfirmBodySchema` (`{linkToken, password}`), `oauthUnlinkBodySchema` (`{password?}` — optional, since a password-less oauth-only account has none to re-prove).
- `oauth.repository.ts` — `oauthRepository`, the `OAuthIdentity` persistence layer: `findByProviderIdentity`, `createOAuthIdentity`, `findActiveOAuthIdentitiesForUser`, `findActiveIdentityForUserAndProvider`, `revokeOAuthIdentity`, `reviveOAuthIdentity` (un-revokes a previously-disconnected identity instead of trying to `create` a second row over the same `(provider, providerUserId)` unique constraint).
- `oauth.service.ts` — `oauthService.startOAuthFlow`/`startOAuthLinkFlow`/`handleOAuthCallback`/`confirmOAuthLink`/`unlinkIdentity`. Builds the PKCE challenge and provider authorization URL for either flow, consumes the Redis-backed state on callback, and branches on the state's `intent`: sign-in resolves to signing in an existing identity, flagging "link required" on an email collision, or auto-creating a new account; link resolves to attaching the identity to the already-authenticated caller.
- `oauth.controller.ts` — `oauthController.start`/`linkStart`/`callback`/`confirmLink`/`unlink`. `start`, `linkStart`, and `callback` are full browser navigations (not fetch calls), so they always end in an HTTP redirect; `confirmLink` and `unlink` are ordinary JSON endpoints. A callback failure never falls through to the JSON error handler mid-navigation — the controller catches it and redirects to the frontend's error page instead.
- `oauth.routes.ts` — `GET /:provider/start` (public, IP rate-limited), `GET /:provider/link/start` (`requireAuth`, IP rate-limited), `GET /:provider/callback` (public, shared by both flows), `POST /:provider/link/confirm` (public, IP rate-limited — the caller isn't authenticated yet, that's what this endpoint establishes), `DELETE /:provider/link` (`requireAuth`). Mounted flat at `/api/auth/oauth` in `app.ts`, alongside (not nested inside) `/api/auth`, matching this codebase's flat route-mounting convention.
- `oauth.utils.ts` — `sanitizeOAuthRedirectPath`, module-local open-redirect guard: only a same-origin relative path (`/...`, never `//...` or an absolute URL) is honored as the post-login destination; anything else falls back to `/`.
- `providers/google.provider.ts` — `exchangeGoogleAuthorizationCode`. Exchanges an authorization code for tokens via `google-auth-library`'s `OAuth2Client`, then verifies the returned `id_token`'s signature against Google's live JWKS (never decodes-and-trusts it) before returning an `OAuthProfile`.
- `providers/facebook.provider.ts` — `exchangeFacebookAuthorizationCode`. Exchanges an authorization code for a Graph API access token, then fetches the profile from `/me` with an `appsecret_proof` (HMAC-SHA256 of the access token, keyed by the app secret) on every call.

## Funnel

**User-facing flow — signing in:** clicking "Continue with Google/Facebook" navigates the whole page to `GET /api/auth/oauth/:provider/start`, which redirects again to the provider's own consent screen. After the user approves, the provider redirects back to `GET /api/auth/oauth/:provider/callback`. From there the browser lands on one of three places: straight back into the app already signed in (the original page they started from); the frontend's OAuth callback page asking them to confirm linking by re-entering their password (their provider email already belongs to an existing account — that page then calls `POST .../link/confirm`); or that same page showing a generic sign-in-failed message.

**User-facing flow — connecting from Account Settings:** an already-signed-in user clicks "Connect Google/Facebook" in Settings, which navigates to `GET /api/auth/oauth/:provider/link/start` (their existing session cookie/bearer token proves who they are). After the same provider consent screen, the callback attaches the new identity to their account and redirects back into Settings, either confirming the connection or reporting that the provider account is already connected elsewhere. Disconnecting a provider (`DELETE .../link`) asks for the account's password first, unless the account has none (a password-less, OAuth-only account) — in that case disconnecting is blocked outright if it's the account's only sign-in method.

**Technical flow:** `oauth.routes.ts` → `oauth.controller.ts` (`start`/`linkStart`) → `oauth.service.ts` generates a PKCE verifier/challenge and an opaque `state`, stores an `OAuthStateRecord` in Redis (`redisKeys.oauthState`, ~10 min TTL) tagged with `intent: SIGN_IN` (carrying `redirectAfter`) or `intent: LINK` (carrying the authenticated caller's `linkForUserId`) → redirects to the provider. On `callback`, `oauth.service.ts` atomically consumes the state (get + delete), calls the matching `providers/*.provider.ts` adapter to exchange the code, then branches on `intent`: sign-in resolves via `oauth.repository.ts` and `#modules/users/user.repository.ts` — reusing `issueTokens` from `../auth.service.ts` for actual session issuance, the same function password login uses; link attaches the identity to `linkForUserId` via the shared `createOrReviveOAuthIdentity` helper, issuing no new session since the caller already has one. A sign-in email collision stores an `OAuthLinkPendingRecord` in Redis (`redisKeys.oauthLinkPending`) keyed by an opaque `linkToken`; `POST .../link/confirm` looks that up, verifies the named account's password (reusing the same lockout counter as `/login`, via `../auth.lockout.utils.ts`), attaches the identity, and signs the user in. `DELETE .../link` re-verifies the caller's password when they have one, then blocks the disconnect with `ONLY_AUTH_METHOD` if it would leave the account with neither a password nor another active identity.

## Non-obvious rationale

Both provider adapters are deliberately symmetric — same input shape (`OAuthCodeExchangeInput`), same output shape (`OAuthProfile`), same failure behavior (every failure, at any step, collapses to one generic `AppError("OAUTH_EXCHANGE_FAILED", ...)` with the real cause logged server-side only, never in the response) — so the code that calls them doesn't need to special-case either provider. Neither adapter enforces "the email must be verified" as a hard rejection itself; each just reports what the provider said (`emailVerified: boolean` on Google, always `true` on Facebook since the Graph API only returns `email` at all for a confirmed address). Whether an unverified email blocks sign-in is a single policy decision applied in `oauth.service.ts`, identically to both providers, not duplicated per adapter.

Facebook's Graph API is called with `fetch` directly (matching `../../payments/providers/khalti.provider.ts`'s convention) rather than a Facebook SDK — there's no first-party Node SDK worth adding a dependency for, and the calls involved are two plain HTTPS requests.

PKCE/state and the pending-link handoff live in Redis with a short TTL, following the same ephemeral-state pattern already used for rate-limit counters and distributed locks (`#redis/redis.keys.ts`), rather than introducing a new session-middleware mechanism just for this flow.

`OAuthProviderParam`, `OAuthFlowIntent`, and `OAuthCallbackStatus` are real TypeScript enums, not string-literal unions — matching this codebase's existing `TokenPurpose`/`TokenTypeEnum` convention (`#constants/enums/auth.enum.ts`) and CLAUDE.md's "use enums, not bare strings" rule. `OAuthProviderParam`'s values stay lowercase (`"google"`, `"facebook"`) because they double as the literal `:provider` URL path segment and Redis-stored `state.provider` value — no separate string↔enum mapping layer is needed for routing, only the existing `PROVIDER_PARAM_TO_ENUM` map in `oauth.service.ts` to bridge into the Prisma-generated, uppercase `OAuthProvider` enum used for persistence.

Never auto-signs-in on an email match alone: finding an existing user by the provider's email with no prior `OAuthIdentity` row always returns `link_required`, never a session. Silently merging on email match would let anyone who controls a matching email address at the OAuth provider take over an existing Outfiqe account.

Signing in and connecting a new provider from Settings share the same `start`/`callback` route pair rather than getting entirely separate endpoints, because both genuinely need the same PKCE round-trip with the real provider to get a `providerUserId` — there's no way to "link" a provider without actually completing an OAuth handshake with it. What differs is only the `intent` carried in the Redis-stored state (set at `start` time, from which endpoint was hit and whether `requireAuth` passed) and what the callback does with the result — sign in vs. attach-and-redirect-to-Settings. The sign-in-time collision case (`link_required` → `POST .../link/confirm`) is a genuinely different, unauthenticated flow: the visitor isn't signed in yet, so there's no session to attach the new identity to — they have to prove ownership of the _existing_ account by password instead, which is also why it reuses `../auth.lockout.utils.ts`'s counter rather than being brute-forceable on a stolen `linkToken` alone.

`createOrReviveOAuthIdentity` (shared by the link-intent callback and `confirmOAuthLink`) revives a previously-revoked `OAuthIdentity` row instead of creating a new one when the same `(provider, providerUserId)` pair is being reconnected by its original owner — the `@@unique([provider, providerUserId])` constraint means a second `create` for the same pair would throw, and a revoked row is never deleted (`unlinkIdentity` only sets `revokedAt`), so reconnecting the same provider account after a prior disconnect has to go through the same row. If that pair belongs to a _different_ user, it's rejected with `OAUTH_IDENTITY_ALREADY_LINKED` instead — treated as identical to "currently linked" for this check, since silently letting a second account claim a provider identity a real account has already claimed (even if since disconnected) would be a takeover surface, not a convenience.

`unlinkIdentity` only requires re-proving the password when the account has one; a password-less, fully-OAuth account has nothing to re-prove and relies on `requireAuth` alone (the existing session already is the proof). Either way, the disconnect is still blocked with `ONLY_AUTH_METHOD` if it would leave the account with zero remaining sign-in methods — a password if there is one always counts as a second method on its own, so this only actually blocks a password-less account trying to remove its last connected provider.

`oauth.controller.ts`'s `callback` handler is the one place in this codebase where a caught application error is deliberately turned into a redirect instead of the global JSON `errorHandler` — because the caller mid-navigation is a browser following a `Location` header from Google/Facebook, not a script that can read a JSON error body. A failure during the link-intent flow currently redirects to the same generic sign-in error page as a failed sign-in, rather than back into Settings with an inline error — an acceptable interim UX gap since the Settings page consuming this doesn't exist until the frontend chunk; revisit once it does.
