# Auth

## Purpose

Identity and session management: email/password registration and email verification, login/logout, access/refresh token issuance and rotation, forgot/reset password, and the invite-gated registration flows for brand owners and admins.

## Structure

- `auth.service.ts` — `register`/`verifyEmail`/`resendVerification`, `login`, `refresh` (rotating, browser-facing) / `validateSession` (non-rotating, SSR-facing), `logout`, `forgotPassword`/`resetPassword`, `registerBrand`/`getBrandInvite`, `registerAdmin`/`getAdminInvite`, `validateToken` (generic invite/purpose-token existence check), `getCurrentUser`.
- `auth.controller.ts`, `auth.routes.ts` — thin HTTP layer. `/register`, `/verify-email`, `/login`, `/refresh`, `/session`, `/logout`, `/forgot-password`, `/reset-password`, `/resend-verification` are public; `/register/brand` and `/register/admin` require a valid invite token instead of a signed-in session; `/me` requires `requireAuth`.
- `auth.schemas.ts` — zod schemas + inferred body/query types for every route above.
- `auth.repository.ts` — refresh-token and brand-invite/brand-membership persistence. Admin invites live in `../admin-invites/adminInvite.repository.ts`, not here.
- `auth.constants.ts` — `PURPOSE_ERROR_COPY`, the user-facing invalid/expired copy per `TokenPurpose`; refresh-token retention window/sweep interval; rate-limit windows/thresholds for every route below; login lockout window/threshold.
- `auth.lockout.utils.ts` — `recordFailedLogin`/`resetFailedLogins`/`isLockedOut`/`getFailedLoginCount`, a Redis-backed per-account failed-login counter, independent of the rate limiters above.
- `auth.captcha.utils.ts` — `verifyCaptcha`, a server-to-server check against Cloudflare Turnstile.
- `auth.retention.ts` — scheduled sweep that hard-deletes refresh tokens once they're past the retention window (revoked or expired), registered in `apps/api/src/jobs/scheduled-jobs.ts`. This is cleanup only, not part of the security model itself — a token stops being usable the moment it's revoked or expired, regardless of when this sweep gets to it.
- `auth.types.ts` — `AuthSession`/`BrandAuthSession`, `AuthUser`/`BrandAuthUser`, invite/record shapes.
- `oauth/` — Google/Facebook social login, as a sub-module. See `oauth/README.md`.

## Funnel

**User-facing:** sign up with name/email/phone/password → a verification email is sent (console-logged in dev/test when `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` aren't set, see `#lib/email.utils.js`) → clicking the link verifies the email → sign in issues an httpOnly `refresh_token` cookie plus a non-httpOnly `has_session` flag cookie (so the client can skip a doomed refresh call when definitely logged out) and an in-memory access token. Forgot/reset password works the same way, off a short-lived signed purpose token, and invalidates every existing session on success. Brand owners and admins never self-register — they redeem a time-limited invite link (issued elsewhere: brand-application approval, admin invite creation) via `/register/brand` / `/register/admin`.

**Technical:** access tokens are short-lived JWTs (`#lib/generate-token.utils.js`); refresh tokens are opaque random values, stored server-side only as a SHA-256 hash (`#lib/opaque-token.utils.js`) with an expiry, and are single-use — `POST /refresh` rotates the presented token rather than deleting it outright (see below), and issues a new pair. `POST /session` intentionally does **not** rotate: it exists for server-side session checks (SSR pages) that call it on every render and have no way to propagate a `Set-Cookie` back to the browser, so rotating there would burn the browser's refresh token on its first server-side use — it does still reject a token that's been rotated out by a real `/refresh` call, same as any other invalid token. Email-verification and password-reset links are stateless signed JWTs (`signPurposeToken`/`verifyPurposeToken`, `#lib/purpose-token.utils.js`) scoped by `TokenPurpose`, not persisted anywhere — nothing to look up, just verify the signature/expiry/purpose claim. `POST /refresh` and `POST /logout` additionally require a `X-CSRF-Token` header matching a non-httpOnly `csrf_token` cookie (`#middlewares/csrf.js`) — see below.

## Non-obvious rationale

`forgot-password` and `resend-verification` both return the same success response whether or not the email is registered, and `resendVerification`/`forgotPassword` no-op silently for an unknown or already-verified address — this is deliberate enumeration resistance, not a missing error case. `verifyEmail`/`resetPassword` extend the same principle to their token's subject: if the token verifies but the user it names no longer exists (deleted account), the response is the identical generic `INVALID_TOKEN` shape used for a malformed/expired token, not a distinguishable `USER_NOT_FOUND` — otherwise the response itself would leak whether a given account ever existed.

Passwords are hashed with argon2id (`#lib/password.utils.js`); a legacy `scrypt:`-prefixed hash (this module's original algorithm) still verifies correctly, and a successful login against one transparently re-hashes and persists it as argon2id in the background (`login` never blocks on this). `register` and `resetPassword` also reject a password found in the HaveIBeenPwned breach corpus (`#lib/password-breach.utils.js`, k-anonymity range lookup) — this check fails open (allows the password through) on any network/API error, since a third-party outage should never block someone from signing up or resetting their password.

`/login`, `/register`, `/refresh`, and `/reset-password` are all rate-limited (`#middlewares/rate-limit.js`, the same Redis-backed limiter `/forgot-password`/`/resend-verification` already used) — `/login` and `/refresh` additionally rely on `req.ip`, which is why `app.ts` sets `app.set("trust proxy", 1)`: without it, every request behind this app's reverse proxy would resolve to the proxy's own IP and share one rate-limit bucket. `/login` layers two limiters (per-IP, then per-email) so a distributed credential-stuffing attempt and a targeted single-account attempt are both caught; `/register`/`/refresh`/`/reset-password` are IP-only since they either have no stable per-account key to limit on or are already covered by another mechanism (`/refresh` by reuse detection above).

`login()` also tracks failed attempts per account independently of the rate limiters, via `auth.lockout.utils.ts` — once an account crosses `LOGIN_LOCKOUT_THRESHOLD` failures within `LOGIN_LOCKOUT_WINDOW_MS`, further attempts are rejected with the exact same generic `INVALID_CREDENTIALS` response as an ordinary wrong password, checked _before_ the password is even verified, and _including when the correct password is supplied_ — anything that responded differently while locked would itself become a way to test whether an account exists or guess when a guess finally lands. A successful login resets the counter; the rate limiters above throttle request volume regardless of outcome, while lockout specifically tracks failures against one account, so both apply — a script spraying passwords against many accounts trips the IP limiter, one spraying passwords at a single account trips lockout, often before either rate limiter would.

Every cookie-authenticated, state-changing request the two flags carrying the actual `refresh_token` cookie touch (`/refresh`, `/logout`) is also gated by a double-submit CSRF token: `setRefreshCookie` sets a non-httpOnly `csrf_token` cookie alongside `refresh_token`, and `requireCsrfHeader` (`#middlewares/csrf.js`) rejects the request unless the `X-CSRF-Token` header matches it exactly. This is deliberately scoped to only these two routes, and only fires when a `refresh_token` cookie is actually present — every other state-changing route in this app authenticates via a `Bearer` access token instead of a cookie, which a cross-site request can't forge, and a request with no session cookie has nothing to protect (this is also what keeps `/logout`'s existing "succeeds silently with no refresh token" no-op behavior intact). `packages/client`'s shared `createApiClient` reads the cookie and attaches the header automatically on every request, including the one raw `axios.post` call inside `refreshAccessToken` that bypasses its own interceptors — so this one change covers `apps/web` and `apps/admin` for free, since both already consume that same factory. `SameSite=Strict` on these cookies already blocks the classic cross-site-form CSRF attack on its own; this is a defense-in-depth layer for the cases that doesn't cover (same-site script injection, older browsers, proxies that don't fully honor `SameSite`), which is also why it's a plain double-submit token rather than a server-side session store this codebase doesn't otherwise have.

Every login-adjacent outcome — register/login success and failure, lockout, captcha rejection, refresh success and reuse-detection, logout, password-reset success — logs through a shared `auditLog` helper as one structured line (`event`, `outcome`, `userId`/`email` where known, `ip`) instead of an ad hoc message string, so these are actually queryable in the log files (the console transport still only prints the human-readable message; the structured fields land in the JSON file transports). Deliberately scoped to the events this file's own module README and the repo's `CLAUDE.md` explicitly call out (`register`/`login`/`lockout`/`refresh`/`reuse-detected`/`logout`/`reset`/`captcha-failed`) — `verifyEmail`/`resendVerification`/`forgotPassword`/`registerBrand`/`registerAdmin` still use the older plain-message `logger.info`/`warn` calls, not yet converted.

`register` always requires a passing Turnstile token (`auth.captcha.utils.ts`); `login` only starts requiring one once an account's failed-login count reaches `LOGIN_CAPTCHA_CHALLENGE_THRESHOLD` — lower than `LOGIN_LOCKOUT_THRESHOLD`, so a script gets a bot challenge before it gets locked out, while an ordinary person who mistypes their password once or twice never sees a challenge. Unlike the breach-password check, `verifyCaptcha` fails _closed_ (treats a Turnstile outage or misconfiguration as "not verified") rather than open — a broken bot check should not silently become no bot check on a public write endpoint, whereas a broken breach-password check blocking every signup would be the more harmful failure mode. `CAPTCHA_ENABLED`/`PASSWORD_BREACH_CHECK_ENABLED` are parsed with `z.stringbool()`, not `z.coerce.boolean()` — `Boolean("false")` is `true` in JavaScript, so `z.coerce.boolean()` would silently treat the literal string `"false"` from an env file as enabled; `z.stringbool()` (zod v4) parses the string's actual meaning instead.

`User.passwordHash` (owned by `../users`) is nullable — an account created entirely through an OAuth provider (Google/Facebook, see the `oauth` subfolder) never has one. `login()` guards every read of it accordingly and still returns the exact same generic `INVALID_CREDENTIALS` response for a null-hash account as it does for a wrong password on a real one — an "this account has no password" response would itself reveal that the account is OAuth-only, which is exactly the kind of account-existence/shape leak the rest of this module already avoids.

Refresh tokens carry a `familyId` shared by every token descended from the same original login, and rotation soft-revokes the presented token (`revokedAt` + `replacedByTokenHash`) instead of deleting it — the row stays around specifically so a _second_ attempt to use that same already-rotated token can be recognized as token reuse (a stolen/replayed token racing the legitimate client) rather than looking identical to "token never existed." When reuse is detected, the entire family is deleted, not just the offending token — this forces every device on that session, including the legitimate one, to sign in again, which is the correct response to a suspected compromise even though it's disruptive. Rotation revokes the old token _before_ creating its replacement (not after) specifically so a failure between the two steps can never leave both the old and new token simultaneously valid.

`AuthUser` (regular users, not `BrandAuthUser`) carries `handle` — added specifically so the frontend can build a `/creator/{handle}` link to the signed-in user's own profile without a second lookup (the notifications bell's click-to-navigate needs it for `LOOK_LIKED`/`LOOK_COMMENTED`, see `apps/web/src/features/notifications/README.md`). `BrandAuthUser` deliberately doesn't get one — brand owners have no public creator-profile page to link to.

`BrandAuthUser` carries `hasPlatformAccess` even though a business account's own dashboard (`apps/web`) never reads it. `apps/admin` now accepts `BRAND_OWNER` sign-ins too (see `crm-access`'s README on business-picker organization onboarding), and its `AdminUser` schema requires this field unconditionally — `getCurrentUser`'s `BRAND_OWNER` branch used to build a separate object literal that omitted it entirely, which passed every test that existed at the time (none exercised a brand owner calling `/auth/me` from `apps/admin`) but failed Zod validation the moment a real business account tried to sign into `apps/admin`, surfacing as an infinite sign-in redirect loop rather than a clear error, since the failure happened inside `AuthContext`'s session-restore `try` block. `apps/web`'s own `brandUserSchema` doesn't declare the field, so it's silently ignored there — Zod strips unknown keys by default rather than rejecting them.

The same `getCurrentUser` object-literal split bit `phone` too: `AuthUser` already carried it, but the `BRAND_OWNER` branch's separate literal didn't, so `apps/web`'s own Security settings page — which reads `phone` off the signed-in `UserSession` to decide whether to prompt "add a phone number" — always saw `null` for a brand owner regardless of the real value on their account, since `toUserSession`'s `"phone" in user ? user.phone : null` had nothing to read. Unlike `hasPlatformAccess`, this one does matter to `apps/web`, so `phone` was added to both `BrandAuthUser` and `apps/web`'s own `brandUserSchema` (a brand user was never getting a real phone value out of that schema either, for the same "field not declared" reason `hasPlatformAccess` doesn't reach `apps/web` at all).

## Follow-ups

- Integration coverage (`auth.integration.test.ts`) currently covers the core identity/session surface: register, verify-email, resend-verification, login, refresh, session, logout, forgot-password (including its rate limit), reset-password, and `/me`. It does **not** yet cover `registerBrand`/`registerAdmin`/`getBrandInvite`/`getAdminInvite`/`validateToken` — those depend on invite provisioning from `../brand-applications` and `../admin-invites`, which is a natural next phase rather than part of this pass. Once added, `src/modules/auth/**` should go into `vitest.config.ts`'s `coverage.include` allowlist (left out for now since partial coverage would fail the 80% gate).
- `packages/client`'s CSRF-header-attachment logic (`getCsrfTokenFromCookie`, the request interceptor, and the raw-`axios.post` path inside `refreshAccessToken`) has no automated test — no package under `packages/*` has any test infrastructure set up yet (no vitest config/devDependency/test script anywhere in that directory), unlike the three apps, which each define `unit`/`integration` vitest projects. Standing up testing for a shared package for the first time is a repo-wide convention decision bigger than this one change, so it was flagged rather than added unilaterally. Server-side CSRF enforcement itself is covered by `auth.integration.test.ts`.
- `verifyEmail`/`resendVerification`/`forgotPassword`/`registerBrand`/`registerAdmin` still log with the older plain-message `logger.info`/`warn` calls rather than the structured `auditLog` helper `register`/`login`/`refresh`/`logout`/`resetPassword` now use — bringing them in line is a natural follow-up, not done here since none of those five were in the specific event list this pass targeted.
