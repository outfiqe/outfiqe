# creator-looks

## Purpose

Creator-posted "looks" (outfit photos with tagged products): posting, editing, deleting, the public explore feed, likes/saves/comments, tag-click attribution, and trending tags.

## Structure

- `creatorLook.routes.ts` — route table. Static/prefixed paths (`/feed`, `/tags/trending`, `/search`, `/saved`) are registered before the `/:lookId`-shaped routes so Express doesn't swallow them.
- `creatorLook.controller.ts` — request/response glue; no business logic.
- `creatorLook.service.ts` — ownership checks, approval gating, worn-by recount orchestration, domain events, and the `runTrendingAggregation`/`runTrendingScoring`/`runTagTrendingAggregation`/`runTagTrendingScoring` scheduled-job entry points for post and hashtag trend scoring.
- `creatorLook.repository.ts` — Prisma queries, cursor pagination, the Redis-cached trending snapshot/tags, and the post + hashtag trend-scoring pipelines (metric bucket upserts, candidate scoring, ranked-score caches).
- `creatorLook.schemas.ts` — Zod request validation.
- `creatorLook.types.ts` — response/DTO shapes, plus `PostMetricBucket`/`PostTrendMeta`/`PostScoreBreakdown`/`PostTrendingEntry` and `TagMetricBucket`/`TagScoreBreakdown` for post and hashtag trend scoring.
- `creatorLook.constants.ts` — job intervals and signal weight/decay/window tuning constants for post and hashtag trend scoring.
- `creatorLook.utils.ts` — this module's cursor payload shapes (`SimpleCursor`, `TrendingSnapshotCursor`, `FeaturedLookCursor`), the `toSummary`/`toEditDetail` mappers, and the post/hashtag trend-scoring math (`scorePost`, `scoreTag` and their helpers). The `encodeCursor`/`decodeCursor` codec itself lives in `#lib/pagination.utils.js` — shared with `trending`'s own snapshot-cursor pagination (see `../trending/README.md`), since it's a generic base64url JSON codec with nothing creator-look-specific about it.
- `creatorLook.socket.ts` — the `FEED_SYNC_REQUEST` socket handler (new-post count for the open feed tab).

## Funnel

**User-facing:** a creator posts a look with photos, a caption, and tagged products from their profile. Other users see it in the explore feed, can like/save/comment, and click a tag to jump to the product. The creator can edit the photos/caption/tags or delete the post from their own profile at any time.

**Technical:** `creator-profile`/`creator-dashboard` (web) → `creatorLook.routes` → `creatorLook.controller` → `creatorLook.service` → `creatorLook.repository` → Postgres via Prisma, with Redis caching the trending snapshot/tags.

## Non-obvious rationale

- **Soft delete only.** `CreatorLook.deletedAt` exists because `OrderItem.attributedLookId` can reference a look for commission history — deleting a look must never orphan a past order's attribution. `remove()` sets `deletedAt`; every read path already filters `deletedAt: null`.
- **`PATCH /:lookId` reuses `createCreatorLookSchema`** rather than a separate update schema — both now require the same full `imageUrls`/`caption`/`taggedProducts` shape, since editing replaces the whole set of images and tags rather than patching individual fields. `update()` fully replaces `CreatorLookImage`/`CreatorLookProduct`/`CreatorLookHashtag` rows for the look inside one transaction; the client is responsible for sending the complete surviving + newly-uploaded image URL list (existing images aren't re-cropped, only added/removed — see `creator-dashboard`'s README for why).
- **`GET/PATCH/DELETE /:lookId` are all owner-scoped**, not public. They 404 (not 403) when the look doesn't exist _or_ isn't owned by the caller, so a creator can't probe for other creators' look IDs.
- **`recountWornBy` is called per affected product ID**, not via `recountWornByForCreator`. That helper only recomputes for products the creator _currently_ tags — it would miss a product that was tagged and then fully untagged in an edit (or removed via delete), leaving its `wornByCount` stale. `update`/`remove` instead diff old vs. new tagged product IDs and recount each one directly, mirroring what `create` already does.
- **`GET /creator-looks/search` (`searchLooks`) matches a post's caption, its hashtags, _or its creator's handle/name_**, ranked by `pg_trgm`/prefix matching via the hand-written `search_creator_looks` Postgres function (migration `20260818150000_add_creator_and_look_search`, extended in `20260818160000_match_creator_in_look_search`) — same pattern as product search (`../products/README.md`). A hashtag match (`#winterlayers`, with or without the `#`, matched by prefix) always outranks a fuzzy caption or creator match, since a deliberate tag is a much stronger relevance signal than a substring match. The creator-name/handle branch exists so that searching "Sabin" on the explore search page surfaces that creator's posts alongside their profile, not just posts whose caption happens to say "Sabin" — matching what `../creators/README.md`'s `search_creators` already does for the Creators section of the same page. It reuses that module's tuned `0.5` trigram threshold (not `0.4`, like the caption-only matching) for the same reason: `handle`/`name` are short strings where a lower threshold produces real false positives (see the creators module README for the "kastha"/"Shrestha" example) — a single `SET pg_trgm.word_similarity_threshold` applies to the whole function, so raising it protects the new creator-name branch without needing two separate functions. `searchLooks` returns ranked ids + `total` from the SQL function, then reuses the same `hydrateFeedPosts` every other read path (`feed`, `listFeaturedLooks`, `feedByCreatorId`, `listSaved`) already goes through, so a searched post has the exact same shape (like/save state, tagged products, `isFollowingCreator`) as one found any other way. Offset-paginated (`SearchLooksCursor { offset }`) rather than the id/engagement-keyset cursors the rest of this module uses, for the same reason product search is offset-paginated — rank isn't a stable column to seek on.
- **`GET /creator-looks` (`listFeaturedLooks`) returns full look posts, not products.** It used to dedupe `CreatorLookProduct` rows by `productId` ordered by `createdAt desc` — i.e. "whichever look tagged this product most recently" — and hand back bare product cards, discarding the look's photo/caption/creator/engagement entirely. It now finds, per tagged product, the single look with the highest `like_count*2 + comment_count + save_count` (via a raw `DISTINCT ON (product_id)`, since that per-group ranking isn't expressible through Prisma's declarative `orderBy`) and returns the hydrated `CreatorLookFeedPost` itself. A `GROUP BY look_id` on the outer query collapses the rare case where the same look happens to be the top pick for two different tagged products, so the homepage rail never shows the same photo twice. The cursor changed shape accordingly — it now encodes `{ engagement, lookId }` instead of a raw `CreatorLookProduct` UUID, so `listCreatorLooksQuerySchema.cursor` is a plain string, not `z.uuid()`.

### Explore trending tab — post trend scoring

**Why this exists.** The Explore "Trending" tab (`GET /creator-looks/feed?tab=trending`, unchanged route/shape) used to rank posts purely by `like_count*2 + comment_count + save_count` — a flat weighted sum with no time decay, so a post's rank never faded once it had accumulated engagement, and a genuine spike looked the same as slow accumulation over weeks. It now scores posts with the same real-time decay/velocity/baseline/momentum approach `../trending` already built for products (`GET /products/trending`), adapted to the signals a _post_ actually has (likes, comments, saves, tag clicks — no purchases/cart-adds, posts aren't sold).

**Shape, partially shared code with `../trending`.** The generic, verbatim-reusable pieces — decay weighting, bucket age, `computeOwnBaseline`/`sumDecayedActivityInWindow` (generic over any `{ bucketStart: Date }` bucket plus an `activityOf` extractor), `meanOf`, the diversity-cap and weighted-rotation shuffle — live in `#lib/trend-scoring.utils.js` (`apps/api/src/shared/utils/trend-scoring.utils.ts`). `computeOwnBaseline`/`sumDecayedActivityInWindow` were promoted from a per-module copy to this generic shape once a _third_ near-identical implementation (hashtags, below) would otherwise have existed — see this repo's shared-code rule. Everything that's genuinely shaped differently per entity — bucket activity weighting (`bucketActivity`/`postBucketActivity`/`tagBucketActivity`, one per module since the raw signal fields differ), the baseline tier count, and each `score*` composition function — stays local. Posts and hashtags share the same two-tier own/global `pickBaseline` shape (neither has a natural "category" the way `Product.type` gives products a third tier), but that two-line discriminated-union function isn't worth extracting on its own — the value was in the generic math underneath it, not in the four-line dispatch on top.

**No diversity/rotation pass, unlike the product homepage rail.** `../trending`'s `getTrendingProductIds` (short homepage rail) applies `applyDiversity` + `applyWeightedRotation` because a 5–30 card rail needs brand variety and shouldn't reshuffle every request. The Explore trending tab is a paginated infinite-scroll feed, not a capped rail — same situation as `../trending`'s own paginated `sort=trending` browse (`listTrendingProductIds`), which also skips both and paginates the full score-sorted list so a user scrolling through it sees the objectively highest-scoring posts in order, with stable results across requests within one session (the existing `{ sessionId, offset }` snapshot cursor already did this job and needed no changes).

**Two-cycle job, cache-aside with cold-start fallback — same shape as `../trending`.** `explore-trending-aggregation` (every 15 min) recomputes the current open hour's `CreatorLookTrendMetric` row per post per signal from scratch (not increment, for the same idempotency reason as `../trending` — see its README), then deletes buckets older than 14 days. `explore-trending-scoring` (every 30 min) scores every post with a recent bucket and writes the ranked list to `cache:explore-trending-score:global` (TTL 40 min). `buildTrendingSnapshot` reads that cache; on a miss it falls back to scoring synchronously (cheap — the aggregation already did the expensive table scans); if the ranked list is empty (no engagement activity scored yet — a fresh environment, or between deploy and the first aggregation cycle), it falls back further to the pre-existing flat engagement-sort query (kept as `buildLegacyTrendingSnapshot`) so the tab is never empty while data collects.

**Raw `$executeRaw` upserts must set `updated_at` on the `INSERT` branch, not only `ON CONFLICT DO UPDATE`.** `@updatedAt` in the Prisma schema only auto-populates through Prisma Client calls — it has no DB-level `DEFAULT`, so a raw SQL `INSERT` that omits the column hits a `NOT NULL` violation on every first-ever insert of a new `(creatorLookId, bucketStart)` row. This surfaced (and was fixed) in both this module's new upserts and `../trending`'s pre-existing, identically-shaped ones while building this feature.

### Explore "For you" tab — personalized re-ranking

**Why this exists.** `for_you` (the Explore feed's default tab) used to be a plain alias for `trending` — same query, same order, for every viewer, personalized or not. It now genuinely diverges per viewer: same trending candidate pool and base scores, re-ranked by the viewer's own follow graph and engagement history. A guest, or a signed-in viewer with no follows/engagement yet, still sees exactly the trending order — the personalization degrades to a no-op rather than needing a separate cold-start branch, because every affinity boost is additive on top of a multiplier that starts at `1`.

**Deliberately re-ranks the trending pool rather than sourcing its own candidates.** `following` (chronological, only accounts you follow) already covers "everything from people I follow." `for_you`'s job is discovery within what's already resonating broadly, weighted toward this viewer's taste — not a personalized duplicate of `following`. So it starts from the same cached trend-scored candidates `trending` uses (`EXPLORE_TRENDING_SCORE_CACHE_KEY`, falling back to `computeRankedLookScores()` on a cache miss and to `buildLegacyTrendingSnapshot()` if there's no scored activity yet at all — same three-tier fallback as `trending`), then multiplies each candidate's trend score by a per-viewer affinity multiplier and re-sorts. A post still needs real momentum to be a candidate at all; personalization decides ordering among posts that already earned a look, not which posts exist.

**Affinity signals, computed fresh per request, not pre-cached per viewer.** `fetchEngagementAffinity` (in `creatorLook.repository.ts`) unions the viewer's own `creator_look_likes`/`saves`/`comments` from the trailing `FOR_YOU_ENGAGEMENT_LOOKBACK_DAYS` (60 days) to derive which creators they've engaged with and which hashtags recur in what they engage with — one raw SQL query, since it's a `UNION` across three tables feeding a `GROUP BY`-shaped aggregation that Prisma's query builder can't express declaratively (same "raw SQL for computed-value aggregation" exception the Database Queries convention documents). Followed-creator IDs come from `followRepository.listFollowingIds`, reused as-is rather than reimplemented — it's the same data `following`'s own tab already needed, fetched at the service layer and threaded down, not duplicated as a second query. Neither signal is cached per-viewer: the candidate pool is already small (bounded by `trending`'s own 7-day recent-activity window), so re-scoring it against a freshly-read affinity is cheap enough to do per request, and avoids a whole second per-user cache-invalidation surface for a feed a viewer might open dozens of times a day.

**Boost shape: multiplicative, capped, additive across signals — not a separate sort key.** `scorePersonalized` starts each candidate at multiplier `1` and adds `FOR_YOU_FOLLOW_BOOST` (0.6) if the viewer follows the post's creator, else `FOR_YOU_ENGAGED_CREATOR_BOOST` (0.3) if they've engaged with that creator before without following (follow and past-engagement don't stack — following is the stronger, more deliberate signal), plus a hashtag-overlap term capped at `FOR_YOU_HASHTAG_BOOST_CAP` (0.4) so no single viewer-history quirk can dominate the score. The result multiplies the trend score rather than replacing it, so a post with negligible trend momentum can't out-rank a genuinely trending one just because the viewer follows its creator — see the worked example below.

**Diversity cap reuses the same generic `applyDiversity` as `trending`'s homepage rail**, keyed by `creatorId` (`FOR_YOU_MAX_PER_CREATOR`, 3) instead of `brandId` — a personalized re-rank that promotes followed creators is exactly the shape most likely to let one prolific followed creator flood the whole feed, so the cap matters more here than it does for the un-personalized trending list.

**Verified against real, seeded data, not just unit logic:** a guest and a signed-in viewer see the identical trend-sorted order; a second viewer who follows the creator behind the third-ranked (score ≈4.34) post sees that post jump above the second-ranked (score ≈4.72) one — `4.34 × 1.6 > 4.72` — while the dominant top-ranked post (score ≈169) stays first for every viewer regardless of who they follow, confirming the boost amplifies rather than overrides.

### Trending tags — hashtag trend scoring

**Why this exists.** `GET /creator-looks/tags/trending` (the Explore sidebar's "Trending tags" list) used to be `COUNT(*) GROUP BY tag` over a flat rolling 7-day window — a tag used on 9 posts spread evenly across 6 days ranked identically to one used on 9 posts in the last hour, and a hashtag that just started spiking had no way to out-rank one that was merely used a lot, slowly, days ago. It now runs the same decay/velocity/momentum pipeline as `trending`/`for_you`, scored off a single signal (`postCount` — how many posts newly carried that tag in each hour bucket), via a new `HashtagTrendMetric` table and its own `explore-tag-trending-aggregation`/`explore-tag-trending-scoring` job pair, on the same 15/30-minute cadence.

**Single-signal by necessity, not by a scoped-down choice.** Posts have four independent event tables (likes, saves, comments, tag clicks) to weight; a hashtag only has one real raw signal — "a post used this tag, at this timestamp" (`creator_look_hashtags` joined to `creator_looks.created_at`). There's no `HashtagLike` table and no reason to invent one. `TAG_TREND_SIGNAL_WEIGHTS` is deliberately a single constant (`TAG_TREND_SIGNAL_WEIGHT = 1`) rather than a record, so `tagBucketActivity` is just `log1p(postCount)` — the log1p dampening (same reason every other `*BucketActivity` function uses it) still applies, so one viral post doesn't single-handedly declare a tag "trending."

**No freshness multiplier, unlike posts and products.** `isWithinFreshnessWindow`/`isWithinPostFreshnessWindow` reward an entity for being newly _created_ (a new product or post gets a boost for its first few days so it isn't buried under established competition). A hashtag string isn't "created" at a point in time the way a row is — `CreatorLookHashtag` has no `createdAt` column, only a composite key — so there's no honest timestamp to hang a freshness multiplier off without adding a schema column purely to serve a multiplier of dubious value for a recurring, not-owned-by-anyone concept. `scoreTag`'s `score` is `decayedActivity * momentum`, no third term — momentum (velocity × baseline-lift, capped) already does the real work of surfacing a hashtag that's spiking right now.

**`fetchTrendingTags` follows the identical three-tier read path as `buildTrendingSnapshot`:** read the scored cache (`cache:explore-tag-trend-score:global`, `EXPLORE_TRENDING_SCORE` TTL, 40 min) → on a miss, compute synchronously from `HashtagTrendMetric` buckets → if the scored candidate list is empty (fresh environment, or between deploy and the first aggregation cycle — recall the aggregation job only ever populates the bucket for the hour it's currently running in, so pre-existing historical tag usage never backfills into scored buckets), fall back to the pre-existing flat `COUNT(*)` query (kept as `fetchLegacyTrendingTags`, with its own short-lived 10-minute cache, untouched). The public response shape (`{ tag, postCount }[]`) is unchanged; `postCount` now reports the scored candidate's raw recent-window count rather than the 7-day total, but nothing in the frontend currently renders that number (checked — it's schema-validated but not displayed), so this is a safe, non-breaking swap.

**Verified against real, seeded data:** with no scored buckets yet, the endpoint returns byte-for-byte the same tag list the old flat-count query produced. After creating one real post (via `creatorLookService.create`, not a raw insert) carrying two brand-new hashtags and running both jobs, those two hashtags — each with a single recent post — immediately outrank every pre-existing tag with 3–9 historical uses, because their decayed activity is fresh and their velocity is undefined-high (zero activity in the previous window), while the old tags have no bucket at all yet and simply aren't candidates. This is the intended behavior, not an edge case: a real spike should beat a stale plateau.
