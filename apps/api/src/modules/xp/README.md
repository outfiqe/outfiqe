# xp

## Purpose

The XP engine: awards XP for qualifying platform activity, enforces the anti-abuse rules an admin configures per activity, and keeps each user's running level (spec 08/09) in sync. Owns `Level` alongside XP — a level is a pure function of `totalXp`, with no independent write path of its own, so it doesn't warrant a separate module (same reasoning `commissions` bundles tier config with the commission ledger).

## Structure

- `xp.types.ts` — `LevelRecord`, `ActivityXpConfigRecord`, `AwardXpInput`/`AwardXpResult`, `UserProgressView`, `XpMultiplierRecord`, `ActiveXpMultiplierView` (the public read shape — `label`/`multiplier`/`endsAt` only, no `id`/`isActive`/`startsAt`, since a caller only ever needs to know "is one live and when does it end," not the full admin record).
- `xp.constants.ts` — `ONE_DAY_MS` (anti-abuse window), `XP_SOURCE` (the `source` values callers pass — one per producing module), `MIN_XP_MULTIPLIER`/`MAX_XP_MULTIPLIER` (1–10, a sanity cap against an admin fat-fingering an absurd value, not a business rule).
- `xp.utils.ts` — pure functions only: `computeLevelProgress` (resolve a user's level + next level from a sorted ladder), `xpToNextLevel`, the three anti-abuse predicates (`hasReachedMaxPerEntity`, `isWithinCooldown`, `hasReachedDailyLimit`), and `applyMultiplier` (base amount × the active multiplier, rounded to the nearest whole XP — see rationale below). No DB access — this is where the unit tests live.
- `xp.repository.ts` — Prisma queries only. Functions that participate in the award transaction (`createTransaction`, `incrementProgress`, `setCurrentLevel`) take a `DbClient` parameter so `xp.service.ts` can compose them inside one `prisma.$transaction`, same pattern as `commissions`' `createPending(client, input)`. `findActiveMultiplier(now)` finds the single highest-multiplier `XpMultiplier` window whose range contains `now` and is `isActive: true` — see rationale below for "highest wins" over stacking.
- `xp.service.ts` — `awardXp`/`grantFixedXp` (both funnel into the private `applyXpTransaction`, which also publishes `DomainEvents.LEVEL_UP` when the award crosses a level boundary) and `getProgressForUser`. Admin-only: `listLevels`/`createLevel`/`updateLevel`, `listActivityConfigs`/`updateActivityConfig`, `listMultipliers`/`createMultiplier`/`updateMultiplier`, `adjustXp` (manual grant/dock with a mandatory reason, spec 32), `getAdminStats`. `getActiveMultiplier` (not admin-only — any authenticated user can read it) backs the "an XP event is live" banner.
- `xp.events.ts` — `registerXpEventConsumers()`: subscribes to the platform domain events (`LOOK_CREATED`, `LOOK_LIKED`, `LOOK_SAVED`, `LOOK_COMMENTED`, `USER_FOLLOWED`, `PRODUCT_PURCHASED`, `SALE_GENERATED`, `PRODUCT_TAGGED`) via `subscribeToDomainEvent` and calls `awardXp` with the right activity type per event. Registered once at boot in `index.ts`, same as `registerLeaderboardEventConsumer`.
- `xp.socket.ts` — `registerXpSocketEventConsumer()`: a second, independent `socket-broadcast` consumer group on `DomainEvents.LEVEL_UP` (published by `applyXpTransaction`, not `xp.events.ts` — that file only consumes events, it doesn't produce them) that emits `SOCKET_EVENTS.LEVEL_UP` to the leveling-up user's own room. Same shape as `leaderboard.socket.ts`'s event consumer.
- `xp.schemas.ts` / `xp.controller.ts` / `xp.routes.ts` — `GET /api/xp/me` (progress, spec 09), `GET /api/xp/me/transactions` (paginated ledger, spec 07), and `GET /api/xp/multiplier/active` (spec 20's "is an event live" read), all `requireAuth`-only — no creator-status gate, since every user (not just creators) earns and can view their own XP. Admin-only (`requireRole(ADMIN)`, spec 40): `GET/POST /api/xp/levels`, `PATCH /api/xp/levels/:id`, `GET /api/xp/activity-config`, `PATCH /api/xp/activity-config/:activityType`, `GET/POST /api/xp/multipliers`, `PATCH /api/xp/multipliers/:id`, `POST /api/xp/adjust`, `GET /api/xp/stats`.

## Funnel

**Technical:** a producing module (`creator-looks`, `follows`, `payments`, `commissions`, ...) either calls `xpService.awardXp(...)` directly, or — for the activities already wired — simply publishes its existing domain event and `xp.events.ts` picks it up asynchronously. Either way, XP is a side effect of an activity that already succeeded, never a precondition for it: nothing in this module can block or fail the triggering request, per the fail-open convention below. `awardXp` reads `ActivityXpConfig` for that activity, runs the configured anti-abuse checks, and — if none reject it — writes an `XpTransaction` row and atomically increments `UserProgress.totalXp` in one transaction, recomputing `currentLevelId` only if it actually changed.

**User-facing:** `apps/web`'s `/dashboard/progress` (creator-dashboard feature, `ProgressSection`) shows a level/XP-bar card (`LevelProgressCard`, using the new shared `@outfiqe/design-system` `ProgressBar` primitive) plus a paginated recent-activity list (`XpTransactionRow`) — reachable from a new "Progress" item in `DashboardSidebar`'s creator nav (not shown for brand accounts, which don't participate in gamification). When an admin has an `XpMultiplier` window live, a banner (`XpMultiplierBanner`) sits above the level card naming it and its end time.

**XP multipliers, technical:** an admin creates a time-boxed `XpMultiplier` (a label, a multiplier, a start/end) from the gamification dashboard. `awardXp` — and only `awardXp` — resolves `xpRepository.findActiveMultiplier(now)` right after computing the activity's configured `xpAmount`, scales it via `applyMultiplier`, and, when a multiplier actually applied, records both the multiplier and the pre-multiplier `baseAmount` in the `XpTransaction`'s own `metadata` so the ledger stays self-explanatory (a `30` XP row for a `10`-XP activity is otherwise a mystery). No `ActivityXpConfig`/anti-abuse row changes — the multiplier is a pure post-processing step on the amount an activity would have earned anyway, checked once per award, no new dedup/cooldown concept needed.

## Non-obvious rationale

**Award is fail-open, not fail-closed.** A Redis-style "never fail the caller's request" convention, applied to Postgres here instead: any error inside `awardXp` (a bad config row, a transient DB error) is caught, logged via `logger`/`describeError`, and returned as a typed `{ awarded: false }` — the like/follow/purchase that triggered it must never fail because XP bookkeeping hiccupped.

**`grantFixedXp` bypasses `ActivityXpConfig`/anti-abuse entirely — a deliberate second entry point, not a shortcut around the real one.** `awardXp` (config-gated, anti-abuse-checked) and `grantFixedXp` (unconditional) both funnel into the same private `applyXpTransaction` — the actual ledger-write + atomic-increment + level-recompute logic is never duplicated. `grantFixedXp` exists for XP awards that are already deduped by their own caller and have no sensible "activity config" to look up: `achievements` calls it for `ACHIEVEMENT_UNLOCKED` (an achievement can only ever unlock once per user, enforced by `UserBadge`'s own unique constraint — a daily cap or cooldown would be meaningless), and a future admin manual-adjustment chunk is expected to call it too (an operator-entered amount has no per-activity default to look up in the first place).

**`ActivityXpConfig` has no row for every `XpActivityType` value.** `FOLLOWER_MILESTONE`, `ACHIEVEMENT_UNLOCKED`, and `ADMIN_ADJUSTMENT` are valid ledger tags with deliberately no config row — none of them are a flat, repeatable per-occurrence amount `awardXp`'s config-gated path makes sense for. `ACHIEVEMENT_UNLOCKED` never actually needs one, since `achievements` calls `grantFixedXp` (see above), not `awardXp`, for it. `FOLLOWER_MILESTONE` remains unused by anything yet (no follower-milestone achievement is seeded); if one is added later it would follow the same `grantFixedXp` path. Calling `awardXp` (not `grantFixedXp`) with any of these today correctly no-ops as `ACTIVITY_DISABLED` (no config found), which is the right fail-safe default even though nothing currently does that by mistake.

**Level recompute avoids a lost-update race without pessimistic locking.** `incrementProgress` uses Postgres's atomic `UPDATE ... SET total_xp = total_xp + $amount` (via Prisma's `increment`), never a read-then-write of `totalXp` in application code — two concurrent awards for the same user (a viral post getting rapid-fire likes) can't stomp on each other. The "previous level" needed to detect a level-up is derived arithmetically from the authoritative post-increment total (`updatedTotalXp - amount`) rather than a separate read taken before the transaction, which would itself be race-prone under READ COMMITTED.

**Anti-abuse dedup (spec 06's "follow a creator only earns XP once") is a plain existence check, not a DB constraint.** `maxPerEntity` is enforced by counting existing `XpTransaction` rows for `(userId, activityType, relatedEntityId)` before writing a new one — a read-then-write, not an atomic constraint. Accepted as a minor, low-severity race (worst case: one duplicate small XP award under true concurrent double-submission of the same action), the same class of tradeoff already accepted elsewhere in this codebase for non-financial, non-scarce data — unlike stock decrement, XP has no correctness requirement that justifies a DB-level uniqueness constraint here.

**Daily limits are a rolling 24h window, not a calendar-day reset.** Simpler than tracking timezone-aware "midnight" boundaries, and functionally equivalent for the stated goal (cap how much XP one activity can produce per day).

**Self-interaction is excluded only on the _receiving_ side.** `xp.events.ts` skips `LOOK_LIKE_RECEIVED`/`LOOK_COMMENT_RECEIVED` when the actor is the look's own creator (a creator liking/commenting on their own post can't inflate their own "received" XP), but does _not_ skip `LOOK_SAVED`/`LOOK_COMMENTED` (the actor-earned side) for the creator's own content — there's no double-dip there, just a creator bookmarking or commenting on their own post, which is legitimate use, not the abuse spec 06 is describing.

**`USER_FOLLOWED` only awards XP when the followed user is an approved creator.** The domain event itself fires for following _any_ user (creator or not); `xp.events.ts` checks `isCreator`/`creatorStatus` before awarding, matching spec 04's "Follow a **creator**" wording rather than the broader "follow anyone" the raw event covers. This mirrors `requireApprovedCreator`'s check (`shared/utils/creator-guard.utils.ts`) without reusing it directly — that helper throws an `AppError` for an HTTP request context, which doesn't fit an event consumer with no response to reject.

**Known limitation: like/unlike and save/unsave farming isn't fully closed.** `CreatorLookLike`/`CreatorLookSave` are existence rows (unique per `(lookId, userId)`, not a per-action log), so there's no stable id to key a `maxPerEntity` dedup off — a user could in principle toggle like/unlike repeatedly to keep re-triggering `LOOK_LIKE_RECEIVED` for a creator. Accepted for MVP: `LOOK_LIKE_RECEIVED`/`LOOK_SAVED` both carry a `dailyLimit`, which bounds the damage to a fixed XP/day ceiling regardless of how many times the same pair toggles — a real per-instance dedup (e.g. a like-event log table) would close this fully but isn't built here. Flagging explicitly rather than leaving it silently unaddressed.

**`PRODUCT_PURCHASED` fires from two different modules, asymmetrically by payment method — this mirrors how stock decrement itself already works, not a new inconsistency.** For COD, `orders/order.service.ts` publishes it right after `checkoutOnce`'s transaction commits (stock is decremented at checkout for COD). For eSewa/Khalti, `payments/payment.service.ts` publishes it from `settleVerified`'s success branch, only once the gateway payment is confirmed _and_ stock decrements cleanly — never when `needsManualRefund` is set, since that path is headed for a human refund decision and awarding "purchase" XP there would need a manual reversal mechanism this module doesn't have. One `PRODUCT_PURCHASED` event per **order**, not per line item — buyer XP is deliberately not proportional to how many separate items an order contains, so splitting one purchase into several smaller orders can't be used to farm more "purchase" XP than a single combined order would earn.

**`SALE_GENERATED` fires once per `CreatorCommission` created, for every payment method, at order-placement time** — not gated on payment settlement. This matches `commissions`' own documented lifecycle: a commission is created `PENDING` speculatively at order placement regardless of payment method (see `commissions/README.md`, "Commission creation isn't deferred like stock is"), and voided later if the sale falls through. `SALE_GENERATED`/creator XP follows that same speculative-then-reversed-if-needed philosophy rather than waiting for `AVAILABLE`/`PAID` — reusing the existing lifecycle sweep's "void" path rather than needing its own separate XP-reversal mechanism is a reasonable follow-up if abuse is observed, not built here.

**`PRODUCT_TAGGED` fires per tagged product, not once per post/edit.** On `create()`, once for every product in the new look; on `update()`, only for products present in the new tag set but absent from the old one (reusing the same old-vs-new diff `recountWornBy` already computes, not a second diff). Removing a tag, or re-saving the exact same tag set unchanged, never fires it.

**`LEVEL_UP` is published from inside `applyXpTransaction`, not from `awardXp`/`grantFixedXp` individually**, so every XP-awarding path — the config-gated one and the fixed-amount one used by `achievements`/admin adjustments — gets the "moment" for free without duplicating the `leveledUp` check at each call site. It's published outside the `prisma.$transaction` (after it resolves, only when `result.awarded && result.leveledUp`), same as every other domain-event publish in this codebase — event publishing is a Redis operation with no place inside a Postgres transaction's atomicity boundary. Going through the domain-event bus (Redis Streams + a `socket-broadcast` consumer, `xp.socket.ts`) rather than calling `getIO().to(userRoom(...)).emit(...)` directly from here was a deliberate choice, not the shorter path: it keeps XP-awarding fully decoupled from Socket.IO (this module never imports `#socket/*` directly), and gets the same retry/dead-letter durability every other domain event gets for free if a transient Redis hiccup drops the first attempt — real value even for an ephemeral toast, since it's "retry a flaky publish a few times" rather than "silently never emit."

**Levels are deactivated, never deleted — `Level` has no `DELETE` route at all.** `UserProgress.currentLevelId` is a required (non-optional) FK to `Level`, so a hard delete of a level anyone currently holds would violate that constraint outright; there's no code path where deleting one could even succeed once it's in use. `PATCH /api/xp/levels/:id` (which accepts `isActive`) is the only removal path, matching the same "void, don't delete" convention `CreatorCommission`/`CommissionTier`/`UserBadge` already use — a deactivated level stays exactly where it is for anyone already on it; `computeLevelProgress` only reads `isActive: true` levels when resolving where a fresh XP total lands, so a deactivated level just stops being reachable going forward.

**`adjustXp` validates the resulting total won't go negative _before_ calling `grantFixedXp`, as a real pre-check, not a caught error.** `Prisma`/Postgres has no natural constraint to express "this column can't go below zero via an `increment`" short of a `CHECK` constraint this schema doesn't have, so the guard is application-level: read the user's current `totalXp` (0 if they have no `UserProgress` row yet), reject with `422` if `currentTotalXp + amount < 0`. This is a plain read-then-write, not atomic — but the actor here is an admin acting one adjustment at a time through a form, not a public endpoint under concurrent load, so the race window (two simultaneous docks on the same user landing it just past zero) is accepted as effectively theoretical, unlike the public-facing dedup cases elsewhere in this build that got a real DB-level fix.

**`adjustXp` grants `XpActivityType.ADMIN_ADJUSTMENT` — the enum value this build seeded from the start specifically for this, with deliberately no `ActivityXpConfig` row (see above).** It carries `source: XP_SOURCE.ADMIN` and `metadata: { reason, adminUserId }` so the ledger keeps a full audit trail of who adjusted what and why, distinct from `badgeService.awardBadge`'s own XP grant (which reuses `ACHIEVEMENT_UNLOCKED`, since a manually-awarded badge's XP reward is conceptually the same "you unlocked a badge" event as an engine-awarded one — see `badges/README.md`).

**An active XP multiplier scales `awardXp`, never `grantFixedXp` — a deliberate scope line, not an oversight.** `grantFixedXp` is what `achievements` calls for badge XP rewards and what `adjustXp` calls for manual admin corrections (see the note above on why `grantFixedXp` exists as a second entry point at all). Neither of those should ever be silently altered by an unrelated promotional event: an admin typing "+50 XP, refunding a support issue" must grant exactly 50, not 100 because a weekend multiplier happens to be running at the same moment, and a badge's designed XP reward is a fixed prize amount an admin set when building the badge, not "activity you did" in the sense a multiplier weekend is meant to reward. Scoping the multiplier resolution to sit inside `awardXp` itself (before it calls the shared `applyXpTransaction`), rather than inside `applyXpTransaction` where both paths would pick it up, is what keeps that guarantee real rather than incidental.

**Overlapping multiplier windows take the single highest value, they don't stack.** `findActiveMultiplier` orders by `multiplier: "desc"` and takes the first match rather than summing or multiplying every currently-active window together — an admin who (by mistake or by design) schedules two overlapping promotions shouldn't produce a runaway 6x from a 2x and a 3x compounding. "Highest wins" is the simpler, safer semantics for something admin-configured with real economic weight (real XP, real level-ups), and it's what an admin would expect from two promotions overlapping in the real world too: you get the better one, not both.

**`XpMultiplier.startsAt`/`endsAt` are always required, never optional, unlike `Achievement`'s seasonal window.** A multiplier with no end date is exactly the kind of thing that gets left on by accident and never turns itself off — `Achievement.activeFrom`/`activeUntil` are optional because most achievements are permanent and a seasonal one is the exception; every `XpMultiplier` row is inherently a temporary event by definition, so there's no permanent-by-default case to support. An admin who wants to end one early still can, via the `isActive` toggle (`PATCH /api/xp/multipliers/:id`) — the same "void, don't delete" pattern `Level`/`Badge` already use, not a second removal mechanism.

**`amount * multiplier` is rounded to the nearest whole XP with `Math.round`, not truncated.** `XpTransaction.amount` is an `Int` column, and a fractional multiplier (`1.5x`) against an odd `xpAmount` produces a non-integer result — rounding to nearest is the fairest rule for something a user is earning (truncating would always shortchange them by up to almost a full point; ceiling would always slightly overpay). `applyMultiplier` is the one place this happens, unit-tested directly against both an even and an odd base amount.
